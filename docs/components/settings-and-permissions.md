# Settings and permissions

> How the harness is configured — the layered settings.json, the permissions CLI, the per-stage grant channel, and the action taxonomy that decides which tool calls run without a prompt.

Three related surfaces control what the agent may do without asking and how the harness behaves.

**Settings.** The policy settings live in [settings/](../../settings/README.md) as [settings/base.json](../../settings/base.json), the versioned source merged per machine by `setup-symlinks.sh` (which calls `apply-settings.sh`). The merge is **additive**, so dropping a key from the source does not clear it from the live settings — a deliberate change must overwrite, not omit. This is where the harness-level knobs and the fleet-wide allowlist of pre-authorized tool calls are defined; by invariant it may hold only side-effect-free (read-only) entries (see [[settings-permission-tiers]]).

**Permissions.** The workflow-level permission grants live in [permissions/](../../permissions/README.md), driven by [scripts/permissions-cli.py](../../scripts/permissions-cli.py). These are operational config (which actions are pre-authorized for which scope), separate from memory and from the settings allowlist.

**Grant channel.** A code-executing or write grant scoped to ONE plan stage's ONE spawned child — neither fleet-wide (so not `settings/base.json`) nor durable across stages (so not a per-kind baseline) — is declared in that stage's `[stage.grants]` table or derived automatically from its own `verify_command`/output artifacts, validated by `scripts/agentctl/grants.py`, and materialized only into that child's own `--settings`/`--add-dir`. Validation is a shape check over rule text, not a completeness boundary over what a shell command line can do at run time — it cannot be complete over shell command lines, and catching an actual escalation attempt at execution time is the PR-C guard's job, not the validator's. Program identification for that shape check looks past a wrapper's own operand tokens (`flock <lockfile>`, `timeout -s KILL`), not just its known dash-flags, so a wrapper cannot hide a refused program behind it. See `scripts/agentctl/README.md` § `[stage.grants]` for the declaration shape and derivation rules, and [[settings-permission-tiers]] § Grant channel for the never-grantable forms, approval binding, and named residuals.

**Action taxonomy.** Side-effect-free actions are pre-authorized as a class — reads, searches, `--help`, `--dry-run`, and the read-only MCP verbs — so the agent never prompts for them. The classification is enforced by a `classify_action` verb taxonomy in the versioned settings, not re-decided per call. Plan-scope-declared actions become pre-authorized once a plan is approved (anything the plan names in its reference files, outputs, or declared operations, including its stage grants), which is why the [plan-approval gate](../architecture/coordination-engine.md) is the boundary that matters: before it, production edits are denied; after it, the declared scope proceeds without re-asking.

## Hook decision semantics

The permissions reference above documents what a PreToolUse hook's `permissionDecision` values (`ask`/`deny`) are *supposed* to mean, but not what they actually do per permission mode, nor whether a requested `--permission-mode` even takes effect. [scripts/probe-hook-decision-semantics.py](../../scripts/probe-hook-decision-semantics.py) measures this directly — every row below is one real, bounded `claude` run (a scratch PreToolUse hook returning a fixed decision for any Bash call), never inferred from documentation; a cell that could not be observed is recorded as such.

| Cell | Requested mode | Decision | Effective mode | Sentinel ran | Prompt shown | Timed out | Notes |
|---|---|---|---|---|---|---|---|
| `headless:default:ask` | default | ask | default | no | no | no | permission denied (result.permission_denials) |
| `headless:default:deny` | default | deny | default | no | no | no | permission denied (result.permission_denials) |
| `headless:acceptEdits:ask` | acceptEdits | ask | acceptEdits | no | no | no | permission denied (result.permission_denials) |
| `headless:acceptEdits:deny` | acceptEdits | deny | acceptEdits | no | no | no | permission denied (result.permission_denials) |
| `headless:auto:ask` | auto | ask | default | no | no | no | permission denied (result.permission_denials) |
| `headless:auto:deny` | auto | deny | default | no | no | no | permission denied (result.permission_denials) |
| `headless:bypassPermissions:ask` | bypassPermissions | ask | bypassPermissions | no | no | no | permission denied (result.permission_denials) |
| `headless:bypassPermissions:deny` | bypassPermissions | deny | bypassPermissions | no | no | no | permission denied (result.permission_denials) |
| `interactive:auto:ask` | auto | ask | not observed | not observed | not observed | no | not observed: hook never fired (last pane showed the task prompt still sitting unsubmitted in the input box, footer reading "⏸ manual mode on") |
| `interactive:auto:deny` | auto | deny | not observed | not observed | not observed | no | not observed: hook never fired (same unsubmitted-prompt evidence as the `ask` cell) |
| `add_dir:accept_edits_read_add_dir` | acceptEdits | n/a (Edit deny via permissions, no hook) | acceptEdits | no | no | no | sentinel_ran=True here means the deny FAILED to hold (write succeeded) — expected False |
| `add_dir:default_write_add_dir` | default (ambient fleet chain) | n/a (Edit allow+deny via permissions, no hook) | default | no | no | no | D2/x written=False (expected True); D2/settings.json written=False (expected False) |

**Measured findings:**

- **In headless (`-p`) sessions, `ask` behaves identically to `deny`.** Every headless cell — including every `ask` decision — shows `sentinel_ran=no` with `result.permission_denials` set, across all four permission modes tested, including `bypassPermissions`. A hook's `ask` decision has no TTY to ask through in `-p` mode, so it resolves to a denial rather than a hang or an implicit allow.
- **A hook's `deny`/`ask` decision overrides even `bypassPermissions`.** `headless:bypassPermissions:ask` and `headless:bypassPermissions:deny` both denied the call — a PreToolUse hook's decision is not bypassed by `--permission-mode bypassPermissions`.
- **`--permission-mode auto` did not take effect in the isolated sandbox** — `headless:auto:ask` and `headless:auto:deny` both report `effective_mode=default`, not `auto`. The requested mode was silently dropped, echoing the `disableBypassPermissionsMode` precedent already noted in the probe script's own docstring (a managed setting can silently override a requested mode).
- **The interactive cells are not observed, and the first round's "observed" result for them was wrong.** The probe now writes one witness-file line from inside the scratch hook itself on every invocation, so a cell only counts as observed if the hook demonstrably ran for the sentinel call — not merely because the tmux pane produced *some* text. Under that rule, the round-1 result (`effective_mode=auto`, `sentinel_ran=no`, `prompt_shown=no`) turns out to have been a false "observed": the witness shows the hook never fired at all — the child was still stuck at a pre-task dialog, and what looked like a clean denial was actually a session that never reached a tool-use attempt. Two distinct blocking dialogs were found and are now handled differently: (1) launching the tmux pane's cwd inside a fresh, untrusted scratch directory hit the folder-trust ("quick safety check") dialog, whose pre-selected default is **"No, exit"** — sending a blind `Enter` (the prior code's `_dismiss_onboarding` did this for every detected dialog) would have silently killed the session rather than dismissing anything; fixed by launching the pane's cwd in `WORKTREE_ROOT` instead (already trusted, since spawns run there) and by adding a dedicated `detect_trust_dialog` check that `_dismiss_onboarding` now consults first and never sends `Enter` into. (2) With the trusted worktree root as cwd, a second, different dialog appeared: this repo's own `CLAUDE.md` carries external `@`-imports (`~/.claude-agent/config.md`, `~/.claude-agent/memory-global/MEMORY.md`), which the TUI gates behind a one-time "Accessing untrusted files… external imports" security dialog; its default, "No, disable external imports", is safe to accept (it does not exit or grant anything), so it was added to `ONBOARDING_INDICATORS` for auto-dismissal. After both fixes the child gets as far as the task prompt being typed into the input box (visible in the pane capture) but the box shows it un-submitted and a footer reading `⏸ manual mode on` — the witness confirms the hook still never fires, so the cell remains honestly not-observed rather than reporting a fabricated decision. Getting the interactive TUI to actually submit that prompt via `tmux send-keys` is left as an open item for whichever later stage needs a live interactive-mode observation; PR-C's guard design should treat "interactive `ask`/`deny` semantics" as unmeasured, not as "same as headless."
- **The `add_dir:default_write_add_dir` cell did not match its expected shape** (expected the write to succeed under the ambient fleet chain; it did not). Per this stage's brief, this is reported as a measured finding here, not fixed — the grant-materialization fix belongs to a later stage of the same plan.
