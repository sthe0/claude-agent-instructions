# Settings and permissions

> How the harness is configured — the layered settings.json, the permissions CLI, the per-stage grant channel, and the action taxonomy that decides which tool calls run without a prompt.

Three related surfaces control what the agent may do without asking and how the harness behaves.

**Settings.** The policy settings live in [settings/](../../settings/README.md) as [settings/base.json](../../settings/base.json), the versioned source merged per machine by `setup-symlinks.sh` (which calls `apply-settings.sh`). The merge is **additive**, so dropping a key from the source does not clear it from the live settings — a deliberate change must overwrite, not omit. This is where the harness-level knobs and the fleet-wide allowlist of pre-authorized tool calls are defined; by invariant it may hold only side-effect-free (read-only) entries (see [[settings-permission-tiers]]).

**Permissions.** The workflow-level permission grants live in [permissions/](../../permissions/README.md), driven by [scripts/permissions-cli.py](../../scripts/permissions-cli.py). These are operational config (which actions are pre-authorized for which scope), separate from memory and from the settings allowlist.

**Grant channel.** A code-executing or write grant scoped to ONE plan stage's ONE spawned child — neither fleet-wide (so not `settings/base.json`) nor durable across stages (so not a per-kind baseline) — is declared in that stage's `[stage.grants]` table or derived automatically from its own `verify_command`/output artifacts, validated by `scripts/agentctl/grants.py`, and materialized only into that child's own `--settings`/`--add-dir`. Validation is a shape check over rule text, not a completeness boundary over what a shell command line can do at run time — it cannot be complete over shell command lines, and catching an actual escalation attempt at execution time is the PR-C guard's job, not the validator's. See `scripts/agentctl/README.md` § `[stage.grants]` for the declaration shape and derivation rules, and [[settings-permission-tiers]] § Grant channel for the never-grantable forms, approval binding, and named residuals.

**Action taxonomy.** Side-effect-free actions are pre-authorized as a class — reads, searches, `--help`, `--dry-run`, and the read-only MCP verbs — so the agent never prompts for them. The classification is enforced by a `classify_action` verb taxonomy in the versioned settings, not re-decided per call. Plan-scope-declared actions become pre-authorized once a plan is approved (anything the plan names in its reference files, outputs, or declared operations, including its stage grants), which is why the [plan-approval gate](../architecture/coordination-engine.md) is the boundary that matters: before it, production edits are denied; after it, the declared scope proceeds without re-asking.
