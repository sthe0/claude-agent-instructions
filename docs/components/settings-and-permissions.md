# Settings and permissions

> How the harness is configured — the layered settings.json, the permissions CLI, the per-stage grant channel, and the action taxonomy that decides which tool calls run without a prompt.

Three related surfaces control what the agent may do without asking and how the harness behaves.

**Settings.** The policy settings live in [settings/](../../settings/README.md) as [settings/base.json](../../settings/base.json), the versioned source merged per machine by `setup-symlinks.sh` (which calls `apply-settings.sh`). The merge is **additive**, so dropping a key from the source does not clear it from the live settings — a deliberate change must overwrite, not omit. This is where the harness-level knobs and the fleet-wide allowlist of pre-authorized tool calls are defined; by invariant it may hold only side-effect-free (read-only) entries (see [[settings-permission-tiers]]).

**Hooks.** Hooks are a machine-specific key, so `base.json` carries none: `scripts/install-reminder-hooks.sh` writes Core's rows into `<config root>/settings.json`, and then merges the **hook fragments** in `<config root>/hook-plugins/*.json` (`settings.json`'s `hooks` shape; `setup-symlinks.sh` creates the directory with a README stub). In a command, `@FRAGMENT_DIR@` expands, unquoted, to the fragment file's real directory (write `"@FRAGMENT_DIR@/x.py"` if the path may contain whitespace). `<config root>/hook-plugins.installed.json` records what each fragment installed, so every run keeps a healthy fragment's entries equal to its current ones and removing a fragment removes exactly them, never a hand-added hook (the record keeps each installed hook object, so a hand entry with the same command but another body is not taken; a byte-identical hand copy cannot be told apart). The sync runs in two phases over all fragments, so an entry moved between fragments lands in its new one on the same run; group order is not maintained. A missing record reads as empty (installed entries look hand-added, nothing is removed); an unparsable one skips the whole fragment pass with a warning, and Core's own pass then sees fragment entries as ordinary hooks (it may retime one that runs a Core script name). An entry is identified by its optional string `id` (fragment-only, never written into `settings.json`), else by its exact expanded command; nothing is parsed to decide it. An entry whose command is already present in the same event and matcher (a hand entry, a Core row, another fragment's entry) is skipped with a stderr warning, and an installed entry is dropped with a warning once an identical command appears, so one command never fires twice from the seam. An entry whose script file name equals that of another entry of the group (a differently spelled copy of one gate) is still installed, with an advisory warning naming both: it may fire twice. A broken fragment (unparsable, a dangling symlink, or naming a script missing under its directory) is skipped with a warning and keeps its installed entries. The personal root gets no fragments; `doctor.sh` warns when a fragment entry is not installed. Contract: `scripts/lib/hook_fragments.py`.

**Child outside any project.** Hooks that a project registers in its own settings reach a spawned child only if the client treats the child's start directory as a project; a child started elsewhere runs without them. `spawn-specialist.py` therefore refuses such a spawn when the parent's project registers hooks. *Project* follows the Claude Code rule (checked against client 2.1.310): a directory is a project if the client would load its `.claude/settings.json`, the `.claude/settings.local.json` at the root of its git repository (for a linked worktree, the main checkout's root; outside git, the directory itself), or a legacy `.claude/settings.local.json` in the directory. User-level files of the harness root and the managed file never count. The parent's directory is taken from `$CLAUDE_PROJECT_DIR`, else from the cwd recorded in the session transcript named by `CLAUDE_CODE_SESSION_ID`, else from the process cwd; a transcript that cannot be resolved counts as a parent with hooks. The parent counts as in a project only when its project settings register at least one hook (an unreadable or unparsable file counts as registering), and a child in any project passes, so a cross-project spawn is allowed. A refusal exits 2 and prints `Refusal: child-outside-project`; stderr names both directories, the parent's project files and the remedy. On a machine whose Core main checkout lacks `.claude/settings.local.json`, the remedy is to create it there (`{}` suffices), after which every Core worktree is a project. A spawn that only assembles a prompt (`assembled_prompt`) is not checked. `--allow-child-outside-project REASON` overrides the refusal for one spawn: a blank reason is rejected, a stderr notice quotes the reason and both directories, and the spawn's cost-log row carries `child_outside_project_override`. `agentctl dispatch` has no override: it parks the stage as BLOCKED with an ESCALATE directive naming the venue and the remedy. A client older than the checked version may load project files differently, so the check can pass or refuse wrongly there.

**Permissions.** The workflow-level permission grants live in [permissions/](../../permissions/README.md), driven by [scripts/permissions-cli.py](../../scripts/permissions-cli.py). These are operational config (which actions are pre-authorized for which scope), separate from memory and from the settings allowlist.

**Grant channel.** A code-executing or write grant scoped to ONE plan stage's ONE spawned child — neither fleet-wide (so not `settings/base.json`) nor durable across stages (so not a per-kind baseline) — is declared in that stage's `[stage.grants]` table or derived automatically from its own `verify_command`/output artifacts, validated by `scripts/agentctl/grants.py`, and materialized only into that child's own `--settings`/`--add-dir`. Validation is a shape check over rule text, not a completeness boundary over what a shell command line can do at run time — it cannot be complete over shell command lines, and catching an actual escalation attempt at execution time is the PR-C guard's job, not the validator's. Program identification for that shape check looks past a wrapper's own operand tokens (`flock <lockfile>`, `timeout -s KILL`), not just its known dash-flags, so a wrapper cannot hide a refused program behind it. See `scripts/agentctl/README.md` § `[stage.grants]` for the declaration shape and derivation rules, and [[settings-permission-tiers]] § Grant channel for the never-grantable forms, approval binding, and named residuals.

**Resource resolution.** A grant or a `Rule:` line is not itself the coverage check — `scripts/agentctl/tool_contracts.py`'s `resolve_command(text, venue, contract_table=...)` resolves the literal command text to a typed `Resolution` (`status`, `resources`, `reason_class`, `identity`) against `scripts/agentctl/tool_contracts.toml`, the contract table of record. A resolution that cannot be pinned to a resource — an ad-hoc script, a `:*` wildcard tail, an unlisted program — comes back `unresolved` (`reason_class` one of `residual-syntax` / `adhoc-undeclared` / `contract-unresolved` / `wildcard-tail` / `unknown-program`) and falls through to asking the user rather than being treated as covered. `scripts/agentctl/plan_resources.py`'s `resolve_rule_grant` / `compute_stage_resources` apply the same resolution at the plan and stage level.

**Per-segment resolution (`resolve_segments`).** `tool_contracts.resolve_segments(text, venue)` is the hook-side counterpart of `resolve_command`, implemented in `scripts/agentctl/segment_resolver.py`; `resolve_command` and the contract table are unchanged. It splits a Bash command on `&&`, `||`, `;`, `&`, `|` and newlines and returns one `Segment` per piece (`status` resolved / opaque / unresolved, `resources`, `opaque_kind`, `reason_class`, `venue` — the cwd it ran in, `None` when unknown). It fails closed: an under-resolved segment costs one prompt, an over-resolved one silently auto-allows, so a form resolves only when it is on an explicit allow-list whose whole effect can be named. Git writes are the allow-list `segment_resolver.GIT_WRITE_FORMS` (`add`, `commit`, `restore`, `rm`, `mv`, `merge`, `checkout`, `switch` and path-form `reset`, each with a closed flag set; push to a literal ref, read-only subcommands) and give a `FileResource(<worktree root>, write)`, with `commit`/`merge` also a `VcsRefResource('.', <branch>, 'commit')` and a push normalised to the branch it names (a destination of `HEAD`, which git creates as a remote ref of that name, is unresolved); `stash`, `rebase`, `pull`, `am`, `cherry-pick`, a commit-ish `reset`, branch-creating or ref-forcing `checkout`/`switch` flags, and `checkout`/`switch <name>` unless `<name>` is an existing local branch (a remote-only match makes git create the branch and write the shared config) are unresolved. `git -C <dir>` and `cd <dir> && git …` resolve only inside the venue's own repository (same git common directory — another repository has its own refs, hooks and config). A commit or merge is attributed to the current branch only when no other segment of the line — before it or running concurrently under `&`/`|` — is a branch switch, unresolved or opaque; an and-or list that ends in `&` runs as a whole in the background, so everything after it counts as concurrent. `mkdir -p` lists the topmost directory it creates, not the leaf. Redirect and `tee` targets give `FileResource(path, write)` (`/dev/null` and fd duplications have no effect). Only a resolved or opaque segment keeps the working directory: a `cd` re-bases `&&`-chained successors, but one reached through `||` or `&`, inside a pipeline, with `-L`/`-P`, to a symlinked directory (bash tracks the logical path, so a later `..` differs), or with a bare operand while `CDPATH` is set, leaves the cwd unknown, as does any unresolved segment, so a later relative segment is unresolved. `python3 -c`, a heredoc or here-string body fed to an interpreter and `python3 <script>` are `opaque` (`python-c` / `stdin-body` / `script-file`) only in a known cwd and only when the code is literal text in the segment — their own effect is not decided, though their redirect targets are still listed. Code held in a variable, a script operand that is not literal, stdin fed by a pipe or `< file`, inline-code flags such as `perl -ne` or `node --eval=x`, and an `awk` program that is not literal are `unresolved`. Syntax the scanner cannot read exactly (`$'..'`, a command substitution in an unquoted heredoc body, an unterminated quote) is `residual-syntax`. A consumer may act on resolved segments only and must treat any opaque or unresolved segment as not fully decided.

**Action taxonomy.** Side-effect-free actions are pre-authorized as a class — reads, searches, `--help`, `--dry-run`, and the read-only MCP verbs — so the agent never prompts for them. The classification is enforced by a `classify_action` verb taxonomy in the versioned settings, not re-decided per call. Plan-scope-declared actions become pre-authorized once a plan is approved (anything the plan names in its reference files, outputs, or declared operations, including its stage grants), which is why the [plan-approval gate](../architecture/coordination-engine.md) is the boundary that matters: before it, production edits are denied; after it, the declared scope proceeds without re-asking.

## Hook decision semantics

The permissions reference above documents what a PreToolUse hook's `permissionDecision` values (`ask`/`deny`) are *supposed* to mean, but not what they actually do per permission mode, nor whether a requested `--permission-mode` even takes effect. [scripts/probe-hook-decision-semantics.py](../../scripts/probe-hook-decision-semantics.py) measures this directly — every row below is one real, bounded `claude` run (a scratch PreToolUse hook returning a fixed decision for any Bash call), never inferred from documentation; a cell that could not be observed is recorded as such.

| Cell | Requested mode | Decision | Effective mode | Sentinel ran | Prompt shown | Timed out | Notes |
|---|---|---|---|---|---|---|---|
| `headless:default:ask` | default | ask | default | no | no | no | permission denied (result.permission_denials) |
| `headless:default:deny` | default | deny | default | no | no | no | permission denied (result.permission_denials) |
| `headless:acceptEdits:ask` | acceptEdits | ask | acceptEdits | no | no | no | permission denied (result.permission_denials) |
| `headless:acceptEdits:deny` | acceptEdits | deny | acceptEdits | no | no | no | permission denied (result.permission_denials) |
| `headless:auto:ask` | auto | ask | default | no | no | no | permission denied (result.permission_denials) |
| `headless:auto:deny` | auto | deny | default | no | no | no | permission denied (result.permission_denials) |
| `headless:bypassPermissions:ask` | bypassPermissions | ask | bypassPermissions | no | no | no | permission denied (result.permission_denials) |
| `headless:bypassPermissions:deny` | bypassPermissions | deny | bypassPermissions | no | no | no | permission denied (result.permission_denials) |
| `interactive:auto:ask` | auto | ask | `⏸ manual mode on · ? for shortcuts · ← 2 agents` | no | yes | no | hook fired; footer: '⏸ manual mode on · ? for shortcuts · ← 2 agents' |
| `interactive:auto:deny` | auto | deny | `⏸ manual mode on · ? for shortcuts · ← 2 agents` | no | no | no | hook fired; footer: '⏸ manual mode on · ? for shortcuts · ← 2 agents' |
| `add_dir:accept_edits_read_add_dir` | acceptEdits | n/a (Edit deny via permissions, no hook) | acceptEdits | no | no | no | sentinel_ran=True here means the deny FAILED to hold (write succeeded) — expected False |
| `add_dir:default_write_add_dir` | default (ambient fleet chain) | n/a (Edit allow+deny via permissions, no hook) | default | no | no | no | D2/x written=False (expected True); D2/settings.json written=False (expected False) |

**How the interactive cells are observed.** The probe drives the tmux pane by sending the task prompt as a literal paste (`tmux send-keys -l <text>`), waiting, then sending `Enter` as a separate `send-keys` call — one `send-keys <text> "Enter"` call lands the whole thing as a paste with the `Enter` swallowed, so the prompt never submits. `CLAUDE_CONFIG_DIR` is forwarded into the tmux session explicitly via `tmux new-session -e CLAUDE_CONFIG_DIR=...`, because a tmux session inherits the tmux *server's* environment, not the launching process's, and without it the child reports "Login expired" instead of running on the fleet's own login chain. `sentinel_ran` is read from a FILE the sentinel command itself creates, never from matching the marker in the pane text — the marker also appears, unsubmitted, inside an `ask` dialog's still-pending command box. `effective_mode` for an interactive cell is the TUI's own bottom-of-pane mode-status footer, kept literal.

**Measured findings:**

- **In headless (`-p`) sessions, `ask` behaves identically to `deny`.** Every headless cell — including every `ask` decision — shows `sentinel_ran=no` with `result.permission_denials` set, across all four permission modes tested, including `bypassPermissions`. A hook's `ask` decision has no TTY to ask through in `-p` mode, so it resolves to a denial rather than a hang or an implicit allow.
- **A hook's `deny`/`ask` decision overrides even `bypassPermissions`.** `headless:bypassPermissions:ask` and `headless:bypassPermissions:deny` both denied the call — a PreToolUse hook's decision is not bypassed by `--permission-mode bypassPermissions`.
- **`--permission-mode auto` does not take effect in the isolated sandbox.** `headless:auto:ask` and `headless:auto:deny` both report `effective_mode=default`, not `auto`. The requested mode is silently dropped, matching the `disableBypassPermissionsMode` precedent noted in the probe script's own docstring: a managed setting can silently override a requested mode.
- **`--permission-mode auto` does not take effect in the interactive session either.** Both interactive cells' footer reads `⏸ manual mode on`, matching the headless finding above. "Manual mode" for an `auto` request means the TUI still requires per-tool confirmation (the `ask` cell's dialog) rather than the auto-accept behavior `--permission-mode auto` is documented to produce; guard design should treat interactive `auto` as behaving like `default`, not as bypassing confirmation.
- **The `add_dir:default_write_add_dir` cell does not match its expected shape.** The write into the `--add-dir`'d directory under the ambient fleet chain does not succeed (expected: it should). The grant-materialization fix for this is tracked separately, as a later stage of the same plan.

**Guard-side consequence.** Because a headless `ask` resolves to a denial with its `permissionDecisionReason` dropped (the finding above), a spawned specialist (`AGENT_RECURSION_DEPTH >= 1`) that hits an `ask`-branch fire in [scripts/hook-guard-permission-surface.py](../../scripts/hook-guard-permission-surface.py) never sees why — it has no TTY for the `ask` dialog to reach. At that depth `main()` now returns `deny` in place of the G-branch's own `ask` verdict, with a `PERMISSION-REQUEST:` hint appended to the reason directing the child to surface the block to its parent (Action/Why/Fallback, per the specialist marker protocol) rather than retry blindly. At depth 0 the decision, branch, and message are unchanged — this is a depth-gated addition applied at the point of decision delivery, not a new branch of guard logic.
