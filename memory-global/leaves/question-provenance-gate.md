## Difficulty

An ungrounded planning leap — "the reporter says it reproduces", "the goal is agreed", "that path exists" — dissolves in confident prose and is never addressable by a reviewer: there is no NAMED record, bound to a NAMED plan element, carrying a NAMED source and an asserted inference. The ledger closes this on the *resolution* axis (every load-bearing claim in the deliverable grounded), but a plan is approved and executed long before resolution; a false premise baked in at plan-approval time has already cost the execution before any claim ledger runs. The plan_approval boundary needs its own provenance gate, and — like enumeration for the ledger — *which questions exist* is perception the engine must not regex-extract, while *whether the recorded set is structurally dispositioned* is a decidable form the engine owns.

## Guidance

**The mechanism.** The `premise` plugin is the first plugin keying the `plan_approval` core gate (the ledger/experience/tracker plugins key `resolution`). Its `auto_activate` predicate is `weight_class == SUBSTANTIVE` **alone** — unlike the ledger, it does *not* require `deliverable_kind in {reasoning, mixed}`, because a false premise harms a code plan exactly as much as a reasoning one, so every substantive plan is armed the moment `classify` routes it SUBSTANTIVE, with nobody hand-arming it. The `AGENTCTL_PREMISE` env seam force-on (`1`) / force-off (`0`) exists for tests and escape.

**Rule vs perception — the boundary, made explicit:**

| Perception (the coordinator's cognition, never mechanized) | Rule (the engine's, decidable from the bag) |
|---|---|
| *Which* questions a plan raises; which are load-bearing | Every recorded question is dispositioned (`open` never survives approve) |
| Whether a `--reason` / `basis` / `own_research` is honest or a decoy | An `escalated` question carries non-empty `own_research`; a `researched` one carries source+derivation; an `assumed` one carries basis+risk |
| Whether the derivation actually *follows* | A substantive Principle's derivation is not a restatement of the claim |
| Whether the advisor's read was real | The `enumerated` flag is set (the cross-check was RUN against current plan content) |
| *Which* elements the order has; whether a stage genuinely ANSWERS the element bound to it | Every recorded order element is dispositioned `covered` (naming a stage the plan HAS) or `cut` (with a reason); the order bag is non-empty once a plan is submitted |
| Whether a cut is a reasonable narrowing or a quiet abandonment | The cut is IN the essence the user approves, verbatim, and stays current until approve |

**One source, generated views.** Questions live once in the plugin bag; `question-list --format md` and `plan-render` are *generated read views*, never a second store to keep in sync. The thinker plan-review reads `question-list --format md` — that is where the perception layer catches what the structural gate cannot.

**The order half — the plan against the order it answers.** The question families above close what a plan *raises*. They say nothing about whether the plan covers the *order*, and that is a distinct failure with its own history: a plan authored over half a two-part order passes every downstream gate 19/19, because every gate checks the plan. The verdict is honest about a domain nobody ordered ([[verdict-covers-the-evidence-domain-it-claims]]), and the narrowing is never compared to anything, because the comparison existed nowhere — `CLAUDE.md` § Substantive plan changes catches contraction only as an edit to an ALREADY-APPROVED plan, and the replan-coverage gate compares a new plan to the *critique*. So the same bag carries `order_elements`: `order-raise` records each element **of the order**, `order-dispose --as covered --stage <n>` or `--as cut --reason <text>` disposes it, and `premise.validate_order_elements` refuses approval on an undispositioned element, a `covered` one naming no stage or a stage the plan lacks, and a `cut` one with no reason.

**The empty set is the opposite rule on the two halves — deliberately.** An empty *question* bag is legitimate: a plan may honestly raise nothing, so the gate is silent. An empty *order* bag is not: a plan always answers an order, so a submitted plan with no element recorded is itself a blocker. The asymmetry is the point — "no questions" is a possible state of the world, "no order" is only ever a state of the record. The blocker names its own way out (`order-raise`, then `order-dispose`), because a session already in flight when this landed meets it with a submitted plan and an empty bag, and a refusal with no route is the failure mode the mechanism exists to prevent.

**Coverage is shown before approval, not after.** `premise.render_coverage_block` is the single generator of a `[scope]` block: the plan's stage count (its SIZE, seen before the user commits, on the header line rather than through a second mechanism) plus one line per covered and per cut element. `present-plan --kind essence` fast-fails when the rendering does not contain the block — stamping nothing and handing the block back verbatim, because the essence is emitted as a turn's FINAL message and discovering the omission at `approve` would cost the whole present → ask cycle. The gate then re-derives the block from **live** state and requires the stored essence receipt to contain the CURRENT one; that is the only way to catch an element cut AFTER presentation, which the `plan_sha256` binding structurally cannot see, because the bag is not plan bytes. The gate is the authority; the fast-fail is a courtesy. The check is mechanical line-containment over engine-generated text — the essence's free prose is never read ([[regex-not-for-semantic-classification]]).

**Two-directional control norm.** The gate must both REFUSE (an open question / an escalated-with-empty-own_research / an un-run enumeration cross-check each block approve, surfaced as `[premise] …` blockers) AND ALLOW (once every question is dispositioned and the cross-check has run against the current plan digest). A gate that only ever refuses is untested on its allow path; the e2e proves both directions on a session nobody hand-armed.

## Honest ceiling — what is NOT guaranteed

Overselling this mechanism is the likeliest way for it to do harm. Guaranteed (fail-closed, decidable): over the questions ACTUALLY RECORDED, no `open` one survives approve; no `escalated` one has empty own_research; no element-bound question is silently carried across a change to the ELEMENT IT TARGETS (a change to any OTHER element of the same stage no longer invalidates it); every substantive Principle carries a non-restatement derivation; no plan is submitted whose control names a path nothing produces. NOT guaranteed:

- **RECALL < 100%.** A question neither the planner nor the advisor pass surfaces still escapes. The advisor *widens* recall; it does not close it. Inherited verbatim from the ledger's honest residual.
- **FABRICATION.** `own_research: "searched X, found nothing"` and a plausible-but-false `derivation` both clear the gate. The derivation field raises the COST and FALSIFIABILITY of the lie — a fabricated derivation from a REAL source tears on the first cross-check, and a reviewer can test the inference rather than only the citation's existence — but it does not detect it.
- **DECOY.** Recording three trivial questions while the load-bearing one goes unasked passes every structural check. Structure counts questions; it does not weigh them.
- **JUNK RETIRE / DISMISS.** `--reason` is free text and cannot be content-checked.
- **A SYSTEMATICALLY FAILING ADVISOR NO LONGER SILENTLY DISCHARGES THE CROSS-CHECK — NARROWED, NOT CLOSED (F3b) — load-bearing.** A run whose runner **failed** (`enumerated_runner_ok is False`) no longer flips `enumerated` for free: `plugins_premise.premise_blockers` blocks `approve`/`replan` until a typed escape is recorded against the live plan content digest with `agentctl question-enumerate-escape --reason <kind> --note <what happened>`, `<kind>` drawn from the closed set `advisor_timeout` / `advisor_error` / `advisor_unavailable` / `manual_enumeration_done`, or `enumeration_not_landed` for a launch that has not yet landed. What survives, named rather than glossed: an ABSENT advisor (`enumerated_runner_ok is None`) still discharges silently BY DESIGN — the gate's `is False`, never `is not True`, predicate exists so a session with no advisor configured (or a bag minted before these keys existed) is never newly blocked, and this narrower case is what the code's own comments (`cmd_question_enumerate`'s docstring in `cli.py`) now label F3b. A ZERO-PAIR SUCCESSFUL run (`enumerated_runner_ok is True`, empty pair list) also still discharges and is NOT escapable — nothing failed, so a genuinely question-free plan stays indistinguishable at the gate from a model that returned nothing for the wrong reason (a refusal, a truncated response). THE ESCAPE COUNT IS A NUMBER SOMEONE MUST CHOOSE TO LOOK AT — `plugins_premise.escape_counts` makes the discharge visible and countable, per-plan-digest and cumulatively per-session, split into `runner_failure` / `manual` / `not_landed` buckets so a fleet that always clicks through does not read the same as one that always did the work by hand, but nothing forces anyone to watch the numbers. THE CHECK IS NOW EVENTUALLY CONSISTENT — detaching the producer bought back the wait it used to cost `approve`, at the price of a window in which a plan approved right after submission meets a refusal ("launched, not landed, N s remaining"), not a result, until the background pass lands or `enumerate_deadline` expires into the `enumeration_not_landed` escape. If this mechanism is ever audited, the first question to ask is no longer "did the advisor actually return anything, ever" — a failed run now leaves a countable trace — it is whether the escape rate is climbing, and in which bucket. This hole is still load-bearing for the same reason as before: the argument that this is not a second `External research:` token gate rests on the agent NOT controlling the question set (via `question-enumerate`) — and that argument is now as strong as the advisor being healthy OR the escape counts actually being read.
- **PATH REACHABILITY, NOT green-reachability (stage 8).** The lint proves a control command names only existing paths; it cannot prove the command can exit 0 (be green). An aggregate runner exits 1 on any pre-existing red in its scope, most of which the stage does not own — exit-code reachability needs the command RUN, and submit-plan runs at approve time, before the artifacts exist. The exit-code half stays with the control author's perception.
- **REACHABILITY ≠ CONTROL-VALIDITY.** Proving a check's inputs exist proves it CAN run and CAN pass; it does not prove passing means anything. A check that greps for a string it also writes is reachable on both axes and worthless.
- **THE ORDER IS UNENUMERATED — load-bearing, and the largest of these.** The order bag deliberately gets no `question-enumerate` analogue: no independent pass reads the user's message and says which elements it contains. So nothing prevents enumerating the elements off the ALREADY-WRITTEN plan, in which case coverage is trivially total and proves exactly nothing about the order. The mitigation is a directive, not a mechanism — `order-raise --element`'s help text says *enumerate from the text of the order, before `submit-plan`*, and `state.log` timestamps each raise, so an element first raised after `submit_plan` is visible as read-off-the-plan to anyone who looks. Nobody is forced to look. This is the order half's exact counterpart to F3b: the argument that the gate compares plan to order is only as strong as the enumeration was independent.
- **`--stage <n>` PROVES EXISTENCE, NEVER ANSWERING.** A `covered` element bound to stage 2 proves the plan has a stage 2. Whether stage 2 does anything about that element is perception. Binding every element to one real stage passes.
- **`--reason` AND `--element` ARE FREE TEXT.** A cut reasoned "out of scope" clears the gate exactly as a well-argued one does, and an element phrased so vaguely that any stage covers it is well-formed. Same class as JUNK RETIRE above.
- **CONTAINMENT, NOT COMPREHENSION.** The essence check proves the block's lines are PRESENT in the rendering. It does not prove they were presented legibly, or that the user read them; and prose in the same essence that contradicts the block is invisible to the check.

So gap 1 is NARROWED, not closed: an ungrounded leap previously dissolved in confident prose is now a NAMED record, bound to a NAMED element, carrying a NAMED source and an asserted inference — addressable by the thinker review that already runs. The perception layer remains the coordinator's own discipline.

## Incentive gradient (F7 — a designed-in gradient, not a perception ceiling)

`plan.goal` and `plan.done_criterion` targets are EXEMPT from the rebind check (by design: they bind to the order, not to plan bytes), and `question-raise` is deliberately permissive about targets. So an agent minimizing its own friction binds every question to `plan.goal` and never pays a rebind — a goal-bound question is well-formed, dispositionable, and cheap forever, and the gate cannot tell a question that genuinely concerns the order from one parked there to dodge maintenance. This is not a perception ceiling — it is a gradient the design itself creates. Knowingly accepted: (1) the alternative — inferring a question's TRUE target from its text — is exactly the perception the rule/perception table refuses to mechanize, and a wrong inference would misfile the record; (2) the F6 scoped-key fix SHRINKS it materially — under a whole-plan sha ANY edit invalidated EVERY stage-bound question, so the pressure to park on `plan.goal` was constant; scoped to the bound ELEMENT's own definition, a rebind is due only when the element the question targets actually changed — an edit elsewhere in the same stage costs nothing — so the gradient is a slope rather than a cliff. The countermeasure is the thinker review reading `question-list --format md` — perception, the right layer for it.

## Element-scoped invalidation (a question binds to the element it targets, not the whole stage)

`Question.disposed_at_key` used to bind to a digest of a stage's ENTIRE definition (`plan.stage_question_key(stage)`), so editing any one field — a typo in `verify_command`, say — invalidated every question ever raised against that stage, including ones the edit never touched. A `Question.target` of `stage:<n>.<element>` now binds to `stage_question_key(stage, element)`, a digest of only that element's own fields, tagged with the element's name so two elements whose text happens to coincide never collide (`order`, `requirements` and `control` have no stage field of their own and keep falling back to the rest-of-stage definition). `question-rebind --confirm-still-valid` re-affirms either shape by hand when a reviewer judges the change immaterial.

Load-bearing, and the reason this is a NARROWING rather than a loosening: `verify_venue_at_final` is only ever contributed to the hash when a stage actually declares it, never as `... or ""` — a plan predating that field must keep reproducing the pre-existing digest byte-for-byte, or every live session's already-dispositioned question against that stage flips to a stale-key blocker the moment the engine starts reading a field that plan never had. See [ADR-0006](../../docs/adr/0006-premise-invalidation-scope.md) invariant 1. The element form is deliberately STRICTER than a loose field-diff on venue fields (hashed raw, not normalized) — erring toward re-confirmation rather than silently accepting a venue change as immaterial.

## Round budgets (the pre-approval phase's own effort limiter, on both its axes)

Nothing previously capped how many `submit-plan` → thinker-revise → resubmit cycles a plan could churn through before approval — every other phase of the spine (replan count, cost tiers) carries a limiter; the pre-approval phase did not, so the cheapest place to start a round was also the one place its number was invisible. `state.plan_review_rounds` counts `PLAN_READY` resubmissions since the last `approve`, advanced only while a review record actually stands (never re-derived from records on file, since a stage-scoped review staled by the very edit that answered it would then read as "no review happened"). At `effort-replan-absolute` (config.md's Rule-of-Three threshold — the same one `CLAUDE.md`'s effort-divergence trigger reuses, not a new key) `plan_review_blockers` stops demanding another review pass and instead routes to the user: accept the plan as it stands via a distinct-reviewer `plan-review --verdict override`, naming why, or cut scope and resubmit — which does not itself refill the budget. The threshold never approves by itself; a scope or risk question at round three is the customer's to answer, not the engine's.

**The enumeration axis is the same shape and needed the same budget.** `cmd_question_enumerate_escape`'s docstring used to argue that a stale enumeration is deliberately not escapable and needs no escape, because re-running the check clears it, *always*. That is true per step and false over the loop: re-running clears staleness but surfaces questions; dispositioning a question frequently edits the plan; the edit moves the plan content digest; the digest change stales the enumeration again. Not a wedge — a **treadmill**, whose every lap is paid for in the user's attention, and whose step rule was correct precisely because it had no termination rule. So `gates.plan_enumerate_round_release_active` mirrors the review twin on the *same* `effort-replan-absolute` threshold and on the *existing* `enumerate_pass` counter (monotonic over the bag's life and deliberately not re-based on a digest change — a per-digest counter would reset on every plan edit and so could never fire across the treadmill's own lap boundary; no new config key, no copy of the review-round code). In `premise_blockers` only the staleness arm of the `if/elif` chain collapses: the undispositioned-question, order-coverage and runner-failure arms are peer branches and stand untouched. The discharge stays typed and countable — one new closed-set reason, `enumerate_rounds_exhausted`, added to `ENUMERATION_ESCAPE_REASONS` and NOT to `ENUMERATION_RUNNER_FAILURE_REASONS` (so it can never discharge a failed runner), refused outright while the release is inactive. Liveness holds on every branch: stale below the budget → re-run; stale at or above it → the new reason; runner-failed → the four F3b reasons; not landed → `enumeration_not_landed`.

## Presenting the round-release choice to the user

`plan_review_round_release_active` firing retires only the GATE's demand for another mandatory review pass — the blocker text's "no further thinker review is required" is not "no further thinker review is possible". An additional, purely advisory thinker-review pass remains spawnable before the coordinator records the now-mandatory `override`, at its own judgment, for extra scrutiny on a plan the budget no longer forces through review. The `AskUserQuestion` presented at this gate must therefore offer, at minimum, three options rather than a bare override-vs-show-full-plan binary:

- record `override` now (name the reviewer + note) — recommended when the plan is already well-scrutinized;
- spawn one more advisory thinker pass first, then record `override` regardless (the budget does not refill; this pass buys extra scrutiny, not another required gate) — recommended when open concerns remain;
- cut scope and resubmit (`replan` / `submit-plan`) — a fresh round is owed only if scope actually changed.

Narrowing to the first two repeats, at this specific gate, the general failure the materiality test names elsewhere in this leaf: presenting the courses the ENGINE happens to gate rather than the full set the coordinator's own analysis enumerated (`CLAUDE.md` § AskUserQuestion mandatory-use, "an ask's options must span the full set"). Confirmed 2026-08-26 by exhaustive git-history search (`log -S` on the candidate phrasings, plus a full-repo grep): no prior version of `CLAUDE.md`, this leaf, or any skill ever wrote the middle option down — its past appearances were unrecorded model recall, not an encoded rule, which is exactly why it could regress with nothing to catch the drop.

## Materiality (a raised question names the control its answer could flip)

A question the plan's own controls cannot turn on still had to be dispositioned, so the gate charged full price for questions that could not have changed the plan either way. `question-raise --control <name>` closes that half, split the standard way: the RULE half — does the named control EXIST in this plan — is decided by the engine using the resolver `check-order-coverage.py` already used (`agentctl/controls.py`, its grammar set a parameter with **no default**, so the coverage caller's three forms and materiality's five can never merge), and the PERCEPTION half — could the answer MOVE it — is a fail-open advisory judge that never blocks. Nothing regex-reads the question's text; the check is over a structured named-control field. Enforcement sits at the WRITE seam, never at the gate: every question persisted before the flag existed carries no control name, and a gate demanding one would convert each of them into a blocker. The same rule reaches enumeration — a candidate addressed to a stage the plan does not contain is recorded `dismissed` with one countable reason instead of being raised. Residual: the name is checked for EXISTENCE only, so a question can name a real control it does not actually bear on; the advisory judge and the thinker review reading `question-list --format md` (which now renders the `control` column) are the perception countermeasures.

**The materiality test — what keeps a lap from being entered at all.** The round budget above is the backstop for a loop already entered; the test is what stops it starting. *A finding justifies editing the plan only if it changes what gets built or what gets verified.* Everything else — a restatement of something a stage already orders, a point the plan's own method already assigns to its executor, a question a precedent the plan copies has already settled, a preference about wording — is **noted, not acted on**: it is dispositioned with its reason, so the judgement stays a counted line rather than a silent skip, and the plan bytes do not move. This is the *perception* half of the same split whose rule half is `plan_enumerate_round_release_active` — which findings deserve a plan edit is judgement the engine cannot decide, and no mechanism can compensate for entering a lap that should never have been entered. Its functional ground is the scarcest term in the objective function: a lap costs the user a round of attention, and a lap spent on a finding that moves neither the build nor the check spends that attention for nothing. The test binds the *reviewer* as much as the author — a review brief that does not carry it invites `revise` verdicts on findings the author will only note, and each such verdict is a lap.
