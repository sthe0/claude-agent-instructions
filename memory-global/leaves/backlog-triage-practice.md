# Backlog triage as a task type

## Difficulty

The backlog accumulates across two disjoint sources — Core (public GitHub Issues, `sthe0/claude-agent-instructions`, labels `difficulty`/`backlog`) and Org (an org-tier tracker's backlog + report queues — see [[instruction-dev-queues]] for the tier model; org-specific queue names/keys are internal detail and don't belong in this Core leaf) — with no standing way to (a) see both together, (b) rank them by anything other than recency/gut feel, or (c) re-derive that ranking each time the user actually has attention to spend on the backlog, since which item is "most worth doing" changes as items get closed, drift in, or accumulate cluster-mates. Without a repeatable procedure, every visit re-invents the triage from scratch — costly, and prone to silently inventing urgency for items that carry no real signal.

This leaf packages "разбор беклога" (backlog triage over a named scope) as one instance of the **general task-resolution process** already governed by `~/.claude-agent/CLAUDE.md` § Coordination spine, `scripts/agentctl/README.md`, and [[plan-activity-ontology]] — it does **not** restate that model. What it adds is specific to this one task type: the priority rubric and the collection procedure. Per explicit user correction: the engine itself never picks which task to work on — triage produces an ORDERED LIST, not an autonomous action; work on a specific item begins only via an explicit appeal naming that item.

## Guidance

### Scope

A backlog-triage task names its sources up front (today: Core GitHub Issues + the Org tier's backlog and report queues; a future run may add/drop a source — state it explicitly, don't assume the set is fixed). Run as a normal Substantive task through the coordination spine (multi-source external reads, likely > `substantive-wall-clock-min` — see `~/.claude-agent/config.md`), not a special-cased flow.

### Priority rubric

```
score(item) = breadth_weight(item) × recurrence_mass(item) / cost_to_resolve(item, in_flight_discount)
```

This is a direct generalization of engine mass-triggers that already exist for other events — `core-difficulty-mass-threshold` and `principle-promotion-threshold` (`~/.claude-agent/config.md`) both count "how many times has this recurred" for a different grading event; backlog priority reapplies the same recurrence-mass form to a fourth event.

- **breadth_weight**: `narrow`=1 / `shared-mechanism`=3 / `universal`=8 — the severity ladder (low/medium/high/critical = 1/2/4/8) applied to *how many future task-passes touch the functional place this item is about*, not to severity. `universal` = every substantive session traverses the mechanism (a core gate, dispatch, marker-parsing, verification path); `shared-mechanism` = a subset of sessions/paths; `narrow` = a one-off script/leaf/edge case.
- **recurrence_mass**: the item's own severity-mass (Core `severity:*` label, 1/2/4/8) **plus** the count of other independent items sharing the same functional ground (a cluster — same counting form as `core-difficulty-mass-threshold`). An item with neither a severity label nor a cluster gets `recurrence_mass = 1` and **must be explicitly marked "no urgency signal"** — never silently defaulted to a guessed weight.
- **cost_to_resolve**: a budget-tier estimate (`budget-small-usd`/`-medium-usd`/`-large-usd`) divided by an in-flight-readiness coefficient — 1.0 if no plan exists yet, ~0.5 if there's a clear what-to-do without a formal plan, ~0.3 if a plan/TOML is already approved and merely deferred. This must come from the item's own text (e.g. "план готов, исполнение отложено", "стадии N из M сделаны") — never assumed.
- **cost_of_problem**: the numerator's one *measured* term — what the difficulty costs us per occurrence or per week, in whatever unit fits (tokens, money, quota share, wall-clock, replans). Distinct from `cost_to_resolve`, which prices the fix, not the loss; `breadth_weight × recurrence_mass` only ever proxied it. Mechanized upstream: `scripts/file-difficulty.py` refuses a filing carrying neither `--cost TEXT` nor `--cost-not-estimable REASON`, so a filed record states the loss or states why it cannot be stated, and `core-difficulty-digest.py` shows it next to the mass. It is free text in incommensurable units, so it is **not** multiplied into the score — read it alongside, and let it override the proxies when the two disagree. A record whose cost is empty came in outside that gate (the digest marks it `N of M filed outside the cost gate`) and carries **no** cost signal — never read that blank as a cheap problem.
- **Hard partial order overrides score.** An item's text naming an explicit, unambiguous dependency on another item creates a hard ordering edge — the dependent item cannot rank above its blocker regardless of score. Indirect/partial mentions stay soft signal (feed into cost/mass within a cluster) and are never promoted to a hard edge. This is the anti-guessing invariant for dependencies, mirroring the anti-guessing invariant for urgency above.
- **No deadline axis.** The rubric has no urgency-by-date term because no source item has carried an explicit deadline so far (the one exception, a user-deferred item, is handled via in-flight discount, not urgency). If a future item names an explicit deadline/external commitment, don't fold it into existing axes by guesswork — escalate to add a deadline axis.

### Procedure

1. **Collect** open items per source into raw tables (title/labels-or-status/updated date) — one file per source, so later runs can diff against the prior collection instead of re-deriving from nothing.
2. **Classify** each item: breadth (from labels + title, cross-cutting-mechanism keywords), recurrence_mass (severity label + cluster membership by shared functional ground), cost_to_resolve (scope keywords + in-flight readiness from the item's own text).
3. **Score and rank**, then apply the hard partial order from step 3's explicit-dependency scan on top.
4. **Mark** every zero-signal item explicitly in its own section — never let it silently inherit a middling score that reads as a real judgment.
5. **Reconcile against the latest board, don't re-derive from nothing.** Before collecting, fetch the current Triage Board artifact (see § Reuse across runs) and diff it against live source: items it lists as open that are now closed/resolved drop out without re-scoring; items whose text and status are unchanged keep their prior score and rank unless a dependency elsewhere in the list moved; only genuinely new items and items whose own text changed get freshly classified. Re-deriving every item's score from scratch on every visit was the original (2026-08-19) design and is now understood to be wrong — it silently discards work whose result never depended on the visit date, and it obscures dependency-edge changes carried between runs. Publish the reconciled board by updating the SAME artifact (see below), not a new one.
6. **Never auto-select.** The output is the ordered list plus its reasoning. Starting work on any specific item is a separate, explicit appeal naming that item — this triage procedure itself never dispatches work.

### Reuse across runs

The scored board is a **living artifact, not a per-run snapshot.** Durability and discovery:

- **One artifact, updated in place.** The board is published via the `Artifact` tool under the stable title **"Triage Board"** at <https://claude.ai/code/artifact/976e53d6-30d9-4b50-83ae-cb32c6e9cc86> (republished 2026-08-24, after the original URL — `1497635a-d972-468b-96e0-4f75d45ace20`, first published 2026-08-19 — went **permanently unreachable**: HTTP 451 on both `WebFetch` and `Artifact action:"read"`, and the `Artifact` tool's own `force:true` overwrite path refused to publish over it, explicitly reporting the 451 as non-transient rather than a version-read race — do not spend a retry on that old URL again). A future run redeploys the SAME (current) `url` (`Artifact` action `publish` with `url:` set, per the tool's own update flow) rather than publishing a new page — keep the title and favicon stable across redeploys so the URL and the reader's bookmark stay valid. Never create a second "Triage Board"-titled artifact; if the URL above is lost, recover it with `Artifact action:"list"` (owned artifacts, newest first) before assuming none exists.
- **Fetch before collecting.** A new backlog-triage run starts with `WebFetch` on the current board URL (found via the pointer above, not re-derived), not a blank raw-collection pass — see procedure step 5.
- **The raw per-source collection files** (`raw-core-backlog.md`, `raw-org-backlog.md`, `priority-model.md` in the run's own scratchpad) are session-local working material, not durable — only the published board and this leaf persist across sessions. A future run regenerates them fresh each time; only the *board*, not the intermediate files, carries state forward.

### Identified engine gaps (candidates, not auto-filed)

Surfaced while executing this instance — presented to the user at the resolution gate for a decision on whether to file them:

1. **Scratchpad not exempt from the Edit/Write state gate.** System instructions direct using the session scratch directory instead of `/tmp`, but `hook-state-gate.py`/`exempt_paths.py` only exempts literal `/tmp/` and three memory directories — the scratchpad path itself is not recognized.
2. **No cross-source priority digest for "разбор беклога."** `core-difficulty-digest.py` only reads Core; the Org tier has no equivalent, so a cross-tier digest (this leaf's whole point) has no standing tool and was built ad hoc in-session (`score-backlog.py` in the session scratchpad — not committed, would need to move to a durable script location to be reusable).
3. **Delivery-proof staleness can recur after a correct re-presentation.** [[question-provenance-gate]] and [[ask-user-question-split-turn]] both document the single-cycle case (`order-dispose` forces a new `rendering_sha256` → re-present → clean stamp). This session hit a **second** "delivery proof is stale" block from `approve` on the SAME re-presentation cycle, after an apparently-correct re-present→timer→final-message→fresh-approval sequence — requiring `agentctl confirm-delivery --escape-reason transcript_unverifiable`. Neither leaf states whether a repeat block is expected (a stamp/receipt race across two turns) or a defect in the order-dispose → re-present → approve sequencing; unresolved, flagged for the user to decide whether to file it.
4. **`~/.claude-agent/memory-global/leaves/` is canon, not personal auto-memory, on this machine.** CLAUDE.md's memory-scope table describes `memory-global` as directly editable ("Global engineering ... Imported into every session"), but here it is a symlink into the canon `claude-agent-instructions` checkout, so a direct `Write` is denied by `hook-guard-canon-readonly.py` and requires `session-isolate.sh` + `land-on-main.sh` — the same production-edit path as Core code, not a lighter-weight memory-write path. `session-isolate.sh` also mis-detected the workspace backend as `arc` on first run here and required `CLAUDE_WORKSPACE_BACKEND=git` to succeed.
5. **Two related mechanical gaps, both hit while closing out stage 4.** (a) `advisor.acceptance_judge`'s nested `claude -p --model haiku` subprocess has a fixed 41s timeout (`advisor.py:93`, no env override) — a longer, more detailed `--observation` text pushes it past that ceiling, and the failure surfaces only as "stale verdict" at the `record-result` gate, never as a timeout message; distinguishing a genuine timeout from a stale binding required reading `judge-usage-ledger.jsonl` by hand (`timed_out: true, duration: ~41.0s`). (b) A plan stage's `verify_command`/`final_check` can silently contradict its own stated `means` when the means defers a push/landing action but the check still points at the post-landing (canon) location — diagnosed via a full `overcome-difficulty` cycle this session (stage 4's `verify_command` checked canon while the leaf commit lived only in an isolated worktree by design); `check-coverage`/`replan` catch a plan whose *invariants text* was not updated to match, but nothing catches the *original* authoring mistake before a stage actually fails. Neither gap has a structural fix yet — both are candidates, not auto-filed.
6. **A `spawn:developer` stage cannot self-serve canon-checkout isolation, and the workflow-level permission grant that PERMISSION-REQUEST routes to cannot fix that.** `DEVELOPER_SETTINGS_ALLOW` (`spawn-specialist.py:505-527`) grants git status/diff/log/show/add/commit/fetch/merge/checkout/restore plus read-only inspection tools, but has no entry for `session-isolate.sh` or any worktree-creation command — so a stage whose means assumes the developer will isolate its own worktree (the `[relocate]` hook's mandated remediation for writing into a canon checkout) deadlocks: every filesystem call the developer tries comes back "requires approval" with no interactive prompt reachable in the headless `-p` spawn. Worse, the marker's own designed escape doesn't help: `agentctl resolve-permission --decision granted` routes through `permissions-cli.py`, whose sole consumer is `digest` — a prose note embedded in the *next* spawn's dossier — never read when `spawn-specialist.py` assembles the child's actual `--settings` `permissions.allow` payload. A "granted" resolution would tell the re-spawned developer in prose that it may proceed while the real runtime enforcement layer still refuses the identical Bash call — the same `bypassPermissions`-inertness trap already documented in [[spawning-specialists]] (2026-08-04: six spawns, ~$4.2, ~40min lost to an elevation that looked applied but wasn't), recurring one layer up in a second, independent mechanism. Worked around this session by having the coordinator pre-create the isolated worktree (mirroring stage 4's own precedent) before dispatching the developer scoped entirely inside it — not a structural fix, a candidate for one: either grant a narrow, reviewed `session-isolate.sh` prefix in `DEVELOPER_SETTINGS_ALLOW`, or make `resolve-permission --decision granted` actually thread into the next dispatch's `--settings` payload instead of only its dossier text.

**Second instance, same session, same stage.** After the worktree-isolation gap above was worked around, the same stage 5 developer hit the identical shape a second time: `DEVELOPER_SETTINGS_ALLOW` pre-grants only three literal verify-script names (`verify-all.py`, `verify-agentctl.py`, `gen_crutch_registry.py`) plus `python3 -m pytest`, so the stage's own newly-authored deliverable (`verify-process-doc-sync.py`) could not be executed to produce the required live-run proof — the allowlist structurally cannot anticipate a script that doesn't exist yet at spawn time. Fixed locally this time by landing one more literal entry (`origin/main` commit `2f043590c4e56045ec4cb429fc3dfedf15521240`). The engine's own effort-divergence trigger then fired on this plan (3 replans since approval) and routed to a full declare/investigate/critique/normalize cycle; the investigation explicitly tested and falsified the "these are two unrelated one-off gaps" hypothesis (the file's own governing comment already named this failure class before either of this session's two hits), confirming the mechanism-level cause: **the grant mechanism itself is the recurring inadequate norm**, not any one script name. Two per-name patches in one session is enough occurrences to warrant generalizing the grant shape (e.g. a `Bash(python3 scripts/verify-*.py:*)` family pattern, plus a standing worktree-bootstrap grant) rather than continuing to add literal names reactively — recommended as the next concrete step, not yet done.

**Coda: the script this entry was patching for never landed.** Acceptance review went on to reject stage 5's deliverable (`verify-process-doc-sync.py`) in full — first its gate/plugin direction, then, on the same ground once the shared defect was demonstrated, its node-diagram direction: both extract an enumeration from prose by regex, and the surviving one false-positives on any all-caps annotation added inside the diagram block. The literal allowlist entry was therefore removed again (branch `drop-verify-process-doc-sync`), leaving the grant mechanism exactly where this entry found it. That does not weaken the lesson — it sharpens it: a literal name was added under deadline pressure for a deliverable that then proved unsound, so the reactive per-name patch bought nothing and had to be reverted. The generalized grant shape is still the open recommendation. Worth carrying forward separately: the sound replacement for a doc/code sync check of this kind is to **generate** the documented artifact from the code (here, the state-machine diagram from `agentctl.state.Node`) rather than to verify a hand-written one — generation leaves nothing to drift and needs no prose extraction at all, whereas any checker of hand-written prose inherits the regex fragility that sank this deliverable.

7. **A post-hoc `agentctl accept` fail verdict, recorded after every plan stage already PASSED, has no legitimate path back into DIAGNOSING.** Hit at this plan's own resolution gate: node=VERIFYING, every stage PASSED, `accept --verdict R5|fail|...` recorded a genuine customer rejection of stage 5's deliverable's design. `verify-final` then correctly blocks resolution (`"AcceptanceReview carries a non-pass verdict..."`) but performs no node transition — unlike the two other failure paths wired into the SAME function (a failing `final_check`, `cli.py:4210`, and `record_result`'s failed branch, `cli.py:4079`), which both call `transition(state.node, "diagnose")`. Every other route into DIAGNOSING is unreachable from here: `declare` refuses outside DIAGNOSING (`cli.py` difficulty-command guard); `reject` requires `node == RESOLUTION` (`cli.py:4398`), and RESOLUTION is entered only via the `"final"` transition on a *successful* `verify-final` — circular, since a successful verify-final is exactly what a fail verdict prevents; `record-result`/`dispatch`/`next-stage` all resolve their target through `state.active_stage()` (`current_stage`), and `current_stage` is set only by `next_stage` picking from `ready_stages()` (PENDING stages with satisfied deps, `state.py:1521-1533`) — a PASSED stage is neither active nor ready, so none of these three commands can re-target it. The only state-machine escape found (`reset --force`, `cli.py:803`) fully discards the session (a brand-new `SessionState`), not a scoped reopen. Net effect: `reject`'s own docstring frames it as covering exactly this need ("the user rejects the delivery as not matching intent") but its RESOLUTION-only precondition makes it reachable only *after* a delivery has already fully passed acceptance — never for the fail-verdict case it reads as designed for. Worked around this session (with the customer's explicit sign-off) by NOT forcing engine state: did declare/investigate/critique informally in dialogue (already substantively done via the acceptance-review exchange itself), dispatched the stage-5 fix as an ordinary `spawn-specialist.py` call outside `agentctl dispatch` (bypassing the stuck engine node entirely), got it code-reviewed normally, and will re-run `agentctl accept` with a fresh verdict once the customer confirms — the engine-tracked difficulty record for this specific divergence was never created. Candidate fix: either loosen `reject`'s precondition to also accept `node == VERIFYING` with a blocking non-pass AcceptanceReview present, or give the accept-verdict blocker in `cmd_verify_final` (`cli.py:4128-4131`) the same `transition(..., "diagnose")` treatment the final_check-failure branch already has.
8. **`spawn-specialist.py --continue-worktree` does not grant filesystem access to the named worktree — only `agentctl dispatch` does, silently, via a side channel the flag's own help text doesn't mention.** The flag's help string says it "instructs the specialist to build on that worktree/branch" (true — it edits the prompt text only, `spawn-specialist.py:191-197`). The actual access grant happens one layer up: `cmd_dispatch` (`cli.py:3661-3689`) resolves `cwd=state.resolve_check_venue(CheckVenue.DELIVERY.value)` and launches the child's `claude -p` subprocess with that `cwd` — a spawned session's default writable/readable scope is its own launch `cwd`, no `--add-dir` involved. A direct `spawn-specialist.py --continue-worktree <path>` call (i.e. any caller not going through `agentctl dispatch`) never sets this — the first attempt this session got `PERMISSION-REQUEST` (EnterWorktree/`git -C`/`Read` on the worktree all refused) despite `--continue-worktree` being set correctly; the fix was mundane (`cd <worktree> && python3 .../spawn-specialist.py ...`, i.e. supplying the missing `cwd` manually by running the launcher itself from inside the worktree) but nothing in `--help` or the flag's own docstring says this is required. Candidate fix: either make `--continue-worktree` set the child's launch `cwd` itself (matching what `agentctl dispatch` already does), or add one sentence to the flag's help text naming the manual-cwd requirement for non-`agentctl dispatch` callers.
9. **The acceptance ledger has no verdict for a requirement the customer WITHDRAWS.** Downstream of gap #7 and hit on this same plan one round later. `accept --verdict` takes only `<id>|pass|fail`. After two acceptance rounds the customer withdrew R5 outright — not because the agent failed to build the mechanism, but because the work itself demonstrated the requirement rested on a flawed premise: both of the script's directions extracted their enumeration from prose by regex, and the surviving one was shown to false-positive on an `NB:`/`TODO:` annotation injected into the very diagram it scans. Neither verdict fits. `fail` asserts the agent failed to deliver a thing the customer no longer wants, and blocks resolution; `pass` asserts it was delivered. R5 was therefore recorded as `pass` carrying a note whose first words state that the requirement was NOT fulfilled and was withdrawn — a verdict contradicting its own annotation, which is what an absent vocabulary term looks like in a ledger. Candidate fix: a third verdict value (`withdrawn`) that neither blocks `verify-final` nor counts as delivery, requiring a mandatory note and the withdrawing party. Recorded as a second context on [[2026-08-17-diagnosing-has-no-exit-to-the-customer]], whose functional ground — the engine can re-author a plan but cannot renegotiate the ORDER with its customer — this shares.
