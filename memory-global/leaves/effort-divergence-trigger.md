# The effort-divergence trigger

The one-clause rule lives in CLAUDE.md § When the work is stuck; the engine-side mechanics are in `scripts/agentctl/README.md` § Effort divergence. This leaf carries what a coordinator needs when the trigger fires at them.

## Difficulty

A task can run many times over its own plan and **nothing in the system notices**. The only detector is the user's attention — the resource the whole coordination machinery exists to spend less of. So the failure is self-concealing in exactly the wrong direction: the more the work overruns, the more supervision it silently demands, and the overrun that most needs a re-plan is the one nobody is counting.

A plan is a **norm**. Running far past it is not merely expensive; it is evidence that the norm is missing something essential about the real situation. That is a [[function-place-difficulty]] — a symptom whose cause is a broken functional place, not a number to push back into range by working harder.

## Guidance

**Four scales, one question.** `spend` and `wall_clock` are ratios: accumulated actual over the estimate the current plan derives from its own stages (plus the reviews the engine itself mandates — one thinker review per plan version, one code review per `spawn:developer` stage). `replans` is an absolute count, because a plan's *intended* replan count is structurally zero. `interactions` ships accounting-only: a plan's intended interaction count is not derivable at all, since driving the same plan more autonomously changes it wildly, so any threshold now would be a guess dressed as a derivation. Values live in `config.md`, each row carrying its own basis; never quote them from memory.

**The window opens at plan approval, not at session start.** Every actual is compared as `actual − baseline`, where the baseline is snapshotted once, at `approve`. That is the only window the estimate describes, since every stage it prices executes after approval. Two consequences worth holding: a session that never passes `approve` — every small change — is inert by construction, not by a weight-class test; and **an overrun spent while planning is invisible to the mechanism**. This feature's own planning phase ran three full review rounds and would not have fired on itself.

**Re-derivation at every replan is the point, not an implementation detail.** The comparison is always against the plan being executed *now*. A plan that contracts under a difficulty lowers its estimate while the actual stands — which is precisely the case where the trigger should be sharpest, and would be blunted by comparing against the original plan forever.

**The terminal is diagnose, never a question.** At the fire site the engine transitions to `DIAGNOSING`, seeds the difficulty and hands you a pre-framed declaration carrying the numbers. It asks nothing, because a confirmation there would reinstate the very supervision the trigger removes. Honestly: the *downstream* consequence can still reach the user, since a substantive replan out of that cycle meets the ordinary approval gate like any other. What is removed is the need for the user to **notice**; their authority over a changed plan is untouched.

**When it fires at you.** Do not treat it as an engine fault and do not work around it. Run the ordinary `declare → investigate → critique → replan`, and let the declaration's numbers be the evidence — the question to answer is *what about the real situation did this plan not know*, not *how do I get back under the number*. Re-arming is deliberate: the baseline rebases onto the actual at each firing, and a further fire additionally requires a `replan` since the last one, so the trigger is silent until a new norm exists to violate.

**The honest weakness: the estimate is declared by the same actor it constrains.** Nothing structural prevents a comfortable estimate. The only mitigation is that estimate and actual both land on the quality-ledger row, so both the thresholds and the estimating habit can be recalibrated against what they actually caught — see [[policy-effectiveness-tracking]] for the Flags-fire → self-improvement → record-movement procedure that is supposed to consume them. Secondary blind spots: the spend scale reads only what the cost ledger attributes to this plan's path, so a task whose overrun is entirely in the main thread under-reads there and is covered only by wall-clock; and the hook-stamped accumulators are best-effort. A third blind spot is structural rather than best-effort: a review round is **not one of its four scales**, so a cycle whose cost concentrates in review passes rather than replans runs unmeasured — measured while this mechanism was being extended, fifteen thinker verdicts across five replans with the trigger never firing on review cost — and the quality-ledger row the closing sequence writes carries the same four ratios and no fifth, so those rounds leave nothing to recalibrate against either. What partially covers the gap is a separate mechanism, the round-release valve on `plan_review_rounds`, which routes a review loop to the user at `effort-replan-absolute` rounds; the counter it reads was long advanced only on the pre-approval path, leaving the valve unreachable from `replan` — exactly where post-approval review cycles recur — until the counter was extended to advance there too. And on the scales that are counted, `record_fire` rebases the baseline onto the current actuals, so one firing consumes that scale's window: the next fire needs a fresh overrun measured from the new baseline, not the continuation of the old one.

**Two further gaps, both now mechanized.** The first: the trigger only ever compared **inside a command the coordinator chose to run** — the fire sites `record-result` / `verify-final`, and the `gates.effort_fire_blockers` refusal on `dispatch` / `submit-plan` / `replan`. A session that ran long without reaching any of them (one stage worked for hours, a specialist that never returned, a next command that kept being deferred) diverged unobserved however far past the multiple it went; "needs no human to notice it" held only once something called the engine. That is now turn-driven: `agentctl effort-check --session <id>` reports every scale's actual, comparand and ratio and **writes nothing** — no transition, no seeded difficulty, no `effort_fires` row, no state save — and `hook-effort-divergence-watch.py` (UserPromptSubmit) drives it on every prompt, printing one advisory line, throttled per session per scale, when a scale is at or past its threshold. Read-only is the load-bearing property, not a nicety: a read command with a side effect would be a second, hidden fire site, consuming the one-fire-per-replan budget with nobody having diagnosed anything. **The closure is scoped:** it covers the engine being *present but uncalled*. A session that never started the engine at all has no declared norm to be measured against, and no hook can invent one — that residual stays open.

The second: **re-entering a task that already RESOLVED was free and uncounted.** RESOLVED has no outgoing edge but `pop_subplan`, so `reset` is the only way back into a closed order — and the fresh `SessionState` it builds zeroes the effort baseline, the replan count and every round-release counter on the way in. An unbounded reopen loop therefore paid nothing: each lap discarded the very budgets that would have bounded it, and nobody was ever asked whether the order still stood. `gates.resolved_reentry_blockers` now refuses a same-task reopen without a recorded `--reopen-reason`, and at `effort-replan-absolute` reopens it demands `--reopen-user-decision` **alongside** the reason — the round-release shape, releasing into an explicit user decision rather than another lap; the decision answers who authorized another lap, the reason still answers what the last one missed. The count lives in the cross-session task accumulator (`resolved_reentry` axis), never on `SessionState`: a counter kept on the state `reset` replaces would be zeroed by the act it exists to count. Its own honest weakness is the key: re-entry is recognized by `task_id` **equality**, so the same order reopened under a reworded task slug arrives at zero prior reopens and passes both the reason and the ceiling untouched — friction on the honest path, not a lock, since the key is supplied by the actor being counted.

**A third gap, not yet mechanized: the `replans` baseline does not snapshot the accumulator at `approve`.** Line 24 promises every scale's window opens at approval — `actual − baseline`, baseline read once at `approve`. Observed on a real task (session `3b0247b5-…`) whose plan needed a long chain of pre-approval revisions before it could be approved: the plan's own header comments recorded that lineage explicitly, and the cross-session task accumulator's `replans` axis had reached **15** by the time the plan was finally approved. Yet `effort_baseline.replans` in the approved session's state was **0.0**, not ~15 — so the very first post-approval `record-result` compared the *lifetime* count directly against the absolute threshold (`multiple: 5.0`, `actual: 15.0`, `estimate: 3.0`) and fired on a session whose own `history` showed **zero** replan events since `approve`. For `spend`/`wall_clock`, a zero baseline is the ordinary case (nothing spent yet); for `replans`, a zero baseline is only correct for a plan with **no** pre-approval revision lineage — any plan that needed real iteration to reach an approvable state inherits its whole history as a false first-fire the moment it dispatches its first stage. Whether baseline is genuinely never captured for this one scale, or captured but read from the wrong source, was not traced into the engine code — that is out of this leaf's scope; the task that surfaced it only needed the pattern recorded, not fixed. **Guidance until fixed:** a `replans`-scale first firing on a task whose approved plan's own text documents multiple pre-approval revisions (grep the plan for "REPLAN"/revision-marker style comments, or check `effort_baseline.replans` against the accumulator directly) is very likely this gap, not genuine in-session thrashing — verify via the session's own `history` array (zero replan events since `approve` is the tell) before trusting the fire as a real divergence signal, same diagnostic move as any other firing, just with a documented prior on which hypothesis to check first.

**A fourth gap: `fire-acknowledge` and the DIAGNOSING-exit precondition are two separate gates, and only one of them mentions the other.** Observed 2026-09-03 (`published-text-writer-gate` plan, replans-scale, actual=8 vs estimate=3): a `replans`-scale fire raised while the session was already inside a DIAGNOSING episode (entered because the *previous* `verify-final` call had failed) was cleared with `fire-acknowledge --decision continue`, and the CLI returned `ok: true, detail: "fire acknowledged (decision=continue); resuming"` — reading exactly like a full unblock. The very next `verify-final` call still refused outright (`ok: false`, zero verification commands run) with `"a prior final-verification refusal/failure already routed this session into the difficulty cycle; complete overcome-difficulty (declare -> investigate -> critique -> replan — replan re-arms verification) before re-running verify-final"`. The two gates check different things: `fire-acknowledge` only clears *that specific fire's* block on `declare`/`replan`; a session's DIAGNOSING node, once entered by *any* cause (a failed `verify-final`, not only an effort-divergence fire), stays entered until an actual `replan` call closes a *complete* difficulty record — and entering DIAGNOSING a second time (here, via the fire itself) resets `state.difficulty` to all-null, discarding whatever record a prior cycle had already built. **Guidance:** after any `fire-acknowledge`, re-run `agentctl status` before assuming the session is unblocked — `node` staying `DIAGNOSING` means a full `declare → investigate → critique → replan` is still required regardless of the ack, and skip straight to a no-content-change replan (empty `--difference-to-remove`) when the underlying deliverable is already verified — do not re-derive the same finding a second time.

**A fifth gap, the terminal one for the `replans` absolute scale: exiting DIAGNOSING structurally requires a `replan` call, and `replan` itself increments the same `replans` counter the absolute-scale trigger compares — with no baseline subtraction for this scale (see the third gap above). Once that counter first crosses `effort-replan-absolute`, no sequence of `declare → investigate → critique → replan` can ever clear `verify-final` again**: every exit attempt makes the counter strictly worse, so the very next `verify-final` re-fires the same trigger, without limit. Confirmed empirically 2026-09-03 on the same session: the counter went 8 → 9 across two consecutive exit attempts, each attempt immediately re-triggering. This is not a resubmission-quality problem (contrast the acceptance-judge goalpost-moving deadlock in [[agentctl-acceptance-judge-gate]], where a better observation can in principle converge) — it is a mathematical guarantee, since the escape mechanism and the trigger condition share one non-resettable counter. The `AGENTCTL_EFFORT=0` kill switch (`agentctl/gates.py::effort_active`) is the documented escape, but it must be set on the exit-`replan` call itself, not merely the failing `verify-final` — DIAGNOSING is persisted state, not a live flag, so setting the var only on `verify-final` after DIAGNOSING is already entered does nothing. In practice the bypass command was also blocked by the Claude Code auto-mode classifier when invoked via the agent's own Bash tool (`"Permission for this action was denied by the Claude Code auto mode classifier. Reason: Blocked by classifier."`, the same pattern already documented for the sibling `AGENTCTL_STAGE_REVIEW` bypass in [[agentctl-acceptance-judge-gate]]) — the user had to reset the underlying cross-session `replans` accumulator directly rather than run the kill-switched command themselves. **Guidance:** treat a `replans`-scale absolute fire recurring immediately after an exit `replan` (i.e. the reported `actual` strictly increasing across consecutive fires with no intervening successful `verify-final`) as this deadlock, not as "the difficulty record was incomplete" — do not keep re-running `declare → investigate → critique → replan` expecting convergence. Surface the mathematical proof to the user (the counter only grows) and get explicit authorization for either the `AGENTCTL_EFFORT=0` kill switch (run by the user directly if the classifier blocks the agent) or a direct reset of the accumulator. **This is a Core mechanism defect, not merely a documentation gap** — unlike the third and fourth gaps above, no sequence of caller-side actions closes it; it needs an engine-side fix (e.g. the exit-`replan` that closes a DIAGNOSING episode should not itself count toward the same absolute threshold that routed the session into DIAGNOSING, or the absolute scale needs the same baseline-rebasing-at-`record_fire` treatment the other three scales already get).
