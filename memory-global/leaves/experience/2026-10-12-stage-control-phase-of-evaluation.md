# A stage control describes the state of one phase but is evaluated in another

## Difficulty
Each stage control is authored as a snapshot of one phase: a probe that is correct before the action, a working-tree diff that is correct before the commit, an exact equality that is correct before a later stage broadens it. The engine evaluates it again at record-result and at verify-final, in a phase where the observable is empty, superseded or stale. The control cannot go green for the right reason there, and nothing in the plan states which phase it was written for.

**Functional ground:** A control observes a state that is true only in one phase of the plan's own lifecycle (before the action, before the commit, before a later stage), yet the engine re-runs it in a different phase, so it is unsatisfiable or false-red by construction.

### 2026-10-07 — ccgram-relay-permanent-fix: two new vectors — STALE-LITERAL and LIVE-STATE
- Where it arose: plan ccgram-relay-permanent-fix, v57 -> v58: stage 6 verify_command and the plan-level final_check; artifacts /home/the0/bin/ccgram-relay-health-test.sh and ccgram-relay-health.py

- **Vector A — STALE-LITERAL.** Stage 6's `verify_command` invoked its own acceptance suite with the case count `11` written as a literal, and that suite compares the argument against its own `REQUIRED_CASES` declaration on EXACT equality. Stage 9 then legitimately grew the suite 11 → 16 and updated its own call site. Stage 6's literal became unsatisfiable at that instant, and nothing re-runs a PASSED stage until verify-final — so the defect sat invisible for the rest of the plan and surfaced only at the closing gate. Fix: read the count from the artifact's own declaration (`grep -m1 '^REQUIRED_CASES='`), assert only the stage's OWN minimum (`-ge 11`), and pass the read value through. Generalised rule: **a criterion that pins a literal count against an artifact's self-declared count is staled by that artifact's next authorized growth — cite the declaration, never repeat the number.** A plan-wide sweep proved this was the only stale literal of its kind here.
- **Vector B — LIVE-STATE in the closing gate.** The plan-level `final_check` ended in a bare six-minute live relay probe demanding `verdict=ok`. That conjunct is a statement about the machine at the moment of closing, not about the delivered work: at 11:54 it reported a stuck session and 2 054 442 bytes of lag; by the end of the same window the identical command returned `verdict=ok` with 15 574 — the relay had healed itself unaided, i.e. the order's self-repair requirement was working *precisely when the closing gate declared failure*. Fix: narrow the band to certify the **instrument** (short window, parseable result line) and leave the health EVIDENCE where it was observed — in the recorded soak log the first band already greps. Generalised rules: **a closing gate may contain only statements ABOUT THE DELIVERED ARTIFACTS**, and **when narrowing a criterion, certify the instrument and leave the evidence where it was observed.**
- Collateral costs worth the next session's time. A plan-text-only criterion fix is still **substantive** to the engine: it reset the corrected stage to PENDING and demanded full user re-approval, because `approve --by agent` refuses while a changed engine-executed command has no first passing thinker review. The AcceptanceReview binds to `plan_sha256`, so the same text-only correction silently voided a user-authored acceptance (`verify-final` treats it as ABSENT) and it had to be re-asked and re-recorded verbatim against the new digest — the seventh proven instance of review-binds-to-plan-version.
