# Spawn budget burned on permission denials when declared stage material lies outside the spawn sandbox

## Difficulty
Desired: a dispatched spawn spends its budget on the stage's work product. Actual: the stage's material list included a file outside the spawn's sandbox, so the spawn spent a large share of its budget probing denied actions (13 denials, multiple phrasings of the same read) and died on budget before completing its report.

## Order & criterion
Execute plan ghost-scope-fix stage 2 via a dispatched developer spawn sandboxed to scripts/

**Acceptance check:** Spawn returns a line-initial marker within budget; no budget spent probing actions the plan already knows are denied

## Contexts

### 2026-07-02 — initial
- Where it arose: ~/claude-agent-instructions; agentctl dispatch -> spawn-specialist.py (budget medium $3, sonnet); plan ~/.claude/plans/ghost-scope-fix.toml stage 2; spawn session 209d493f
- Working plan: Recovery applied: manager salvaged the delivered working-tree code (full diff review), wrote the out-of-sandbox doc section per the plan's manager-fallback condition, ran all verification (147 scope/spawn, full 1149), recorded the stage passed with an honest control note. Prevention: at plan-authoring/dispatch time, diff each stage's material list against the spawn sandbox root; move out-of-sandbox items into an explicit manager step in the stage method and state them as off-limits in the spawn prompt.


### 2026-08-11 — 2026-08-10 - spawn workspace is the LAUNCH CWD, and the plans dir is the read-only channel
- Where it arose: ~/claude-agent-instructions (canonical checkout) coordinating a merge-reconciliation sub-plan whose delivery venue was the worktree /Users/the0/claude-agent-instructions-smd-act; two spawns launched via scripts/spawn-specialist.py (code-reviewer $0.77 / 71 s, developer $0.84 / 77 s), each returning PERMISSION-REQUEST: without doing any of its work
- Working plan: Root cause, read out of spawn-specialist.py rather than guessed: the script passes NO cwd= to Popen, so the child inherits the LAUNCHING shell's cwd - and that cwd IS its workspace. The only additional grant is --add-dir <plans_directory> plus Read(//<plans>/**) and Bash(shasum -a 256:*) with an Edit() DENY, for PLANS_READ_KINDS = (thinker, code-reviewer, developer). --continue-worktree only injects prompt TEXT; it grants nothing. Neither spawn had git in its Bash allowlist. Hence the two positive routes, both using the mechanism as designed and neither touching the permission surface: (a) to give a spawn the delivery worktree, LAUNCH IT FROM the worktree (cd <worktree> && python3 <canon>/scripts/spawn-specialist.py ...); (b) to give a READ-ONLY spawn artifacts it must judge, stage them as files under ~/.claude-agent/plans/<slug>/ - the read channel the spawner already grants - and say in the brief that the boundary is established so it does not re-probe. Route (b) also removes the git dependency: stage git show / git log / git status output as .diff and .txt files. The reviewer's independence cost of route (b) must be STATED in the brief, not hidden: the artifacts are generated by the party being reviewed, so the reviewer can only cross-check them for internal consistency, and it should report that limit rather than imply it re-derived them.

## Common core & variations
**Common:** Same functional ground as the 2026-07-02 instance: a spawn discovers its own boundary by burning budget, because the launcher knew the material and the boundary but never compared them. Partitioning the material list against the sandbox is still the fix.

**Variations:** New here: the boundary is not a fixed sandbox root to partition material AGAINST - it is a PARAMETER the launcher sets, and sets implicitly, by where it stands when it launches. So the 2026-07-02 rule (move out-of-sandbox material to a manager step) is the fallback, not the first move: first CHOOSE the launch cwd so the material is inside, and only then partition what is still out. Also new: the developer failure was a conformance divergence of mine, not a rights shortage - an earlier successful spawn in the same task HAD been launched from the worktree, so the working precedent existed and I diverged from it. A permission-layer denial remains a stop-and-ask, and widening a settings*.json permissions.allow to clear it is outside every plan's scope; both of these were cleared without touching it.
