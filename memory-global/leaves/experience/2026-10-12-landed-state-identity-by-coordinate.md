# A landed-ness or identity check binds to a coordinate that a moving trunk or a squash merge invalidates

## Difficulty
Landed-ness and artifact identity are checked through a coordinate: the delivered head sha, a range off a base, a `path:line` pin, a task trailer. Trunk advances, a squash merge orphans the frozen head, or an unrelated edit shifts a line, and the check goes red while the delivered content is byte-identical on trunk. The same movement can also hide a genuine edit behind an unchanged coordinate, so the fragility cuts both ways.

**Functional ground:** A check establishes that a delivery landed, or that an artifact is the one it names, by a positional coordinate (a sha, a range, a line number, a trailer) instead of by content or ancestry, so any unrelated movement of the shared history falsifies it.

### 2026-08-04 — Instance 23 — POSITIONAL BOOKKEEPING: a `path:line` pin false-fails on a pure line SHIFT (and silently covers a genuine EDIT) — closed structurally with content anchors
- Where it arose: landing branch `hook-prune-two-file` (parked ~5 days) into `main` — `verify-all` went red at `verify-config-root-refs.py` even though `git range-diff main...branch` reported BOTH of the branch's commits as `=`. Fix task: plan `~/.claude-agent/plans/fix-positional-bookkeeping.toml`, worktree `/Users/the0/claude-agent-instructions-anchor`, branch `anchor-config-root-pins`, 5 stages.
- **The finding — a new axis for this family: the check is correct, the venue is correct, the interface is correct, and it still false-fails because the ADDRESS it uses is positional.** `scripts/config-root-refs-allowlist.txt` pinned each vetted legacy-config-root reference as `path:line`. Nothing about the branch changed those references; what changed was that `main` advanced and the rebase shifted line numbers inside the *referenced* files. Every prior instance in this leaf is about a check whose SCOPE/VENUE/INTERFACE was mis-authored; this one's check is authored perfectly and its data model is wrong. **The tell is diagnostic gold and easy to misread:** `range-diff` says `=` for every commit, so the instinct is "my branch is fine, the tree is broken" — both halves are true, and the breakage lives in a bookkeeping artifact that addresses a *shared, moving* file by position. Positional identity across a moving trunk is the same disease as instance 20's SHA-equality and merge-base-pinned range sweeps, one layer down: express identity by CONTENT, never by coordinate.
- **The two-way misfire (why "just re-pin the numbers" is not the fix).** A shifted pin fails in BOTH directions, and only one direction is loud. (i) Loud: line N now holds unrelated text → reported stale → a red on a genuinely-green tree. (ii) **Silent, and the one that matters:** after a shift, line N may coincidentally still hold *some* vetted-looking occurrence, so the entry keeps "covering" it while the reference the human actually vetted has moved elsewhere — an allowlist that has quietly stopped allowlisting what it was reviewed for. A hand re-numbering pass fixes (i) and *entrenches* (ii).
- **The fix — content anchors (`path:line:<sha8>`).** `sha8` = first 8 hex of `sha256` over the referenced line's STRIPPED text; anchors are resolved against occurrence lines only, yielding four explicit outcomes: `pinned` (anchor matches at the pinned line), `relocated` (matches exactly one other line — the pin follows its reference and the run prints `docs/x.md:48 -> :49`), `ambiguous` (matches several — resolves to nothing, so it can neither cover nor be reported stale), `unresolved` (matches none — genuinely stale: the reference's TEXT changed and must be re-vetted). Duplicate coverage (two entries resolving onto one occurrence) is its own failure. `--repin` migrated all 85 line pins in place; the accepted limit is stated in the file's own header — two byte-identical occurrence lines in one file cannot be pinned apart, which is what the whole-file form exists for.
- **The rule that makes the fix honest, and nearly got written the other way: `--repin` must REFUSE to re-anchor a STALE entry.** A migrator that "helpfully" re-anchors an entry whose text changed launders an unreviewed reference into a vetted allowlist — precisely the silent hole (ii) above, now automated. `--repin` rewrites only entries it does not have to guess about, and skips stale/ambiguous/duplicate ones by design. This bit immediately: editing line 122 of `scripts/README.md` (to describe the new mechanism) staled that row's own pin, and the correct path was to re-read the reference, confirm the reason still held, compute the anchor independently with `shasum`, and hand-edit the one spec — the mechanism catching its own author is the strongest evidence it works.
- **REJECTED HYPOTHESIS, recorded because the next reader will form the same one: "the red is `crutch_registry.toml` drift."** The generated registry *was* also stale in the same red run, and it is the more familiar failure, so it reads as the root cause. It is not: registry staleness is conditions (a)/(b) of `verify-semantic-gates.py` — genuine, independent, and cured by re-running `gen_crutch_registry.py` — while the allowlist red is a distinct positional defect no regeneration touches. Two unrelated bookkeeping artifacts going stale in one landing is coincidence of *cause class* (both are position/snapshot-shaped bookkeeping over a moving tree), not a shared root. Remediation landed for the registry half too: its FAIL output now says which half is bookkeeping (regenerate, never hand-edit) and which is NOT — condition (c), a reverted judge guard, is a real regression that regenerating would merely RECORD.
- **Anti-vacuity: a test that reads back a generator-written artifact with the SAME function that wrote it proves nothing.** Asserting `anchor_of(line) == <what the tool wrote>` is circular — it holds for any hash function, including a broken one. The stage-1 suite pins the definition with an INDEPENDENTLY derived literal, `_SEE_ANCHOR = "d3b52e9e"`, with the shell that produced it in a comment above (`printf '%s' '<line>' | shasum -a 256`). Generalize: whenever a control's expected value comes from the code under test, one constant must come from OUTSIDE it. Five review rounds on this plan also surfaced three vacuous controls and a fail-open two-file `grep -q` — re-confirming instance 21's norm verbatim: **a control is not authored until it has been RUN once and observed to exit as declared, with RED demonstrated against a mutated WORLD, not a mutated CHECK.**
- **Two small landing gotchas worth the line.** (1) `git rev-list --left-right --count main...branch` — the LEFT number is `main`; misreading it inverts ahead/behind at exactly the moment you are deciding whether a rebase is needed. (2) Do not hand-fix a GENERATED artifact that a check reports stale (here `crutch_registry.toml`) — re-run its generator; hand-editing produces a file that passes the check and no longer describes the tree.
- **Unexplained mechanism defect observed in passing (not diagnosed):** at `approve`, `cmd_approve` refused with "no delivery proof recorded" although a direct call to `hook-plan-delivery-gate.py`'s `gate_decision()` on the real observables returned `('allow', '', True)` — allowed AND `delivery_verified`, whose only stamping path is `_delivery.write_stamp`, yet no sidecar stamp existed. Closed honestly via `confirm-delivery --session --by user` after the user confirmed on the record that the essence had reached them (an escape that trades a machine proof for a human's word — say so out loud when using it). Root cause not established; noted here so a recurrence is recognized rather than re-diagnosed. Cross-ref: [ask-user-question-split-turn.md](../ask-user-question-split-turn.md).
- **This leaf was the first victim, and the escape hatch it took is what hid the general defect.** Instance 18's `inline-config-root-keep-marker` task (2026-07-22, above) collapsed EIGHT `path:line` pins covering THIS file into one whole-file entry, explicitly "killing the line-pin churn every append to this append-only leaf caused" — a correct local fix that read as a property of append-only leaves rather than as the first sighting of a general positional defect, so the other 85 pins kept the coordinate addressing until this landing broke them. Lesson: when a bookkeeping mechanism forces you to disable it for one input, ask whether the input is special or the mechanism is — an escape hatch used once is a workaround, used to explain away a class it is a missed diagnosis.
- Cross-ref: instance 20 (MOVING-SHARED-TRUNK — SHA equality and merge-base-pinned ranges; this is the same "identity by coordinate breaks under a moving trunk" lesson at the bookkeeping-artifact layer), instance 21 (the run-it-once norm this re-confirmed and the fail-open `grep -q` shape review caught again), instance 18 / `inline-config-root-keep-marker` (the whole-file escape hatch this generalizes), and instance 22 immediately above — landed on trunk by a PARALLEL session while this branch sat unpushed, so this very entry hit the moving-trunk collision it describes: the rebase conflicted on this file, "instance 22" was taken, and the entry had to be renumbered to 23 by hand.
