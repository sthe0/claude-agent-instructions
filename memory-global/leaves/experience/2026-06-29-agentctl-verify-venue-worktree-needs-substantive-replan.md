# agentctl verifies a stage in repo_root, not the worktree it ran in; only a substantive replan can move the venue

## Difficulty
Executing a substantive agentctl plan in an isolated git worktree (chosen so a parallel session's dirty tree is not entangled) silently diverges the verification venue from the engine's bookkeeping. The engine stores meta.repo_root once at submit-plan and runs every stage's verify_command as 'cd <repo_root> && <cmd>' — i.e. against the MAIN checkout, which lacks the worktree's commits — so each genuinely-green stage is recorded FAILED and routed to DIAGNOSING. Worse, the obvious fix (edit the plan's verify_command/repo_root to the worktree and replan) does NOT take: diff_plans classifies a verify_command/repo_root-only change as a 'refinement', and the refinement branch of cmd_replan reassigns only title/result/means/method/conditions/invariants — never verify_command or repo_root. Those two fields are reloaded ONLY by a 'substantive' replan (state.stages=new.stages; state.repo_root=new.meta.repo_root), and the structural signature that triggers substantive excludes verify_command — so a structural field (e.g. a stage done_criterion) must be changed to force it.

## Order & criterion
Make the engine verify in the venue that holds the commits. Either (a) keep repo_root = main checkout and accept the double-cd (verify_command itself 'cd <worktree> && ...' wins over the engine's prepended 'cd <repo_root> &&'), OR — when stages were already loaded with main-checkout verify_commands — force a SUBSTANTIVE replan: bump a structural field (a stage's done_criterion) so diff_plans returns 'substantive', which reloads state.stages (worktree verify_commands) + state.repo_root=worktree, returning to PLAN_READY for re-approval. Criterion: state.json shows repo_root=worktree and every stage verify_command points at the worktree; record-result then runs the real check green in-venue.

**Acceptance check:** agentctl status + state.json: repo_root and all stage verify_commands resolve to the worktree; each stage record-result passes its real verify_command (no rubber-stamp); verify-final green.

### 2026-06-30 — same reload gap, NON-worktree, and the destructive-substantive-replan trap
- Where it arose: a project/global: 7-stage `junk/<user>/agents/` workspace-restructure plan (projects/ + common/ split). NOT a worktree this time — the verify_command divergence surfaced from a plain bug: stage 6's `verify_command` used `awk 'NR>140'` (counts lines across the *concatenation* of all files) where it meant `awk 'FNR>140'` (per-file line number). The engine auto-ran the stale NR command at record-result and false-FAILED the genuinely-green stage. Same class as the worktree case: **the field the engine actually executes (`verify_command`) cannot be corrected by a refinement replan**, because `_structural_signature` (plan.py) excludes verify_command, so a check-only fix always classifies as refinement, and the refinement branch of `cmd_replan` never copies verify_command into state.
- **KEY new tradeoff — a substantive replan RESETS already-PASSED stages.** The "force substantive" remedy from the initial context is *destructive* when earlier stages are already verified: the substantive branch does `state.stages = new.stages`, which re-initialises every stage outcome to pending — throwing away stages 1–5's PASSED records to fix a single field in stage 6. The cheaper, surgical remedy: **hand-patch the engine state store directly.** The state store (`~/.claude/agentctl/state/<session>.json`, a `FileStateStore`) is plain JSON and is NOT covered by the production gate (the gate guards settings/skills/agents/CLAUDE.md/instruction-repo/plans — not runtime state). Patch only `stages[k].criterion.verify_command` (NR→FNR), back the file up first, leave the 5 PASSED outcomes intact. Then a replan that targets the *node* (DIAGNOSING→VERIFYING) + re-arms the one stage suffices — no stage reset.
- **Registered-plan in-place-edit trap.** `cmd_replan` does `old = _load(state.plan_path)` and the refinement branch sets `state.plan_path = args.plan`. So after a refinement, `state.plan_path` *is* the file you last submitted — editing THAT file in place to build the next correction makes `old == new`, and the coverage gate's CHANGE check (the new stages' `(means, method)` multiset must differ from old) can then never pass. Remedy: submit each correction round as a **fresh, separately-named file** (plan-replan-v2.toml, -v3.toml, …), never by mutating the file at `state.plan_path`.
- **Flaky auto-dispatch on already-done work + no prior-dispatch guard.** `dispatch` for a `spawn:developer` stage auto-spawns a verifier synchronously; on work that is already complete this is non-deterministic (observed: one run COMPLETED at $0.36, an identical re-run MALFORMED→BLOCKED because the spawned developer misread the dispatch as "execute the whole plan"). `record-result` has **no** guard requiring a fresh dispatch — it needs node=EXECUTING + a non-None active stage + a non-empty `--control` attestation. Reliable path on already-done work: `unblock` (clear the BLOCKED) → `record-result --status passed --control "<genuine review attestation>"`, skipping dispatch entirely.
- Cross-ref: [[2026-06-24-developer-marker-not-on-line-1-false-block]] (the auto-spawned developer's MALFORMED marker is the same false-block failure mode).

### 2026-06-30 — THIRD instance (verify_command typo) + the surgical remedy was missed again

A verify_command-only correction is now a cheap, non-destructive refinement — PASSED stages are preserved. Remedies (a) (force-substantive) and (b) (hand-patch state.json) are no longer needed for this class of error.

### 2026-06-30 — FOURTH instance, DURING the fix: the engine fix removes the *correction cost*, not the *authoring antipattern*
- Where it arose: the `agentctl-verify-command-replan-fix` task itself (the engine change above). Stage 1's plan `verify_command` was again malformed at authoring — `python3 -m pytest scripts/tests/test_replan.py -q 2>&1 | grep -qiE 'verify|repo_root|carries'`: `pytest -q` prints only progress dots + an `N passed` summary, **never test-function names**, so the grep matched nothing and exited 1 → the engine false-FAILED a stage whose tests were 899-green. A 4th instance of the same false-FAIL class, committed *while shipping the fix for that very class*.
- **Two distinct difficulties, only one removed by the engine fix.** (1) *Correction cost* — once a verify_command is wrong, how expensive is the fix? The engine change removed this: the correction was a single verify_command-only **refinement** replan that carried the new command into live state with **no stage reset and no re-approval** (live-validated end-to-end here — `replan` returned `kind=refinement`, stage 1 went FAILED→PENDING, re-recorded green). Remedies (a)/(b) were not needed. (2) *Authoring antipattern* — writing a check whose observable does not contain what it greps for. The engine fix does **NOT** remove this; it remains operator cognition.
- **Residual discipline (the durable lesson):** author a `verify_command` against the **actual observable** the command emits, not an assumed one. Two concrete traps now seen: a tool's CLI signature (instance 3: `lint-prose-length.py FILE` when the script takes no positional), and a tool's *output format* (instance 4: greping test-function names out of `pytest -q`, which suppresses them). Before trusting a check, **run it once by hand and read its real output**; for "is test X present" prefer greping the **test file** (`grep -q 'def test_…' file`) or `pytest --collect-only -q`, never the green-run summary. The engine now makes the fix cheap, so the cost of this mistake is low — but a one-line manual dry-run of the check still avoids the whole difficulty cycle.

### 2026-06-30 — SIXTH instance: the SAME reload gap exists for `final_check`, and the 2026-06-30 engine fix did NOT cover it
- Where it arose: a project/global: the `retire-last-accessed-stamp` task (retire the last_accessed temporal-frontmatter mechanism). 5-stage plan, all stages already PASSED and both sub-PRs landed; the ONLY blocker to resolution was a defective plan-level `[[final_check]]` (FC4). FC4 shelled `python3 scripts/memory_dates.py x.md` to assert the validator rejects a re-introduced `last_accessed` — but `memory_dates.py` is an **importable module with no `__main__`/CLI**, so the invocation no-ops to exit 0, and FC4's `! …` flipped it to exit 1: the check could NEVER pass regardless of the (correct, landed) deliverable. `verify-final` re-runs every `[[final_check]]`, so it refused the RESOLUTION transition and stayed at VERIFYING.
- **The gap is `final_check`, NOT `verify_command` — and the landed 2026-06-30 fix is field-specific.** The earlier contexts' engine fix added per-stage `verify_command`/`expected_exit` to `diff_plans._prose` and made the `cmd_replan` refinement branch carry them into state. But **`final_check` was left out of BOTH**: `diff_plans` (plan.py) references `final_check` nowhere (neither `_structural_signature` nor `_prose`), so a final_check-only edit classifies as `no_change`; and the `cmd_replan` refinement branch (cli.py) updates per-stage `criterion.verify_command` but never `state.final_check` — only the **substantive** branch does (`state.final_check = new.meta.final_check`). So the cheap refinement path that now exists for stage verify_commands does NOT exist for final_checks: a buggy final_check is reloadable ONLY by a substantive replan (or remedy (b)).
- **I took the DESTRUCTIVE force-substantive path (a) again — the leaf's own remedy (b) was the right move and I missed it a fourth time.** I wrote a corrected plan to a fresh sibling file (FC4 → direct `validate_temporal` import-and-call; plus a meta.done_criterion bump to force `substantive`), ran a substantive replan → PLAN_READY → re-approved against standing approval (check-correctness fix, scope/deliverable byte-identical and already landed) → re-drove all 5 stages via next-stage+record-result (dispatch skipped to avoid re-spawns; one stage-1 dispatch fired a $0.46 verifier before I switched to direct record-result) → verify-final green. **Cheaper remedy (b), unchanged from the prior contexts:** hand-patch `~/.claude/agentctl/state/<session>.json` `final_check[k].command` directly (the state store is plain JSON, NOT covered by the production gate), back the file up first, then re-run `verify-final` — NO replan, NO stage reset, NO re-approval. For a final_check-only fix this is strictly better than force-substantive (which re-initialises all stage outcomes). Discipline fix reaffirmed: on ANY engine false-block rooted in a field the engine executes (`verify_command` OR `final_check`), read this leaf and prefer the state.json hand-patch (b).
- **Authoring antipattern (new vector — INTERFACE mismatch):** the check shelled an importable module as if it had a CLI. Like instances 3/4/5 (signature / output-format / scope-CWD), the durable fix is the same: author the check against the **actual interface** of what it calls — a module with no `__main__` must be exercised by `python3 -c "import m; …"`, not `python3 m.py ARGS` (which silently does nothing). A one-line manual dry-run of FC4 would have exposed it at authoring time.
- **Systemic signal (RESOLVED — engine fix landed):** the structurally-identical `final_check` gap was closed by a targeted Core change (committed 2026-06-30, `origin/main` `4761b49`, task `finalcheck-refinement-reload-gap`), mirroring the verify_command fix exactly: `diff_plans` now ORs a `final_check` signature (`[(fc.command, fc.expected_exit, fc.label) …]`) into the refinement trigger (NOT `_structural_signature` — final_check stays refinement-class), and the `cmd_replan` refinement branch now carries `state.final_check = new.meta.final_check`. Three regression tests mirror the verify_command trio. **So a final_check-only correction is now a cheap, non-destructive refinement too** — remedy (a) force-substantive (which I wrongly took here) and remedy (b) state.json hand-patch are no longer needed for either executed field. The fix rode the full protected-Core spine (planner-cognition in-thread → user approval → spawned developer → verify-final → land via isolated worktree off origin/main).

## Common core & variations
**Common:** Same root as all seven prior contexts: the engine runs a literal check (per-stage `verify_command` at record-result, or every `[[final_check]]` at verify-final) so an over-broad / wrong-scope / wrong-venue / wrong-interface check false-FAILS a genuinely-green stage or refuses resolution. The durable discipline is unchanged and now eight-times-confirmed: author each check against the ACTUAL observable+scope+venue+interface, scoped to the stage's OWN deliverable, and run it by hand once before trusting it. **Since 2026-08-10 that manual dry-run is partially mechanized:** `scripts/agentctl/checkrun.py` runs every stage-level `verify_command` in its declared venue at `submit-plan` and reports what it printed — warn-only, and blind by construction for a venue that does not exist yet (see the 2026-08-10 ENVIRONMENT context for the exact boundaries); the habit is still the operator's, the mechanism only removes the excuse for skipping it. **Instance 8 adds the venue-LIFETIME rule:** the engine's verify cwd is `state.repo_root`, and verify-final re-runs EVERY stage's `verify_command` — so if a stage DELETES its own working venue (a worktree/mount it removes as its final act), that venue must appear in NEITHER `[meta] repo_root` NOR any surviving stage's `verify_command`. Pin `repo_root` to a checkout that OUTLIVES all stages (the stable main checkout) and verify the LANDED artifact (origin/main), never the ephemeral venue — `cli.py`'s `cd <repo_root> && <cmd>` short-circuits to a false FAILED the moment that cwd is gone (cli.py:75-76). The two engine-correction remedies generalise across BOTH executed fields: (b) hand-patch `state.json` (`stages[k].criterion.verify_command` OR `final_check[k].command`) is cheap+non-destructive and always available; (a) force-substantive resets PASSED stages and should be the last resort. **As of `origin/main` `4761b49` (2026-06-30) the refinement-reload engine fix now covers BOTH stage `verify_command` AND plan-level `final_check`** — a correctness-only edit to either is a cheap refinement that preserves PASSED stages; remedies (a)/(b) are fallbacks, no longer the only path for final_check (instance 6 closed) — re-validated end-to-end in instance 7 (a single refinement replan carried BOTH the narrowed verify_command AND a re-pointed final_check into live state with no stage reset, no re-approval). Scope an absence/purity check to the stage's changed files (the task delta), **and a measurable stage's test gate to the stage's OWN subsystem tests, never the whole-repo suite** (or pre-existing unrelated reds false-fail it — whole-suite green is a separate concern, fixed by repairing the unrelated reds, not by widening the gate); prepend an explicit `cd <venue>` whenever the check touches a repo other than [meta] repo_root.

**Variations:** The false-fail vectors span a growing family: CLI-signature/output-format/interface typos (instances 3/4/6), file-SCOPE (recursive scan reaching unrelated files) and CWD (check venue != repo_root) (instance 5), SUITE-SCOPE (instance 7 — a stage gate pointed at the whole-repo `pytest tests/ -q` false-failed on 2 pre-existing unrelated reds, though the stage's own subsystem tests were green), and now VENUE-LIFETIME (instance 8 — `[meta] repo_root` pinned to the isolated worktree that the final stage DELETES, so the engine's own `cd <repo_root>` failed post-deletion and short-circuited every check to a false FAILED; fixed by repointing repo_root to the stable main checkout AND rewriting the earlier stage's verify_command — which verify-final re-runs — to verify the LANDED origin/main artifact from a mktemp extraction rather than the removed worktree). Instance 7 also exercised the correction under the plan-freeze gate: at DIAGNOSING the canonical `~/.claude/plans/*.toml` is frozen, so the corrected plan was authored in a gate-exempt /tmp copy and fed to `replan --plan`; the engine returned kind=refinement and carried BOTH the narrowed verify_command AND the re-pointed final_check into live state with NO stage reset (5 PASSED stages preserved) and no re-approval — the same cheap path validated for verify_command (instance 5) and final_check (instance 6), now confirmed for both fields in a single refinement. Force-substantive (a) and hand-patch state.json (b) were not needed. Net: the engine fix removed the correction cost across all these vectors, but the authoring antipattern (a check whose scope/observable/venue/interface does not match the stage's own deliverable) remains operator cognition — pre-empted only by the one-line manual dry-run. **The 2026-08-10 instance adds the sharpest form of the venue rule and one new axis.** Venue: the engine has owned this structurally since schema 24 (`Criterion.verify_venue_at_final`, plus `check_venue_warnings`' survivability warning naming this exact failure), so the operator's job is no longer to remember the rule but to DECLARE the venue — a hardcoded absolute `cd` bypasses the mechanism AND silences its warning about the bypass, because the lint returns early while no `delivery_worktree` is declared. And the venue can be UNRECOVERABLE, not merely absent: once `land-on-main.sh` has soft-reset the delivery branch, re-creating the worktree yields an empty tree, so re-anchoring on the landed surface is the only honest repair. New axis — LITERAL PROVENANCE: a `verify_command` greping for file CONTENT can name a phrase that landed in a sibling file, which reachability validation cannot catch (the path resolves; only the assertion is false), so the literal must be read back with `grep` from its target file rather than transcribed from memory. Both are now recorded in `skills/specializations/planner/SKILL.md` as a one-clause pointer to `scripts/agentctl/README.md` § Check venue plus the read-back rule (`59fbd3f`) — the re-norming was a missing CROSS-REFERENCE, not a missing mechanism, which is what the independent reviewer's first `revise` verdict established. **Instance 25 adds INVOCABILITY, one layer below every vector above:** the check is right in venue, scope, observable and interface and still cannot be RUN, because the permission layer denies the tool call — `hook-guard-canon-readonly.py` reads the command string textually, so any literal `$VAR` in a path while the engine's cwd is a canon root is denied as a potential canon write (workaround: the same command verbatim in a `.sh` file invoked as `bash /abs/path/gate.sh`, since the hook never inspects script contents — which is also the hole, filed as a Core task rather than patched mid-task). Its second half is an AUTHORING triple that only review caught: a negated comparison as the gate's LAST command inverts the verdict with no `&&`/`||` in sight; a fixture authored by the control's own author silently obeys the property under test (a self-authored fixture belongs to the CHECK, not the world — the mutated-WORLD norm covers it); and an absolute negative in a prose fact-control false-fails on a pre-existing NEGATED mention, i.e. the population-scoping rule this leaf records for code applies verbatim to text. Its cost half is a sandbox fact worth knowing before planning any spawn-executed stage: the session scratchpad under `/place/vartmp/…` is unreachable to EVERY spawn regardless of `--kind` or `--permission-mode` (three denials, $1.41), which is [[2026-07-02-spawn-sandbox-excludes-declared-stage-material]] widened from "the declared material" to "the session's own scratch root". **The 2026-09-03 context adds LANDING-METHOD:** a `kind="landed"` check correct in venue/scope/interface/observable can still false-fail because `_freeze_delivered_head` freezes the delivery worktree's PRE-merge branch tip, and a squash (or rebase) merge — as opposed to the plain two-parent merge every other stage used — discards that exact commit from trunk's ancestry, orphaning it; the fix is a one-off hardcoded ancestry check against the actual merge commit (`gh pr view <n> --json mergeCommit`), and the structural prevention lives one layer out, in landing discipline (always `--merge`), not in the check-authoring habit this leaf otherwise covers. **The 2026-10-07 context adds two vectors that are both about a criterion's REFERENT rather than its venue, scope or interface.** STALE-LITERAL: a criterion may be correct when authored, satisfiable when the stage passes, and unsatisfiable by the time verify-final re-runs it, because a LATER stage legitimately grew the artifact the criterion pins a literal count against — the dry-run habit cannot catch this, since the check passed at authoring time and at record-result; the fix is to cite the artifact's own declaration and assert only the authoring stage's own minimum, never to repeat the number. LIVE-STATE: a closing-gate conjunct whose truth depends on the machine's state at the moment of closing certifies the world, not the work, so it can false-fail while the very requirement it is probing is visibly working — the repair is to certify the INSTRUMENT in the gate and leave the evidence in the recorded observation the gate greps. Both vectors are authoring-time properties invisible to `checkrun.py`, which is why they argue for the criterion-contract pre-flight (execute every `verify_command`/`negative_control` against live state at `submit-plan`/`replan` and report each conjunct's truth value) rather than for another prose rule.

## Cost
High for the diagnosis, low for the fix. The 5-stage plan itself was small mechanical edits; the cost concentrated in two false-FAIL difficulty cycles on stage 2 before the root cause (refinement replan does not reload `verify_command`/`repo_root` — only a substantive replan does) was isolated. Net overhead vs. a clean run: ~2 extra difficulty cycles + one full substantive replan (v2→v3) + reading `cmd_replan`/`gates.py`/`plan.py` to localize the reload gap. No spawned specialists (all stages driven in-thread via next-stage+record-result, dispatch deliberately skipped to avoid re-spawning already-done work).
