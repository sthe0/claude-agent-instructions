# agentctl verifies a stage in repo_root, not the worktree it ran in; only a substantive replan can move the venue

## Difficulty
Executing a substantive agentctl plan in an isolated git worktree (chosen so a parallel session's dirty tree is not entangled) silently diverges the verification venue from the engine's bookkeeping. The engine stores meta.repo_root once at submit-plan and runs every stage's verify_command as 'cd <repo_root> && <cmd>' — i.e. against the MAIN checkout, which lacks the worktree's commits — so each genuinely-green stage is recorded FAILED and routed to DIAGNOSING. Worse, the obvious fix (edit the plan's verify_command/repo_root to the worktree and replan) does NOT take: diff_plans classifies a verify_command/repo_root-only change as a 'refinement', and the refinement branch of cmd_replan reassigns only title/result/means/method/conditions/invariants — never verify_command or repo_root. Those two fields are reloaded ONLY by a 'substantive' replan (state.stages=new.stages; state.repo_root=new.meta.repo_root), and the structural signature that triggers substantive excludes verify_command — so a structural field (e.g. a stage done_criterion) must be changed to force it.

## Order & criterion
Make the engine verify in the venue that holds the commits. Either (a) keep repo_root = main checkout and accept the double-cd (verify_command itself 'cd <worktree> && ...' wins over the engine's prepended 'cd <repo_root> &&'), OR — when stages were already loaded with main-checkout verify_commands — force a SUBSTANTIVE replan: bump a structural field (a stage's done_criterion) so diff_plans returns 'substantive', which reloads state.stages (worktree verify_commands) + state.repo_root=worktree, returning to PLAN_READY for re-approval. Criterion: state.json shows repo_root=worktree and every stage verify_command points at the worktree; record-result then runs the real check green in-venue.

**Acceptance check:** agentctl status + state.json: repo_root and all stage verify_commands resolve to the worktree; each stage record-result passes its real verify_command (no rubber-stamp); verify-final green.

### 2026-06-30 — same reload gap, NON-worktree, and the destructive-substantive-replan trap
- Where it arose: a project/global: 7-stage `junk/<user>/agents/` workspace-restructure plan (projects/ + common/ split). NOT a worktree this time — the verify_command divergence surfaced from a plain bug: stage 6's `verify_command` used `awk 'NR>140'` (counts lines across the *concatenation* of all files) where it meant `awk 'FNR>140'` (per-file line number). The engine auto-ran the stale NR command at record-result and false-FAILED the genuinely-green stage. Same class as the worktree case: **the field the engine actually executes (`verify_command`) cannot be corrected by a refinement replan**, because `_structural_signature` (plan.py) excludes verify_command, so a check-only fix always classifies as refinement, and the refinement branch of `cmd_replan` never copies verify_command into state.
- **KEY new tradeoff — a substantive replan RESETS already-PASSED stages.** The "force substantive" remedy from the initial context is *destructive* when earlier stages are already verified: the substantive branch does `state.stages = new.stages`, which re-initialises every stage outcome to pending — throwing away stages 1–5's PASSED records to fix a single field in stage 6. The cheaper, surgical remedy: **hand-patch the engine state store directly.** The state store (`~/.claude/agentctl/state/<session>.json`, a `FileStateStore`) is plain JSON and is NOT covered by the production gate (the gate guards settings/skills/agents/CLAUDE.md/instruction-repo/plans — not runtime state). Patch only `stages[k].criterion.verify_command` (NR→FNR), back the file up first, leave the 5 PASSED outcomes intact. Then a replan that targets the *node* (DIAGNOSING→VERIFYING) + re-arms the one stage suffices — no stage reset.
- **Registered-plan in-place-edit trap.** `cmd_replan` does `old = _load(state.plan_path)` and the refinement branch sets `state.plan_path = args.plan`. So after a refinement, `state.plan_path` *is* the file you last submitted — editing THAT file in place to build the next correction makes `old == new`, and the coverage gate's CHANGE check (the new stages' `(means, method)` multiset must differ from old) can then never pass. Remedy: submit each correction round as a **fresh, separately-named file** (plan-replan-v2.toml, -v3.toml, …), never by mutating the file at `state.plan_path`.
- **Flaky auto-dispatch on already-done work + no prior-dispatch guard.** `dispatch` for a `spawn:developer` stage auto-spawns a verifier synchronously; on work that is already complete this is non-deterministic (observed: one run COMPLETED at $0.36, an identical re-run MALFORMED→BLOCKED because the spawned developer misread the dispatch as "execute the whole plan"). `record-result` has **no** guard requiring a fresh dispatch — it needs node=EXECUTING + a non-None active stage + a non-empty `--control` attestation. Reliable path on already-done work: `unblock` (clear the BLOCKED) → `record-result --status passed --control "<genuine review attestation>"`, skipping dispatch entirely.
- Cross-ref: [[2026-06-24-developer-marker-not-on-line-1-false-block]] (the auto-spawned developer's MALFORMED marker is the same false-block failure mode).

### 2026-06-30 — FOURTH instance, DURING the fix: the engine fix removes the *correction cost*, not the *authoring antipattern*
- Where it arose: the `agentctl-verify-command-replan-fix` task itself (the engine change above). Stage 1's plan `verify_command` was again malformed at authoring — `python3 -m pytest scripts/tests/test_replan.py -q 2>&1 | grep -qiE 'verify|repo_root|carries'`: `pytest -q` prints only progress dots + an `N passed` summary, **never test-function names**, so the grep matched nothing and exited 1 → the engine false-FAILED a stage whose tests were 899-green. A 4th instance of the same false-FAIL class, committed *while shipping the fix for that very class*.
- **Two distinct difficulties, only one removed by the engine fix.** (1) *Correction cost* — once a verify_command is wrong, how expensive is the fix? The engine fix does **NOT** remove this; it remains operator cognition.

Two concrete traps now seen: a tool's CLI signature (instance 3: `lint-prose-length.py FILE` when the script takes no positional), and a tool's *output format* (instance 4: greping test-function names out of `pytest -q`, which suppresses them). Before trusting a check, **run it once by hand and read its real output**; for "is test X present" prefer greping the **test file** (`grep -q 'def test_…' file`) or `pytest --collect-only -q`, never the green-run summary. The engine now makes the fix cheap, so the cost of this mistake is low — but a one-line manual dry-run of the check still avoids the whole difficulty cycle.

### 2026-08-04 — Instance 23 — POSITIONAL BOOKKEEPING: a `path:line` pin false-fails on a pure line SHIFT (and silently covers a genuine EDIT) — closed structurally with content anchors
- Where it arose: landing branch `hook-prune-two-file` (parked ~5 days) into `main` — `verify-all` went red at `verify-config-root-refs.py` even though `git range-diff main...branch` reported BOTH of the branch's commits as `=`. - **The finding — a new axis for this family: the check is correct, the venue is correct, the interface is correct, and it still false-fails because the ADDRESS it uses is positional.** `scripts/config-root-refs-allowlist.txt` pinned each vetted `~/.claude` reference as `path:line`. Nothing about the branch changed those references; what changed was that `main` advanced and the rebase shifted line numbers inside the *referenced* files. Every prior instance in this leaf is about a check whose SCOPE/VENUE/INTERFACE was mis-authored; this one's check is authored perfectly and its data model is wrong. **The tell is diagnostic gold and easy to misread:** `range-diff` says `=` for every commit, so the instinct is "my branch is fine, the tree is broken" — both halves are true, and the breakage lives in a bookkeeping artifact that addresses a *shared, moving* file by position. Positional identity across a moving trunk is the same disease as instance 20's SHA-equality and merge-base-pinned range sweeps, one layer down: express identity by CONTENT, never by coordinate.
- **The two-way misfire (why "just re-pin the numbers" is not the fix).** A shifted pin fails in BOTH directions, and only one direction is loud. (i) Loud: line N now holds unrelated text → reported stale → a red on a genuinely-green tree. (ii) **Silent, and the one that matters:** after a shift, line N may coincidentally still hold *some* vetted-looking occurrence, so the entry keeps "covering" it while the reference the human actually vetted has moved elsewhere — an allowlist that has quietly stopped allowlisting what it was reviewed for. A hand re-numbering pass fixes (i) and *entrenches* (ii).
- **The fix — content anchors (`path:line:<sha8>`).** `sha8` = first 8 hex of `sha256` over the referenced line's STRIPPED text; anchors are resolved against occurrence lines only, yielding four explicit outcomes: `pinned` (anchor matches at the pinned line), `relocated` (matches exactly one other line — the pin follows its reference and the run prints `docs/x.md:48 -> :49`), `ambiguous` (matches several — resolves to nothing, so it can neither cover nor be reported stale), `unresolved` (matches none — genuinely stale: the reference's TEXT changed and must be re-vetted). Duplicate coverage (two entries resolving onto one occurrence) is its own failure. `--repin` migrated all 85 line pins in place; the accepted limit is stated in the file's own header — two byte-identical occurrence lines in one file cannot be pinned apart, which is what the whole-file form exists for.
- **The rule that makes the fix honest, and nearly got written the other way: `--repin` must REFUSE to re-anchor a STALE entry.** A migrator that "helpfully" re-anchors an entry whose text changed launders an unreviewed reference into a vetted allowlist — precisely the silent hole (ii) above, now automated. `--repin` rewrites only entries it does not have to guess about, and skips stale/ambiguous/duplicate ones by design. This bit immediately: editing line 122 of `scripts/README.md` (to describe the new mechanism) staled that row's own pin, and the correct path was to re-read the reference, confirm the reason still held, compute the anchor independently with `shasum`, and hand-edit the one spec — the mechanism catching its own author is the strongest evidence it works.

## Common core & variations
**Common:** Same root as all seven prior contexts: the engine runs a literal check (per-stage `verify_command` at record-result, or every `[[final_check]]` at verify-final) so an over-broad / wrong-scope / wrong-venue / wrong-interface check false-FAILS a genuinely-green stage or refuses resolution. The durable discipline is unchanged and now eight-times-confirmed: author each check against the ACTUAL observable+scope+venue+interface, scoped to the stage's OWN deliverable, and run it by hand once before trusting it. **Instance 8 adds the venue-LIFETIME rule:** the engine's verify cwd is `state.repo_root`, and verify-final re-runs EVERY stage's `verify_command` — so if a stage DELETES its own working venue (a worktree/mount it removes as its final act), that venue must appear in NEITHER `[meta] repo_root` NOR any surviving stage's `verify_command`. Pin `repo_root` to a checkout that OUTLIVES all stages (the stable main checkout) and verify the LANDED artifact (origin/main), never the ephemeral venue — `cli.py`'s `cd <repo_root> && <cmd>` short-circuits to a false FAILED the moment that cwd is gone (cli.py:75-76). The two engine-correction remedies generalise across BOTH executed fields: (b) hand-patch `state.json` (`stages[k].criterion.verify_command` OR `final_check[k].command`) is cheap+non-destructive and always available; (a) force-substantive resets PASSED stages and should be the last resort. **As of `origin/main` `4761b49` (2026-06-30) the refinement-reload engine fix now covers BOTH stage `verify_command` AND plan-level `final_check`** — a correctness-only edit to either is a cheap refinement that preserves PASSED stages; remedies (a)/(b) are fallbacks, no longer the only path for final_check (instance 6 closed) — re-validated end-to-end in instance 7 (a single refinement replan carried BOTH the narrowed verify_command AND a re-pointed final_check into live state with no stage reset, no re-approval). Scope an absence/purity check to the stage's changed files (the task delta), **and a measurable stage's test gate to the stage's OWN subsystem tests, never the whole-repo suite** (or pre-existing unrelated reds false-fail it — whole-suite green is a separate concern, fixed by repairing the unrelated reds, not by widening the gate); prepend an explicit `cd <venue>` whenever the check touches a repo other than [meta] repo_root.

**Variations:** The false-fail vectors span a growing family: CLI-signature/output-format/interface typos (instances 3/4/6), file-SCOPE (recursive scan reaching unrelated files) and CWD (check venue != repo_root) (instance 5), SUITE-SCOPE (instance 7 — a stage gate pointed at the whole-repo `pytest tests/ -q` false-failed on 2 pre-existing unrelated reds, though the stage's own subsystem tests were green), and now VENUE-LIFETIME (instance 8 — `[meta] repo_root` pinned to the isolated worktree that the final stage DELETES, so the engine's own `cd <repo_root>` failed post-deletion and short-circuited every check to a false FAILED; fixed by repointing repo_root to the stable main checkout AND rewriting the earlier stage's verify_command — which verify-final re-runs — to verify the LANDED origin/main artifact from a mktemp extraction rather than the removed worktree). Instance 7 also exercised the correction under the plan-freeze gate: at DIAGNOSING the canonical `~/.claude/plans/*.toml` is frozen, so the corrected plan was authored in a gate-exempt /tmp copy and fed to `replan --plan`; the engine returned kind=refinement and carried BOTH the narrowed verify_command AND the re-pointed final_check into live state with NO stage reset (5 PASSED stages preserved) and no re-approval — the same cheap path validated for verify_command (instance 5) and final_check (instance 6), now confirmed for both fields in a single refinement. Force-substantive (a) and hand-patch state.json (b) were not needed. Net: the engine fix removed the correction cost across all these vectors, but the authoring antipattern (a check whose scope/observable/venue/interface does not match the stage's own deliverable) remains operator cognition — pre-empted only by the one-line manual dry-run. **The 2026-08-10 instance adds the sharpest form of the venue rule and one new axis.** Venue: the engine has owned this structurally since schema 24 (`Criterion.verify_venue_at_final`, plus `check_venue_warnings`' survivability warning naming this exact failure), so the operator's job is no longer to remember the rule but to DECLARE the venue — a hardcoded absolute `cd` bypasses the mechanism AND silences its warning about the bypass, because the lint returns early while no `delivery_worktree` is declared. And the venue can be UNRECOVERABLE, not merely absent: once `land-on-main.sh` has soft-reset the delivery branch, re-creating the worktree yields an empty tree, so re-anchoring on the landed surface is the only honest repair. New axis — LITERAL PROVENANCE: a `verify_command` greping for file CONTENT can name a phrase that landed in a sibling file, which reachability validation cannot catch (the path resolves; only the assertion is false), so the literal must be read back with `grep` from its target file rather than transcribed from memory.
