# A norm or advisory that is already recorded does not reach the act of authoring the control

## Difficulty
The vector catalogue and its remedies are recorded, and in one case the engine even mechanized an advisory at submit-plan. The author, working in a fresh plan or session, still writes the same control, or reads the fired advisory and dismisses it as intentional. A recorded norm is only as strong as its trigger into the authoring act; prose recall and warn-only gates leave the decision to the same judgement that already failed.

**Functional ground:** The remedy for a control-authoring defect exists in memory or in an engine advisory, but nothing places it in front of the author at the moment the control is written, so the defect recurs against a known remedy.

### 2026-07-20 — TWELFTH instance: the SUITE-SCOPE advisory FIRED and I dismissed it as "intentional" — warn-only leaves the baseline-green check as residual perception
- Where it arose: `agent-bench-grade-integrity-gates` (local-only repo) — a stage added two grading-integrity gates to `grade_all.py`; I set the measurable `verify_command` to whole-suite `pytest -q` for a "no-regression" proof. At `record-result --status passed` the engine re-ran it LITERALLY → exit≠0 from ONE pre-existing red (`test_vendor_provenance::test_staged_commit_carries_both_cost_accounting_fixes` — machine-state-dependent vendored-toolchain check, **0** grading references, disjoint from my diff), routing a genuinely-green delivery to DIAGNOSING. Instance-7 vector exactly (whole-suite gate false-fails on a pre-existing unrelated red), now **self-inflicted the 12th time**.
- **The new, distinguishing failure:** the instance-11 mechanization *worked* — `verify_command_scope_warnings` DID surface the suite-scope advisory at submit-plan. I **dismissed it as "intentional"** and never ran the one-line residual discipline the warn-only design leaves to the model: **verify the aggregate check's baseline is GREEN before adopting (or overriding the advisory for) it.** A whole-suite exit-0 criterion only proves no-regression when the baseline is green; against a baseline with pre-existing unrelated reds it mis-fires on a correct delivery. Lesson sharpened: a non-blocking advisory only helps if not reflexively overridden — the perception the model still owns is the **baseline-green attestation**, not merely "is a whole-suite run justified." (Validates the open self-improvement question: should the suite-scope advisory require a recorded baseline-green attestation to override, rather than staying purely ignorable?)
- **Remedy applied:** overcome-difficulty cycle (declare→investigate→critique→normalize→replan); narrowed the criterion to `pytest -q --deselect <that one nodeid>` (exit 0 ⟺ no NEW failure AND grading tests green; all grading tests stay in the run). Adversarial thinker review (`git stash` on the diff) confirmed the excluded test is red on the UNMODIFIED baseline identically (change adds only green 371→384, subtracts nothing) — legitimate no-regression scoping, not gaming.
- **New engine wrinkle — a CRITERION-ONLY correction trips `replan_coverage_blockers`:** the replan changed only the stage's control criterion (`verify_command` scope), not means/method. But the coverage gate's CHANGE demand asserts "a difference cannot be removed without re-selecting a means/method" (it diffs the (means,method) multiset). That model assumes difficulties are removed via means/method; a mis-specified-**criterion** difficulty is removed by re-selecting the criterion, which the gate cannot observe. The designed `--coverage-waiver <reason>` is the honest escape (used here with a precise reason: criterion-only fix by construction; PRESERVE side already semantically in stage invariants). Candidate engine refinement: let a criterion-field change satisfy the CHANGE demand when the critique's difference is criterion-scoped.
