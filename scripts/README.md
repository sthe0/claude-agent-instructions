The table below is machine-checked against the filesystem by [verify-readme.py](verify-readme.py) (every `scripts/*.py|*.sh` and `cursor/scripts/*.py|*.sh` must appear; nothing dangling). Add a row when you add a script; `verify-readme.py --fix` reconciles the row set, then fill in any `TODO` purpose cells by hand.

## Change attribution

Answering "which agent session made which change" doesn't require reading a transcript. Two pieces work together: a durable edit-ledger that records every Edit/Write, and a commit trailer that stamps the session onto the commit it produced.

**The edit-ledger.** The ledger (`agentctl/edit_ledger.py`) has **two feeders**. The primary one is the `hook-scope-track.py` PostToolUse chokepoint: every Edit/Write tool call appends one JSON line, at the same point that already observes every tool call. The second covers writers that reach canon files by direct filesystem IO and so never pass through the Edit/Write hook — `record-experience.py`, `stamp-memory-dates.py`, and the four setup shell scripts (`apply-settings.sh`, `install-reminder-hooks.sh`, `set-context-cap.sh`, `setup-project-memory.sh`); each calls `edit_ledger.stamp(file, tool)` itself so its write is attributed too. Both feeders drop **scratch paths** (`/tmp`, `$TMPDIR`, `tempfile.gettempdir()`, or `$AGENTCTL_SCRATCH_ROOTS` when set) through `exempt_paths.is_ledger_noise`, so the ledger records only durable edits. It lives at `config_root.agentctl_edit_log()` (`~/.claude-agent/agentctl/edit-log.jsonl` by default, overridable via `$AGENTCTL_EDIT_LEDGER`) and is append-only and fail-open: a write failure never blocks the edit that triggered it.

Each row names its feeder in the `tool` field: `Edit`/`Write` for the hook, or a descriptive marker for a direct-IO writer (`record-experience:new`, `stamp-memory-dates`, `script:apply-settings`, …), so a query can tell which writer produced a row.

The `edit-ledger.py` CLI has both a read side and a write side:

```
scripts/edit-ledger.py by-session <session_id>   # read
scripts/edit-ledger.py by-file <path>            # read
scripts/edit-ledger.py stamp <file> <tool>       # write — used by the shell writers above
```

Each row carries **two session ids**, not one: `session_id` is the agent that actually made the edit (which may be a subagent), and `env_session_id` is the root session's `CLAUDE_CODE_SESSION_ID` — the id a commit trailer keys on. `by-session` matches a row when *either* id equals the query, so looking up a commit's `Agent-Session` value also surfaces every subagent edit made under that root session, not just edits made by the root session directly.

**The commit trailer.** `agent_commit_trailer.py` builds up to two trailer lines — `Agent-Session: <session_id>` and `Agent-Task: <tracker_key-or-task_id>` — from the current session's `CLAUDE_CODE_SESSION_ID` and its agentctl state file. Both the git `commit-msg` hook and a machine-local landing script call this same helper, so the trailer format is byte-identical across Core git commits and any other VCS front-end. A human commit (no agent session, or no matching state file) gets no trailer at all — only agent-authored commits are stamped.

Two things to know before trusting `Agent-Task`:
- It's best-effort, not authoritative: it reflects whatever task the agentctl state file held *at commit time*, so a session that got re-purposed for a different task without a fresh `classify` can carry a stale value.
- It's deliberately restricted to `tracker_key`/`task_id` and never derived from the free-text `goal` — `goal` can carry private or internal detail, and this trailer lands in the public Core repo (and, via a machine-local landing script, in that VCS's history too).

And some commit paths are known to carry no trailer at all: `git commit --no-verify` (skips the hook entirely), a squash or rebase-merge that rewrites the commit message afterward, a non-agent shell that happens to have a leaked `CLAUDE_CODE_SESSION_ID` in its environment, and an ad-hoc `<vcs> commit -m` run outside the landing script.

## Judge execution ledger

A judge call that fails open is invisible on every other observable: the hook still exits 0, the harness sees no error, and a fabricated `False` looks byte-identical to an honest `NO`. The ledger (`lib/judge_ledger.py`) exists so that "the judge said no", "the judge never ran" and "the judge ran and the hook threw the answer away" — three outcomes with the same net effect (allow) and unrelated meanings — stop arriving as one indistinguishable event.

**Two feeders**, one per side of the frozen boundary. The three judge-calling hooks (`hook-escalation-diagnosis-gate.py`, `hook-deferring-disposition-gate.py`, `hook-turn-end-gate.py`) write the shape of an invocation: `hook_start` as the first statement of `main()`, then `entered` / `decided` per judge decision point, and `final` / `emitted` / `discarded` around delivery. `agentctl/advisor.py::subprocess_runner` writes the mechanical facts of the call itself — `started` before the subprocess, `call` after it (duration, `timed_out`, returncode, `raised`) — because it is the sole place `RunResult.timed_out` is ever set. Attribution crosses that boundary on an ambient carrier (`set_current_judge` / `take_current_judge`), since the judge functions' `runner(...)` call sites cannot grow a parameter; a call no judge claimed is recorded as `unattributed` rather than guessed onto whichever judge ran last.

It lives at `config_root.agentctl_judge_ledger_log()` (`~/.claude-agent/agentctl/judge-usage-ledger.jsonl` by default, overridable via `$AGENTCTL_JUDGE_LEDGER` — which is what the test suite's autouse isolation fixture sets, so a suite run never lands lines in the real ledger) and is append-only and fail-open like the edit-ledger: each line is one JSON object written with `O_APPEND` + `fsync` inside a blanket `except`, so a ledger failure never becomes a new way for a hook to fail, and a line that lands survives the process being killed immediately after. Lines carry outcome metadata only — never turn content.

**Two readers consume it**, answering two different questions. `judge-usage-report.py` answers *what did the judges do* — the whole outcome taxonomy counted, so that all but three of the recordable shapes — which end alike in "the turn was allowed" — stop reading as one event. `check-dispatch-witness.py` answers the narrower *did this hook dispatch at all under the new registration*, and it is the one that can refute a config-file claim: the old registration killed each hook below its own judge's fastest measured call, so it demands a ledger line that could not have been written under the old limit.

That witness reads the old limits from a snapshot file another step writes. Both ends of that contract live in `lib/dispatch_witness_snapshot.py` — `write_snapshot()` for the capture step, `load_snapshot()` for the witness — so the format cannot drift between them; schema `dispatch-witness-old-wiring/v2`:

```json
{
  "schema": "dispatch-witness-old-wiring/v2",
  "hooks": {
    "hook-turn-end-gate.py": {
      "status": "wired", "timeout": 5,
      "scope_qualified": true,
      "members_read": ["/home/u/.claude-agent/settings.json"]
    }
  }
}
```

`status` carries one of `lib/hook_wiring.py`'s three probe outcomes verbatim and `timeout` is a number or an explicit null. Both fields are required even where one looks redundant: a bare null cannot separate "was never registered" — under which any execution is already new evidence — from "could not be determined", under which nothing may be concluded, and collapsing them would silently read every unknown as the permissive case.

`scope_qualified` records whether the snapshot's claim is a fact or a qualified one, and it is why the schema is at v2. A probe falls short of the whole settings chain in three ways, not one: `hook_wiring.probe()` reads the project-level `.claude/settings.json` only when the harness names a project root in `$CLAUDE_PROJECT_DIR`; a member may not parse; and a member may parse and then carry a settings shape the scanner does not model, so its entries are skipped unread even though the file opened fine. The last two apply at **either** level — a user-level member the probe could not read hides a registration, or a larger timeout, exactly as well as a project one, which is why the field is not a project-scope question.

Under any of them ABSENT means "not registered in the members this probe could account for" and WIRED's `timeout` is the largest among those members. Both are unsafe to spend unqualified, and in opposite directions: an unqualified absence lets a hook wired in a member the probe never accounted for be witnessed by any line at all, and an unqualified timeout is a *lower bound* that a call beating it need not have beaten in reality. So a qualified entry blocks on either status, and `members_read` names the files the claim rests on. The field is derived from `Wiring.scope_fully_covered`, never declared — there is no seam for a caller to assert past the probe, because a caller convinced it saw every member has no way to prove it; widen `hook_wiring.settings_chain()` instead. (`Wiring.project_scope_covered` is the neighbouring field and answers the *other* question — how wide the chain reached, which is what an ABSENT sentence has to word.) There is no v1 read path: a v1 file carries no scope information to upgrade from, and it is refused rather than guessed at.

**Neither rotation nor a `--since` window bounds ledger growth**, deliberately. Rotation would live in the writer, and the writer's design principle is that a ledger failure must never become a new way for a hook to fail — a rename/reopen path adds exactly that second failure mode to the one place that cannot afford one. A read-side window would bound the read but not the file. The file is machine-local, uncommitted, and truncatable by hand, so the residual risk is a slow read rather than a lost gate; `judge-usage-report.py` prints a NOTE once the ledger passes `LEDGER_SIZE_ADVISORY_BYTES` (64 MiB) so the decision is revisited by measurement rather than by memory.
