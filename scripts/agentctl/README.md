# `agentctl` — the coordination engine

`agentctl` is the **deterministic control-flow engine** for a substantive task. It owns the *spine* — classify → plan → approve → execute → verify → resolve — while **prose supplies the cognition** at each step (the classification judgment, the plan content, the marker handling). The canon: **code = deterministic control-flow, prose = cognition.** The engine never decides *what* the right answer is; it decides *which step is legal next* and *which gate blocks*.

Run it from any cwd via the standalone entry point:

```bash
python3 ~/claude-agent-instructions/scripts/agentctl-cli.py <cmd>
```

Each command returns a **Directive** (JSON): the next node, which cognitive leaf to run, and whether a gate blocks.

## State machine

A substantive task moves through this node lifecycle (`agentctl.state.Node`):

```text
start → CLASSIFIED → ROUTED → PLANNING → PLAN_READY ──■APPROVAL GATE■──→ APPROVED
                                            ⟲ revise_plan                    │
                       │              (resubmit pre-approval)          PARTITIONED
        small change ──┘                                                    │
                       │                                                    │
                       └──────────────────────────────→  EXECUTING  ⇄  VERIFYING
                                                              │             │
       (stage FAILED → DIAGNOSING: declare→investigate→critique → replan ──┘
                          → retry, or PLANNING on a substantive replan)      │
                                    ▲                                  RESOLUTION
                                    └───────────── reject ────────────────┘  │
                                        (user rejects the delivery)          │
                                                            ──■RESOLUTION GATE■──→ RESOLVED
```

`PARTITIONED` also has a guarded direct edge straight to `VERIFYING` (event
`finalize_partitioned`, fired by `next-stage`): when a substantive replan
carried every stage's PASSED outcome forward (a control-criterion-only change
left every stage's carry-key unchanged), there is no ready stage left to
execute, so the engine advances straight to final verification instead of
dead-ending.

The two gates (`■`) are **non-skippable**:

- **Approval gate** — [`hook-state-gate.py`](../hook-state-gate.py) hard-denies production Edit/Write until the engine reaches an execution node. "Production" includes the agent's own config/instructions; only memory and `/tmp/` scratch are unconditionally exempt.
- **Resolution gate** — requires explicit user confirmation; [`hook-turn-end-gate.py`](../hook-turn-end-gate.py) blocks a turn from ending without it, [`hook-resolution-reminder.py`](../hook-resolution-reminder.py) is the complementary advisory nudge.

[`verify-agentctl.py`](../verify-agentctl.py) checks that every gate has its guardian hook and that the schema, transitions, and cognitive leaves stay consistent.

### States

Each node is a phase in the task lifecycle (`Node` in `state.py`). The *route* picked at `ROUTED` decides the path: **chat** ends there (answer in-thread), **small change** jumps straight to `EXECUTING`, **substantive** walks the full spine.

| State | Meaning |
|---|---|
| `CLASSIFIED` | Session armed; awaiting the weight-class judgment. |
| `ROUTED` | Weight class + route recorded. Terminal for chat (`DIRECT`); small change → `EXECUTING`; substantive → `PLANNING`. |
| `PLANNING` | Authoring the plan (stages, each with its result image + done criterion). |
| `PLAN_READY` | Plan authored; **held at the approval gate** until the user approves. |
| `APPROVED` | Plan-approval gate passed. |
| `PARTITIONED` | M1–M4 **delivery-partition** verdict recorded — into how many independently-shippable units (PRs/tickets) the approved plan is cut. Normally exits via `execute_approved` once a stage is ready; if a substantive replan already carried every stage's PASSED outcome forward and none is ready, `next-stage` instead fires the guarded `finalize_partitioned` edge straight to `VERIFYING` (see State machine above). |
| `EXECUTING` | Running the active stage — in-thread or via a dispatched specialist. |
| `VERIFYING` | A stage result was recorded; checking it, then choosing next stage vs final. |
| `RESOLUTION` | All stages PASSED; **held at the resolution gate** awaiting user confirmation. Exits via `resolve` (confirmed) or `reject` (user rejects the delivery, re-opening the difficulty cycle at `DIAGNOSING` — see `reject` below). |
| `RESOLVED` | User confirmed the task is done (terminal). |
| `DIAGNOSING` | A stage FAILED — or the user `reject`ed a `RESOLUTION`-gate delivery, or the engine itself detected an **effort divergence** on a PASSING result (§ Effort divergence: the third entry path, and the only one no human initiates), or a **failing `AcceptanceReview` verdict** surfaced at `verify-final` with no other reachable difficulty cycle (§ Effort divergence § Renegotiation gate, GitHub #128) — entering the **overcome-difficulty** sub-spine. The engine runs `declare → investigate → critique` (filling the `Difficulty` record) and **blocks `replan` until the record is complete** (`gates.difficulty_blockers`); this same completeness check gates authoring the corrected plan file at `DIAGNOSING` (`hook-state-gate.py`'s `diagnosing_plan_write_ok`). When `critique` records the structured similarities/differences split, `replan` additionally enforces a **coverage gate** (`gates.replan_coverage_blockers`): every named similarity must reappear as a stage condition/invariant (normalized substring match), and naming any difference forces the plan's **operative surface** — what the engine executes or dispatches on, not its prose — to change (see § Check venue for the surface's exact field list); a failing coverage gate can be bypassed with a recorded `--coverage-waiver <reason>` (never the difficulty-record precondition). Once the cross-session `replans` count reaches `effort-replan-absolute`, `replan` itself additionally refuses until an explicit customer renegotiation decision is recorded (§ Effort divergence § Renegotiation gate, GitHub #177). `replan` is the sole exit — back to `VERIFYING` to retry, or to `PLAN_READY` for a substantive re-plan. The *cognition* of each phase lives in the `overcome-difficulty` skill. |
| `BLOCKED` | A structural blocker (spawn refusal, escalation) interrupted the flow; `unblock` / `replan` returns to the prior node. |

### Sub-plan stack

When a stage's unmet element requires a full substantive plan to supply it, the engine nests a **service sub-plan** via `push-subplan` / `pop-subplan`. On `push-subplan` a `PlanFrame` snapshot of the current parent context (plan path, node, stages, gates, repo root, `final_check`, `partition`, `originating_stage`) is pushed onto `state.plan_stack`; the child starts a fresh `CLASSIFIED → … → RESOLVED` cycle. On `pop-subplan` the parent frame is restored and the originating stage is marked `PASSED`. **No auto-pop across an unresolved child** — `pop-subplan`'s source node is `RESOLVED`, which already requires `resolution.passed`, so the guarantee is structural (machine transition table), not an extra check. Stack depth is bounded by `_MAX_PLAN_STACK` (mirrors `max-recursion-depth` from `~/.claude-agent/config.md`).

## Commands

The happy-path spine, in order:

```text
start → classify → plan → submit-plan → approve → partition → next-stage
      → dispatch → record-result → verify-final → resolve
```

| Command | Effect (transition) |
|---|---|
| `start` | Arm a session (idempotent with `--if-absent`; auto-run by `hook-engine-start.py` on each prompt). Optional `--host claude|cursor` best-effort-binds sticky `runtime_host` (classify is the hard gate). |
| `reset` | Re-arm for a new task at a task boundary; refuses mid-substantive without `--force`. Optional `--host` on the fresh state (same best-effort as `start`). |
| `classify` | Record weight class + route (`CLASSIFIED → ROUTED`). Requires a bound `runtime_host` (`--host claude|cursor` or ambient detect — sticky thereafter). `--deliverable-kind reasoning\|code\|ops\|mixed` records what kind of artifact the task produces; `reasoning`/`mixed` on a SUBSTANTIVE session arms the `ledger` plugin's `auto_activate` (see § Plugins). |
| `plan` | Enter planning for a substantive task (`ROUTED → PLANNING`). |
| `submit-plan` | Mark the plan authored and ready for approval (`PLANNING → PLAN_READY`). A TOML plan may set `[meta] repo_root` and `[meta] delivery_worktree`, and each stage/`[[final_check]]` may declare a `verify_venue`/`venue` — see § Check venue for where a check actually runs; unset, `repo_root` is the invoker's cwd, so paths in a check with no delivery venue must then be absolute. Called again **at `PLAN_READY`** (pre-approval revision, e.g. after a thinker `revise` verdict), it resubmits via the `revise_plan` self-loop instead of `submit_plan` — no `reset --force` needed — and unconditionally clears any recorded `plan-review` so that gate re-arms for the new plan version. This is also the event `review_dispatch` (§ Plugins) observes to proactively name the required thinker spawn, ahead of `approve`'s reactive refusal. |
| `plan-review` | Record a thinker's review of a plan version (`--verdict pass\|revise\|override --reviewer <name> [--concern …] [--note …] [--target <plan>] [--scope 'stage:<n>']`). Backs the **plan-review gate** (`gates.plan_review_blockers`): on a SUBSTANTIVE session `approve` and `replan` are refused until a review exists that is bound to the current plan and whose verdict is `pass` (or a user-authored `override` — distinct reviewer, non-empty note). A review recorded at a *different* path still binds when its attested digest matches the current plan's bytes — a rename, not a replacement (#195); the digest itself is only ever stored when the engine could re-read the reviewer's own target and confirm it, so an unreadable target plus a `--plan-digest` is refused rather than taken on the caller's word. `--scope` (default: whole plan) binds the verdict to one stage's current rendering instead — see § Review scope and the coverage decision. A stage-scoped `revise`'s concerns are partitioned by `gates.classify_concerns` into in-scope and out-of-scope (a concern naming a *different* stage, or `meta:`/`order:`, is outside a stage-scoped reviewer's remit) — only an in-scope, non-discharged concern blocks; an out-of-scope one is stored (`PlanReview.out_of_scope_concern_ids`) and surfaced as a non-blocking advisory note, never silencing it but never letting it hold up a review that was never asked to cover that part. A legacy review recorded before this classification existed (both id lists empty) still blocks on every concern, as before. The gate closes at `present-plan --kind essence` too: essence cannot be presented (and thus an approval ask cannot be assembled) before a passing thinker verdict bound to the current plan bytes; `--kind full` is the detailed on-request view, not the approval trigger, so it stays ungated. A third kind, `--kind replan_diff`, backs the separate **replan-authorization gate** instead (§ Replan authorization) and carries no thinker-review precondition of its own. `AGENTCTL_PLAN_REVIEW=1/0` force-enables/disables the gate. Past the pre-approval review-round budget (§ Review-round budget) the gate substitutes a routing message for a further review demand. No node change. This gate is the reactive counterpart `review_dispatch` (§ Plugins) surfaces proactively at `submit-plan`, so the required spawn is named before this row is ever reached. **present-plan refuses an essence while premise blockers stand**: past the plan-review precondition above, `cmd_present_plan` (kind=essence) also computes `plugins_premise.premise_blockers` — the same set `approve` refuses on (open questions, undispositioned order elements, a stale or not-yet-run enumeration cross-check) — and stamps nothing while any stand, reversing the earlier "present, then discover at approve" ordering (#60; incident 2026-09-28: an essence was stamped with 12 raised enumeration candidates and `approve` then refused, costing a second approval round). The essence-coverage half of `premise_blockers` is excluded from this check (it would compare the receipt against itself before it exists); `approve`'s own gating stays unfiltered. This narrows, rather than closes, the in-flight enumeration-disclosure window (§ Order coverage): an essence can no longer be stamped while the enumeration cross-check has not landed — `present-plan` refuses with "enumeration not run" until the pass lands, or its deadline passes and `enumeration_not_landed` is recorded as an escape. Accepted cost: in that window the coverage-block containment check first asks the coordinator to paste the in-flight disclosure line, and the premise check then refuses the stamp anyway — one extra round in a rare window. |
| `plan-review-delta` | **Read-only** pre-flight (`--session <sid> [--plan <path>]`): reports, without saving state, whether a whole-plan review is currently needed (meta/order moved, or none has ever landed) or which stage indices instead need their own `--scope`d pass, and hands back the current rendering of exactly the part that needs eyes. See § Review scope and the coverage decision. |
| `present-plan` | Stamp the `PlanPresentation` receipt the approval ask (and `replan` authorization) is assembled from: `--kind essence\|full\|replan_diff --rendering-file <path>` (`--plan <candidate>` only with `replan_diff`; `--rejection-text` records the user's reply to a prior presentation; `--emit-skeleton` stamps nothing and hands back the `[stage N]` anchors a `full` rendering must keep). The receipt binds the plan's `plan_sha256` and the rendering's bytes; the delivery hook then verifies those bytes reached the user (see the approval-gate sections below). The hook writes the essence delivery stamp at any replan-capable node (`STAMP_NODES`: `PLAN_READY`, `APPROVED`, `PARTITIONED`, `EXECUTING`, `VERIFYING`, `DIAGNOSING`), not only `PLAN_READY`: a changed plan is re-presented *before* `replan` while the node is still `APPROVED`, and a stamp bound to the exact bytes cannot go stale by the later move to `PLAN_READY` — so `approve` needs no `confirm-delivery` escape on the honest path. Outside `PLAN_READY` the hook only observes and stamps; every DENY stays `PLAN_READY`-only. Existing refusals — plan-review blockers (`essence`, `replan_diff`), premise blockers (`essence`), the rendering cap, `full` completeness — are unchanged. **Writer-pass gate** — it runs after them and covers **all three kinds** (unlike the plan-review refusal above, which leaves `--kind full` ungated): the rendering must be bound, by `lib.writer_pass.bind`, to a tech-writer witness in this session's transcript — a `Skill tech-writer` / tech-writer subagent / `spawn-specialist.py --kind tech-writer` call followed by a `Write` of the whole rendering file. The transcript is derived from the session id (newest `<projects root>/*/<session id>.jsonl` across `config_root.projects_roots()`), never named by an argument. `data.writer_gate.outcome` is one of `bound` (strength and evidence alongside), `no_transcript` and `unreadable` (advisory — the presentation proceeds, as for a caller outside the harness), `override`, or `refused` (strength `NONE`/`NO_WITNESS_IN_WINDOW`: nothing is stamped). `CLAUDE_PUBLISHED_TEXT_GATE=0` is the kill switch shared with the published-text hook; the directive's detail then opens with `writer gate OVERRIDDEN` and the presenting turn names it to the user. |
| `risk-accept` | Record an accepted-risk discharge for a `revise`-verdict concern (`--scope <'' \| 'stage:<n>'> --concern-id <id> --basis <text> --risk <text> --author <name>`), bound to the same `(scope, concern_id)` pair the concern was raised under and to a snapshot of the plan bytes as they stand when the acceptance is recorded. See § Accepted risks. No node change. |
| `approve` | Pass the plan-approval gate (also gated by `plan_review_blockers`, see `plan-review` — already surfaced proactively by `review_dispatch` at `submit-plan`); `--by` names the approver (`PLAN_READY → APPROVED`). Also snapshots the plan **as approved** (content-hash-named file under the state dir, recorded as `plan_snapshot_path`/`plan_snapshot_hash`) — the immutable baseline `replan` diffs against, so an in-place edit of `plan_path` can never masquerade as "no change". |
| `partition` | Record the M1–M4 **delivery-partition** assessment — into how many independently-shippable, separately-reviewable units (PRs/tickets) the approved plan is cut. Delivery segmentation, **not** the planner's step-level decomposition (`APPROVED → PARTITIONED`). Optionally materializes the split as **units** via repeatable `--unit '<mode>\|<stages csv>\|<title>[\|<ref>]'` — each unit groups approved-plan stage indices (pairwise disjoint) under an org-neutral execution mode `inline` / `spawn` / `subtask`; see `memory-global/leaves/partition-markers.md` § Materialization. |
| `partition-units` | Record (or replace) the per-unit delivery routing **after** the verdict is surfaced — the user's structure decision arrives once they have seen the M1–M4 verdict. Same `--unit` syntax as `partition`; allowed only at `PARTITIONED` or `EXECUTING`; replaces the whole units list, leaves verdict + node untouched. Re-recording at `EXECUTING` does not re-validate against already-PASSED stages (documented limitation). |
| `next-stage` | Select the next ready stage and enter execution (`→ EXECUTING`). At `PARTITIONED` with no ready stage: if every stage is already PASSED (a substantive replan carried them forward), fires the guarded `finalize_partitioned` edge to `VERIFYING` instead of refusing; a genuine non-ready, non-PASSED stage still returns a non-ok directive. |
| `dispatch` | At `EXECUTING`, route the active stage to its actor (`in_thread` / `spawn:<specialization>`) and return the cognitive leaf + return-marker handling; no node change. For a spawn stage this command **is** the spawn — it runs `spawn_cli_for(runtime_host)` (`spawn-specialist.py` for `claude`, `spawn-cursor-specialist.py` for `cursor`) synchronously (blocking until the specialist returns); do **not** spawn manually with `spawn-specialist.py` or `claude -p` first. `--constraints` passes the spawned specialist a clarification that bounds HOW it does the already-approved stage — never a scope or done-criterion change; long text as `@<path>` (`dispatch` only forwards the reference, the specialist resolves it on its own side) — the plan-authored `--done-criterion` shares this same `@<path>` forwarding, not only `--constraints`. `--dry-run` is a pure preview: echoes the spawn command with no event log, no state save, no marker routing. On a `needs_control()` (`spawn:developer`) stage, this is also the event `review_dispatch` (§ Plugins) observes to proactively name the required code-reviewer spawn, ahead of `record-result`'s reactive refusal. |
| `record-result` | Record a stage's actual result + status, plus an optional general `--control` attestation (how element #3, the control criterion, was met) and an optional `--code-ref` (for `spawn:developer` stages, cross-checked against the bound code review — see *Code-review gate* below). PASSED → `VERIFYING`; FAILED → `DIAGNOSING` (enter the overcome-difficulty sub-spine). A `spawn:developer` stage is **refused** PASSED without a non-empty `--control` — see *Control attestation* below; on a SUBSTANTIVE session it is also refused without a bound passing `CodeReview` — see *Code-review gate* below, already surfaced proactively by `review_dispatch` at `dispatch`. |
| `code-review` | Record a `code-reviewer`/human review of the active `spawn:developer` stage's produced code (`--verdict pass\|revise\|override --reviewer <name> [--concern …] [--note …] [--code-ref <rev>]`). Backs the **code-review gate** — see *Code-review gate* below. No node change. `review_dispatch` (§ Plugins) is the proactive trigger naming this spawn at `dispatch`. |
| `declare` / `investigate` / `critique` | In `DIAGNOSING`, fill the three sections of the `Difficulty` record **in order** (the engine refuses out-of-order calls). Each records one phase's artifact; the content is the `overcome-difficulty` skill's cognition. `critique` also accepts the structured split `--invariant-to-preserve` / `--difference-to-remove` (both repeatable) that the `replan` coverage gate checks. |
| `verify-final` | Pass the final-verification gate: all stages PASSED + the plan's *Final verification* (`VERIFYING → RESOLUTION`). |
| `resolve` | Pass the resolution gate; `--by` names the confirmer (`RESOLUTION → RESOLVED`). |
| `reject` | The resolution gate's **negative exit**: the user rejects the delivery as not matching intent (`RESOLUTION → DIAGNOSING`). Requires `--reason <text>` (non-empty; seeds the `Difficulty` record's `declaration.actual`); marks the stage(s) named by repeatable `--stage <n>` FAILED, defaulting to the final stage so a reject is never a structural no-op. Hands off to `overcome-difficulty` exactly like a stage failure — `declare → investigate → critique → replan`. |
| `replan` | Apply a revised `--plan`. **Precondition-gated** in `DIAGNOSING`: refused until the `Difficulty` record is complete, and — when the critique recorded a split — until the **coverage gate** passes (similarities carried into conditions/invariants, matched by substring after normalizing case/whitespace on both sides; a means/method changed for the declared differences). A failing coverage gate can be bypassed with `--coverage-waiver <reason>` — refused if the reason is empty, recorded in session history and the gate log (`replan_coverage_waiver`), and never bypasses the difficulty-record completeness precondition. **Also precondition-gated at/above `effort-replan-absolute`** by `gates.diagnosing_replan_blockers` (§ Effort divergence § Renegotiation gate, GitHub #177): a bare `replan` is refused until `--renegotiation-decision {continue,rescope,abandon} --renegotiated-by <name> --renegotiation-note <text>` records an explicit customer decision; `continue`/`rescope` call `task_accumulator.reset`, zeroing every axis of the cross-session task accumulator (including `review_rounds`), before the replan proceeds, `abandon` parks the session at `BLOCKED` without touching `--plan`. Diffs the corrected plan against `_replan_baseline_path`: the **approved snapshot** (`plan_snapshot_path`) when that file exists on disk, otherwise `plan_path` (a legacy pre-snapshot session) — so the possibly-in-place-edited `plan_path` is the baseline only when no snapshot exists. An ordinary `replan` does not reset `review_rounds`; only the renegotiation path above does. A means/method/conditions/invariants/verify_command/expected_exit-only delta (or a `[meta] repo_root` change) is a **refinement** (retries the re-armed stage, `→ VERIFYING`; carries the corrected check command into live state without resetting PASSED stages); executor/done-criterion changes are **substantive** (re-arm the approval gate, `→ PLAN_READY`, **carrying forward PASSED status** — and its recorded `Outcome` — for any stage whose full definition is unchanged by the diff; a change to only `verify_venue_at_final` does not count as unchanged and resets that stage, tracked in [#305](https://github.com/sthe0/claude-agent-instructions/issues/305)). `--renormalize` selects a fourth branch that bypasses all of the above (§ Renormalization). **Also precondition-gated by `gates.replan_authorization_blockers`** (§ Replan authorization): outside a complete `DIAGNOSING` difficulty cycle, a refinement or no_change diff is refused until `present-plan --kind replan_diff --plan <candidate>` has been presented AND proven delivered (an `[authorize-replan]`-marked ask, or the `confirm-delivery --kind replan_diff` escape); a substantive diff and a byte-identical proposal are exempt. `AGENTCTL_REPLAN_AUTHORIZATION=1/0` force-enables/disables it. |
| `check-coverage` | **Read-only** pre-flight (`--session <sid> --new <path>`): reports whether `--new` would clear the `replan` coverage gate right now, without saving state, logging a gate, or transitioning the node — lets the coordinator learn about a coverage miss before spending a thinker plan-review on a plan version that would only bounce off `replan`'s own gate afterward. Calls `gates.replan_coverage_blockers` directly against the same OLD (approved snapshot, falling back to `plan_path`) / NEW (`--new`) pair `replan` diffs. Exits non-zero with the blockers list when the active critique's invariants aren't covered; exits zero with `OK — coverage clear` when they are; exits zero with a plain "nothing to cover" message when no critique is recorded. |
| `fire-acknowledge` | Resolve the **synchronous effort-fire gate** (`gates.effort_fire_blockers`, § Effort divergence § The synchronous gate): `--by <name> --decision continue\|abandon\|revise [--note <text>]` appends an `ack` onto the LAST entry of `state.effort_fires` (never deletes — the append-only audit trail is preserved). `continue` clears the gate with no node change; `abandon` parks the session at `BLOCKED` via the same bypass-`transition()` idiom `block` uses (never `RESOLVED` — a mid-execution fire routinely leaves stages PENDING, and `check_invariants` refuses `RESOLVED` unless every stage is PASSED), reversible via `unblock`; `revise` also makes no node change (a fire always lands in `DIAGNOSING` already) but records the human decision informing the ordinary `declare → investigate → critique → replan` cycle that follows. A no-op (returns `ok=True`, `action="noop"`) when no fire is recorded or the last fire is already acknowledged — repeat calls never re-acknowledge. |
| `block` / `unblock` | Mark a difficulty (`any → BLOCKED`) and return to the prior node. |
| `resolve-permission` | Record the decision on a specialist's `PERMISSION-REQUEST` (`--session <sid> --decision granted\|denied --scope once\|project\|global\|stage`). A `stage`/`once` scope additionally **materializes** the grant onto the active stage as a runtime `[stage.grants]` entry via repeatable `--rule <rule>` / `--add-dir <PATH:MODE>` — validated through the identical `grants.validate_rule`/`validate_add_dir` every declared/derived grant passes, atomically (one invalid entry refuses the whole call, nothing partially recorded). `stage` scope lives for the rest of the stage's dispatches; `once` is consumed after the first dispatch that uses it (`_consume_once_grants`). See § `[stage.grants]` below. |
| `plan-grants` | **Read-only** (`--plan <path> --format compact\|full\|json`, default `compact`): renders a plan's per-stage effective (declared+derived) grant set without touching session state — the planning-time research command a planner runs before submitting a plan, and the same generated block a planner-kind spawn's own prompt already references under "Prescribed research commands". `full`/`json` additionally break out each entry's provenance and any `dropped` derivation candidates that failed validation. |
| `stage-grants` | **Read-only** (`--session <sid> [--stage <n>] [--json]`): reports the flat EFFECTIVE grant set (declared + derived + unconsumed-runtime) for one stage of a live session, each entry self-labeling its own `provenance`. Derived entries are read from the approved plan **snapshot**, and only included if a fresh `grants_sha256` re-hash of that snapshot still matches `state.approved_grants_sha256` — a materialization-layer change since approval silently drops derived entries from the report rather than reporting a stale derivation as current. `--stage` defaults to the session's active stage. |
| `grant-stats` | **Read-only** (`--session <sid> [--json]`): reports `state.planning_misses` (with `planning_miss_counts: {asked, unasked}`), `state.materialization_defects`, `state.settings_drift`, and `state.cwd_drift` — the four-ledger view behind § `[stage.grants]`'s planning-miss / materialization-defect / drift distinction below. |
| `evidence-dir` | Create (idempotently) and print a stage's durable evidence directory (`--session <sid> --stage <n>`) — see § Durable evidence and checkpoint commits. No node change, no event log. |
| `plugin-activate` | Activate a registered plugin for this session (`--plugin <name>`); the owning skill calls it on invocation. See § Plugins. |
| `plugin-deactivate` | Manual escape hatch: deactivate an active plugin (`--plugin <name>`). |
| `plugin-record` | Mark a plugin phase done (`--plugin <name> --phase <…>`, e.g. `experience`'s `searched` / `recorded` / `skipped`; a `skipped` requires `--note`). Optional `--stage <n>` composes the `published_phases` key as `<phase>:<stage>` instead of the bare phase name — used by `tracker`'s per-stage journal gate (§ Plugins) so several `progress` entries, one per stage, don't collide under one key. |
| `ledger-add` | Declare or re-declare one claim in the active `ledger` bag (`--id --status axiom\|derivation\|assumption` plus `--source` / `--premise` (repeatable) / `--basis` / `--load-bearing`\|`--not-load-bearing`). ### Spine orchestrators (`drive` / `close`)

`drive` and `close` are **thin orchestrators**: they sequence the existing `cmd_*` commands above and branch on the `Directive` each returns — collapsing the ~15–20 hand-issued calls per task into two invocations (the [CLAUDE.md root principle](../../CLAUDE.md) *"Separate rule from perception; determinize the rule at its proper structural level"*, whose named canonical instance is this spine — the engine mechanizes the rule, the coordinator supplies the perception). They introduce **no new node, machine edge, or gate**: every state mutation is performed by a delegated `cmd_*`, so the engine's invariants hold by construction. Their one rule beyond sequencing is to **never auto-cross a human gate** — `drive` halts at `PLAN_READY` and `close` at `RESOLUTION` unless handed the explicit `--approved-by` / `--confirmed-by` token, which the coordinator may pass **only after** the real user-approval / confirmation round. Each returns the full step `trace` under `Directive.data`.

### Control attestation (`record-result --control`)

The **control criterion** (element #3 of the plan activity ontology) is a general property of *every* stage: how the result's conformance to the order is checked. `record-result` carries it as an optional general field, `--control <attestation>`, stored on the stage. It is mandatory in exactly one data-driven case: a stage whose **actor** (element #6) is `spawn:developer`. Recording such a stage PASSED without a non-empty `--control` is **refused** (a Directive, no node transition) — `Stage.needs_control()` is true iff the actor is `spawn:developer`, and the precondition lives in `cmd_record_result` as the single chokepoint where PASSED is set. `status=failed` and every non-developer stage (`in_thread`, other `spawn:*`) are unaffected, and `--control` stays optional-and-accepted on them (any stage may attest its control). Review is the value this control criterion takes for a delegated code producer — there is deliberately no review-specific command: the engine enforces the general structural fact, the specific content (reviewed by whom, or a waiver with its reason) is free-text cognition (**code = control-flow, prose = cognition**).

### Code-review gate (`code-review`)

A structured upgrade of *Control attestation* above, scoped to the same `Stage.needs_control()` condition (actor `spawn:developer`) but SUBSTANTIVE-only and independent of the free-text `--control` floor (the two never auto-satisfy each other — a stage recorded PASSED needs both). `code-review` is the **only** path that ever writes a `CodeReview` (stage_index, verdict, reviewer, concerns, note, `code_sha256`) — there is no automated judge for code review, unlike the acceptance path's cheap judge, since a code-reviewer/human verdict is the whole point. A `--code-ref` (if supplied, on both `code-review` and `record-result`) is hashed via the shared `_digest` helper and bound into `code_sha256`, never recomputed from git so `gates.py` stays pure; a `record-result --code-ref` that disagrees with the bound review's ref makes that review **stale** and re-blocks the pass.

`gates.code_review_blockers(state, stage, expected_code_sha256=...)` is a **pure** function reading only the recorded `CodeReview` — like `acceptance_review_blockers` it is an **internal command precondition, deliberately NOT a member of `gates.GUARDIANS`**, folded directly into `cmd_record_result` (before `verify_command` execution and the node transition, so a blocked pass never advances past `EXECUTING`). `AGENTCTL_CODE_REVIEW=1/0` force-enables/disables the gate; scoped to SUBSTANTIVE sessions by `gates.code_review_active`. A `verdict=override` clears only with a non-empty reviewer **and** note, mirroring `plan_review`/`acceptance_review`.

### Element-scoped invalidation

Before this, `Question.disposed_at_key` bound to `plan.stage_question_key(stage)` hashed over the stage's ENTIRE definition, so editing any one field of a stage invalidated every question ever raised against it, including ones the edit never touched. This gate is now element-scoped: `stage_question_key(stage, element=None)` takes an optional `element` (one of `text_shape.ELEMENT_NAMES`) and, when given, hashes only that element's own fields, tagged with the element's own name so two elements whose text happens to coincide never collide. `Question.target = "stage:<n>.<element>"` binds to the element digest instead of the whole-stage one; `question-rebind --confirm-still-valid` re-affirms either shape. Three element names (`order`, `requirements`, `control`) have no stage field of their own and keep falling back to the rest-of-stage definition.

Load-bearing: `verify_venue_at_final` is only ever hashed when a stage actually declares it, never as `... or ""` — an absent field must reproduce the pre-existing digest byte-for-byte or every live session's already-dispositioned question against that stage flips to a stale-key blocker. See [ADR-0006](../../docs/adr/0006-premise-invalidation-scope.md) invariant 1.

### Per-part enumeration keying

The enumeration cross-check (`question-enumerate`) used to re-read the whole plan on every call and stamp one composite `enumerated_at` digest, so a single-stage edit forced a full-plan re-run. The bag now carries per-part digests — one for the plan's meta/order and one per stage — compared via `plan.changed_parts(doc, baseline)`. `_apply_enumeration_result` upserts detected candidates under a deterministic `qenum-<part>-N` id (`part` is `meta` or `s<index>`), refreshing only the digests of the parts a pass actually covered; a stage nobody re-read stays recorded against the bytes it was read at, and its dispositioned candidates are untouched. `plugins_premise.enumeration_run_scope` narrows a re-run to just the moved stages only when a pass has already landed, the plan's meta is unchanged, and at least one stage moved — a meta move always widens back to the whole plan.

Load-bearing: a bag written before the per-part split carries no per-part baseline and can only be judged whole. `stale_enumeration_parts` falls back to comparing the single legacy composite digest (`plan.plan_content_digest`) against the whole-plan bytes: a match proves nothing moved and clears every part, but a mismatch cannot localize the change and so invalidates every part rather than guessing none did. The composite digest itself stays byte-compatible with its pre-split form so an escape, launch-window counter or already-persisted `enumerated_at` recorded before the split still matches. See [ADR-0006](../../docs/adr/0006-premise-invalidation-scope.md) invariants 2 and 3.

### Edit-scoped enumeration and carried dismissals

*Difficulty removed:* `enumeration_run_scope` used to narrow on `bag['enumerated']`, a flag `_launch_enumeration` clears back to `False` on every `submit-plan`/`replan` while leaving the per-part baseline exactly as the last landed pass wrote it — so a manual `question-enumerate` run in the window before the relaunched background worker lands widened to the whole plan for no reason the baseline didn't already answer. Separately, a coordinator's dismissal of a candidate was bound to that candidate's id, an id a later pass's part/index churn does not preserve — so a question the coordinator had already dismissed came back looking new, and a narrowed pass had no principled way to leave alone a question addressed to a stage it never re-read.

Narrowing is now gated on `plugins_premise.enumeration_baseline(bag)` — whether **any** per-part baseline is on record — not on the transient flag. A first pass, a pass after a meta/order move, or a bag with no baseline at all still reads the whole plan (`enumeration_run_scope` returns `(True, ...)`); only a pass with a landed baseline and moved stages, meta unchanged, narrows. `cmd_question_enumerate` and `_fold_enumeration_sidecar` both expose which branch fired as `scope_source ∈ {"whole_plan", "enumeration_baseline"}`.

On a narrowed pass, `_apply_enumeration_result` never upserts a pair whose target parses as a stage **outside** the parts just read — the pass has no standing to disposition a question about a stage it did not re-read. That pair is listed instead, in `EnumerationApplyResult.out_of_scope` (surfaced as `Directive.data["out_of_scope"]`), tagged `premise.CANDIDATE_OUT_OF_EDIT_SCOPE`, and re-evaluated fresh on every pass rather than carried forward — a plan-level or unparseable target is exempt and upserted as before, the same safe direction `_enumeration_part`/`_candidate_immateriality` already take.

Every genuine **coordinator** dismissal (`question-candidate-dispose --as dismissed`) records a content hash of the candidate's question text — `premise.dismissal_hash`, deliberately text-identity-only: it strips the `[target] ` address prefix, casefolds, collapses whitespace, and sha256s the rest, so two differently-worded questions never share a dismissal (the safe direction — a dismissal of one wording is not a dismissal of another). Stripping the address for HASHING does not mean the same text re-addressed to a *different* target is safe to auto-dismiss, so the record carries its **target** alongside the hash: `bag['dismissed_hashes'][hash]` is a list of `{reason, from_id, target}` records, one per target a coordinator has dismissed that exact text against, tolerant of a legacy/bare `{reason, from_id}` dict predating per-target tracking (read as target `None` — unknown). The field survives `_launch_enumeration`'s clear and loads as `{}` on an old bag with no such key. The engine's own automatic dismissals (immateriality) and out-of-scope listings never write here.

Any later pass — manual command or detached-worker fold, under any id or part — producing a candidate whose (text, target) pair matches a record here writes it `dismissed` with reason `"carried: <original reason> (from <from_id>)"` instead of freshly raising it — this is the SILENT carry, and it fires only when the recorded target is the *same* target the new candidate addresses. A same-hash record filed under a *different* target (or a legacy record with no target at all) never silently carries; instead the new candidate stays **open**, with its `reason` stamped by `premise.dismissal_hint_note` — `"similar to dismissed <id> for <target>: <reason>"` — a pointer for the coordinator to weigh, not a disposition. The two lookups share one call, `premise.dismissed_hash_lookup(dismissed_hashes, hash, target) -> (carry, hint)`, at most one non-`None`.

A silent carry is upserted via a 3-tier resolution in `_upsert_candidate`: (1) an existing row at the entry's own id with the same statement (ordinary in-place carry), unless that row is already `recorded` (never converted by a carry); (2) failing that, any existing `dismissed` row addressed to the *same* target whose own hash matches — reused under **its** id, so the carry can never overwrite an open candidate that happens to land on the same id/part/index slot, nor reach across to a same-text row addressed to a different target (that case is a hint, and never reaches this function); (3) failing both, a fresh non-colliding id. Disposing a candidate as anything other than `dismissed` — including via `--as recorded` — forgets its `(hash, target)` record (`premise.forget_dismissed_hash`) so a later pass does not keep silently carrying an overturned ruling; a legacy target-less record is dropped along with it once any dismissal for that hash is overturned, since it cannot be attributed to one target with confidence. `question-enumerate --reopen-dismissed` both skips the carry for one pass and forgets the record it would otherwise have carried (`honor_dismissed_hashes=False`), so the very next *ordinary* pass does not silently re-carry a dismissal the coordinator just reopened; the fold path always honors carry. `cmd_question_enumerate`'s and `_fold_enumeration_sidecar`'s `question_enumerate` log event records `scope_source`, `out_of_scope`, `carried`, and `carried_hint` counts alongside the existing fields.

Binding a dismissal to the plan *element* a question actually concerns, rather than to a target string plus this text hash, is a planned separate follow-up, not this one.

### Review scope and the coverage decision

By default `plan-review` binds a thinker's verdict to the whole plan. `--scope 'stage:<n>'` instead binds it to one stage's own current rendering, letting a large plan absorb a single-stage correction without re-reviewing everything the edit did not touch. `plan_review_blockers`' coverage half walks every stage that moved since the last whole-plan review and requires either that review still to be current, or a stage-scoped review recorded specifically against that stage's current bytes and not staled again since — a meta/order change can only ever be answered by a whole-plan review, never a stage-scoped one (see `stage.principle` at plan toml line ~625: "A review is a statement about what the reviewer read; binding it to the whole artifact when it read a part discards the coverage information the reviewer actually produced.").

`plan-review-delta` is the read-only pre-flight for this decision: it reports, without recording anything, whether a whole-plan review is needed or which stage indices need their own scoped pass, and hands back the actual current rendering of exactly the part that needs eyes — so a reviewer preparing to run `plan-review` never hand-computes this from a raw digest dump.

**Consumers of a moved interface.** The stage scope is the stages whose own review digest moved plus the direct consumers (`plan.consumers`) of every moved stage whose **interface** digest (`plan.stage_interface_digest`) moved: a consumer relied on the declared product, so a changed product is a changed reliance although the consumer's own key did not. A construction-only change (method, means) adds no consumer. `plan-review-delta` names such a stage as "consumer of N" and returns them under `data.consumer_of`. A review record keeps the per-stage interface digests it saw (`PlanReview.reviewed_interface_keys`); a record without them (written before they were kept, or built by hand) cannot show a moved stage's interface unchanged, so its consumers are in scope — the wider answer, never the narrower. A consumer's own `stage:<n>` pass stands for it only if it recorded each such supplier's interface as it is now. `gates.review_scope` computes this scope once: `plan-review-delta` reports it and the `approve`/`replan` blockers enforce it, so an interface move blocks until each consumer has such a pass.

**Pair currency follows the declared product.** When the pair bundle shows its service only as the declared product (a stage that relies on something and has a concrete interface — `plan.pair_shows_declared_product_only`), `pair_status` and `walk_stale_pairs` judge the service end by `service_interface` alone: its construction (`service_key`, `service_file`) is not in the evidence, so a construction-only change leaves the pair `current`. A source stage and an `interface_empty` stage are shown in full and keep all seven keys. A whole-plan record keeps the per-pair currency hash (`PlanReview.reviewed_pair_currency`); one without it falls back to the stricter seven-digest hash, so a construction-only change still marks its pair stale there; the record gains the narrower judgement once a new whole-plan review is recorded.

#### Pair scope — `--scope 'topo:<pair>'`

A third scope records a verdict about one **reliance edge**: a base `b` relying on a service `s` (`plan.review_pairs` lists them — `base-plan`, `plan-<s>`, `<n>-<s>`; ids from `plan.parse_pair`, which refuses an unknown or unit-form id). The record is a `PlanPairReview` in `state.plan_pair_reviews[<pair>]`, bound to the seven digests of `plan.pair_binding` (context, edge, both node keys, both node files, the service's interface). It is a separate store: a pair record never touches `plan_review`, `plan_review_passes`, `plan_stage_reviews` or `plan_review_rounds`. `plan_review_blockers` reads it only through `pair_status`: once a plan has any pair record, every moved stage's obligation since the whole-plan review is discharged when every pair of the walk-stale set (`gates.walk_stale_pairs`) is `current` or `override`, and each uncovered pair of that set that no `stage:<n>` pass covers is a blocker naming it. `gates.pair_status(state, doc, plan_path, pair)` is the single currency function — `missing`, `stale:<key>` (the first mismatching digest in `state.PAIR_BINDING_KEYS` order, named without its `_digest`/`_key` suffix: context, edge, base, base_file, service, service_interface, service_file), `current`, `override` or `revise`.

A `pass` must carry `--plan-digest` equal to the sha256 of a fresh load of the target, so a stale verdict is refused at write time. A `revise` over a still-current same-pair `pass` is a PAIR OVERTURN and needs `--regression-command` run by the engine in `state.repo_root` and exiting non-zero; a prior whole-plan pass is ignored. An `override` needs a non-empty `--note` and passes the same refusal check as a whole-plan override (`_plan_review_override_refusal`): a reviewer distinct from the prior `revise`'s, `agent` only while the review-round or cross-axis friction release is active, and — when the order declares a `customer_id` — that customer as the reviewer. `--concern-id`, `--findings-blocking` and `--findings-nonblocking` are refused on a pair scope rather than silently dropped. Every `revise` concern opening with the condition-4 marker (`C4:`) appends a `confirmed-gap` line to the escalation ledger (`~/.local/log/claude-plan-review-escalations.jsonl`, override `AGENTCTL_ESCALATION_LEDGER`; fail-open); an `override` of that `revise` appends a `false-alarm` line per such concern.

#### Topological review — the review route of a SPAWN-route plan

*Difficulty removed:* a plan whose rendering exceeds the whole-plan spawn ceiling cannot be reviewed by one thinker, and a reviewer that must hold the whole plan cannot attribute a verdict to anything smaller than the plan. The topological route replaces "one reader holds the plan" with local checks on each reliance edge.

**Route split.** On a session whose route is SPAWN (`gates.pairwise_review_route`) pairwise review is the only review route: the `submit_plan` directive and the missing-review blocker name `plan-review-topological.py` followed by `plan-review-compose`, and no whole-plan spawn is offered. On any other route (inline) the directive keeps the whole-plan thinker review recorded with `plan-review`. Both routes end in the same gate, `gates.plan_review_blockers`.

**Pairs.** A pair is a base `b` relying on a service `s`; `b` is judged against the *declared product* of `s`, never against `s`'s construction. Two synthetic nodes make the plan itself a participant: the **plan** node (the plan's own `[meta]`; it is the base of the `plan-<s>` pairs, relying on the sinks and coverage-named stages) and the **base** node (the order text, `[meta.order]`, rendered from `base.md`). The order is an ordinary pair, `base-plan`: the reconstructed base activity relies on the plan. Its condition 3 reads "not applicable" since the base delivers no product of its own.

**Four conditions per pair** (`plan.CONDITION_MARKERS`, `C1:`..`C4:`; the wording is per pair kind, `render._pair_conditions`): C1 every need of the base is attributed to a declared edge, i.e. it is organized in a non-arbitrary way; C2 the base is a genuine derivation from the order through this edge; C3 the base delivers its full declared product, the part that depends on the service measured against the service's declared product; C4 the service's declared product covers the part of the base attributed to this edge. An undeclared need of `b` is a C1 "declare the edge" concern; a C4 concern is an ordinary `revise`.

**Pull-based starting prompt.** `spawn-specialist.py --review-topo <pair>` (with `--kind thinker`; one pair per spawn, a comma list is refused) builds the prompt with `render.render_pair_review_bundle`: order context, the base's full node file, the service's declared product, the edge, the `Plan digest:` line, the per-pair procedure and the protocol. The service's *full* node file is not inlined; it is one `Read` away in the per-version **view directory** `<topo root>/<plan_sha256>/view-<pair>/` (topo root `$AGENTCTL_TOPO_UNITS_DIR` or `lib.config_root.agentctl_topo_units_dir()`), which holds exactly that one file and is the only path the pair reviewer may read. Prompt size therefore does not grow with fan-in. The pair reviewer echoes the spawner-rendered `Plan digest:` line instead of computing one.

**The walk.** `plan-review-walk [--target <plan>] [--format json]` (read-only) lists every pair in dependency order, base before service; a pair's *level* is its base's depth, because a revise at a shallower pair edits the brief a deeper pair reads. Each row carries `status` (`gates.pair_status`), advisory `ready`/`waiting` (the base's own prerequisites not yet satisfied) and the `spawn` and `record` commands. Readiness orders the work; it never gates it.

**Reviewer memory.** `plan-review-pair-history --session <sid> --pair <pair> [--target <plan>]` (read-only; never a user-authority verb) prints `{pair, records, changed_parts_since_last}`: every recorded review of the pair against the target (`record_seq`, `plan_sha256`, `reviewer_verdict`, `effective_verdict`, and per concern its stable `id`, raw `severity`, `effective_severity`, `parts`, `text` and whether it is still an `unresolved` blocker), plus the pair's own parts whose digest differs from the latest record's (all of them when the record stored none). The driver calls it before spawning a pair whose walk status is not `missing`, writes the payload to a temp file and passes `--review-topo-history <file>` to `spawn-specialist.py` (only when records exist; the flag is refused without `--review-topo`; the spawn stays session-free). A record taken before events carried `concern_ids` is recovered from the concern ledger: only entries raised against the target plan count, and an event with no `record_seq` takes the ledger group whose concern texts equal its own, never one by position; when none matches its texts are rendered under `(not in the concern ledger)` without ids. If the verb fails the driver prints `TOPO-HISTORY-UNAVAILABLE` and reviews the pair without history. `render_pair_review_bundle(..., history=...)` then adds `## Prior review of this pair` and `## Changed since the prior verdict` and a protocol bullet: block only on a changed part, or on a part still carrying an unresolved blocker listed under the prior review, re-raised as `re:<id>`. Without history the bundle is the first-review rendering, byte for byte (`scripts/tests/fixtures/pair_bundle_golden/`).

**Severity tags.** Every concern a pair reviewer writes is `blocking: [re:<id>] <C1:..C4:> <text>` or `note: ...`; an untagged concern is refused by `plan-review --concern` on any verdict and by the driver on a `revise` (the driver ignores untagged lines on a `pass`), and `blocking:` on a `pass` is refused. Each concern gets a stable ledger id (`<pair>#<seq>.c<i>`) and each record stores per-part digests. A blocking concern holds the pair in `revise` only when its part changed since the pair's previous record, or when the part still carries an undischarged earlier blocker (not fixed by an edit, not risk-accepted, not followed by a `pass` on the same scope). Otherwise it is recorded as advisory; a `re:<id>` restatement of an already dispositioned concern is advisory unless it carries a new `--regression-command`, and `re:<unknown id>` is refused. A `revise` whose concerns are all notes or advisory composes as a `pass` and leaves the pair current.

**The driver.** `scripts/plan-review-topological.py --session <sid> --plan <plan.toml>` runs the walk level by level: it re-reads the walk before each level, spawns one pair reviewer per open pair of the level (ready or not, since a pair's prerequisites do not gate its own review; under `--early-stop` only ready pairs, the rest print `TOPO-WAITING`), records the results in walk order, parses the `REVIEW:` reply (`Verdict:`, `Plan digest:`, condition-prefixed concerns), and records it with `plan-review --scope topo:<pair>`. No pair is spawned twice per run and no level starts before the previous one returns. Pairs of one level run concurrently by default (`--parallel` defaults to the level's batch width, capped by the `review-parallel-max` config key; an explicit `--parallel N` wins, `--parallel 1` is sequential; a missing key means sequential): a level's pairs share no input another pair of that level produces, so concurrency changes only wall-clock. The driver continues past a level containing a `revise` or a refusal and reviews every open pair, because per-pair digest binding keeps a deeper review current across later edits of other parts, so an early stop only discards it; `--early-stop` opts into the stop, and `--no-early-stop` stays accepted as a no-op alias. It judges nothing: order, readiness, currency and composition stay with `agentctl`, and the only text it parses is the fixed protocol tokens. A pair that cannot be recorded (pre-spawn ceiling, unparseable reply, digest mismatch, ambiguous cost row, engine refusal) prints `TOPO-REFUSED` and is left unrecorded. Other lines: `TOPO-PAIR` (verdict, digest, cost, duration, pulls), `TOPO-CURRENT`, `TOPO-HISTORY-UNAVAILABLE`, `TOPO-WAITING` (only under `--early-stop`), `TOPO-DRY` (`--dry-run` prints the prompt size and view files per pair without spawning). Exit codes: **0** composed pass or a scoped run whose pairs passed, **1** blocked (a revise, stale, missing or waiting pair remains), **2** any `TOPO-REFUSED` in the run or a usage error, **3** nothing to review.

**Scoped and whole-plan pairwise runs share one driver.** `--pairs <p,...>` restricts the run to named pairs in walk order; `plan-review-delta` names the walk-stale set (`gates.walk_stale_pairs`) to pass it. When every pair of the walk-stale set is `current` or `override`, the moved stages' `stage:<n>` obligations are discharged (`gates.pair_discharged_stages`, shown as "discharged by pairs alone" in the walk) — all or none. **The scoped run's blind spot:** it requires current only the walk-stale pairs, so a defect living in a pair outside that set (one whose bound digests did not move) is not looked at; only a full run, in which `plan-review-compose` requires every pair, covers it.

**Compose.** `plan-review-compose [--target <plan>]` writes one ordinary whole-plan `pass` (reviewer `topological-composition`) only when *every* pair of `plan.review_pairs` is `current` or `override` against the live plan bytes; otherwise it refuses with `data.failing`, a pair → status map. `gates.autonomy_boundary` counts the record as the first thinker verdict when it was composed with no `override` pair (the condition is "no override pair", the same as for a whole-plan record, not the reviewer's kind); a compose containing an override pair is not one. Compose never advances `review_rounds` (§ Review-round budget); the pair records already counted the version. The driver runs compose as its last step and prints `COMPOSE: pass` or `COMPOSE: blocked <pairs>`; on a scoped run with open pairs it prints `COMPOSE: skipped scoped run; not current: ...`.

**`TOPO-SUMMARY`.** One closing line with per-run totals: pairs, summed cost, duration and the pull counts (reads of the view directory, counted from the child's transcript; each `tool_use` once). It is telemetry, not a gate: an unknown cost or pull count prints `NA` and is counted as unknown, never as 0 (the cost comes from the spawn-cost log, matched by transcript path and otherwise by `review_pair` + `plan_sha256`; more than one candidate row is an ambiguity refusal). The pull volume is what a deferred pull-skipping optimization would be decided from.

**The condition-4 gap ledger** (`~/.local/log/claude-plan-review-escalations.jsonl`, override `AGENTCTL_ESCALATION_LEDGER`) counts how often a service's declared product was too thin to decide a pair: a `C4:` concern recorded by a `revise` is a `confirmed-gap` line, and an `override` of it a `false-alarm` line, keyed by session, plan path and pair id. Its rate is the detector for the residual below.

**Residual K1.** The induction covers only couplings expressed as reliance edges (`depends_on`, `supplies`). A coupling expressed in neither — an undeclared shared resource, an ordering side effect between stages with no reliance path — passes every pair while the plan fails, and so does a defect visible only across two edges at once (two services of one base whose conflict neither pair's context shows). C1's "declare the edge" obligation and C4's "enrich the interface" mitigate it; the gap ledger measures how often it happens. It is a named residual, not a closed case.

### StageNorm — the stage's norm and its three identities

`scripts/agentctl/stage_norm.py`'s `StageNorm` is one stage's norm as plain data: the same object a spawned specialist (a depth n+1 manager) receives as its order. `to_dict` / `from_dict` round-trip it through JSON. It replaces three hand-maintained field lists that each claimed "this stage's norm changed" with three projections of one object ([ADR-0007](../../docs/adr/0007-stage-norm.md)); `plan.stage_carry_key` and `plan.stage_interface_digest` delegate to it.

| Identity | Covers | Decides |
|---|---|---|
| `review_digest` | the whole stage as a reviewer saw it; byte-identical to `plan.stage_question_key(stage)` (persisted in `Question.disposed_at_key`, so its payload may not drift) | which stages moved since a review |
| `interface_digest` | what a consumer relies on: title, result image, criterion, `output_artifacts` (a stage with a blank interface falls back to its rendered brief) | whether a stage's consumers are affected |
| `carry_digest` | the stage's definition with its edges as sorted `(on, element, artifact, delivery)` tuples in place of the bare `depends_on` slot | whether a PASSED verdict survives |

**Carry rule.** `stage_norm.stage_carried(prev, new, index)`: a PASSED stage keeps its outcome iff its own `carry_digest` is unchanged and every direct supplier's `interface_digest` is unchanged; otherwise it is reset to PENDING. A supplier missing on either side counts as changed; a supplier whose only change is construction (method, means, procedure) carries its consumers. Both carry sites call it before mutating the live stages: the `approve`-time refresh and the substantive `replan`. Retyping an edge (element, artifact or delivery) at an unchanged supplier index moves the `carry_digest`, which the former index-only key missed.

**Review-scope rule.** `gates.review_scope` computes what a refinement owes review: the stages whose `review_digest` moved, plus the direct consumers of every moved stage whose `interface_digest` also moved. `plan-review-delta` reports it and the `plan_review_blockers` enforce it. A review baseline recorded before interface digests were kept cannot show an interface unchanged, so it widens the scope to the consumers, never narrows it. A consumer pair's currency and `walk_stale_pairs`' service-end staleness follow the service's declared product (`interface_digest`), not `service_key` / `service_file`.

**Edge delivery.** Every edge in a new substantive plan names `element` (a bare edge is refused by `submit-plan`, naming the edge and what to add; legacy plans still load). An edge may also name how its provision arrives with `delivery`, optional, one of:

- `artifact` — a named file; needs `artifact = "<path>"` naming one of the supplier's `output_artifacts` entries, else `submit-plan` refuses.
- `continuation` — the consumer continues the supplier's working copy and branch; the supplier must be a `spawn` stage.
- `report` — an inline or summary hand-off with no file or tree dependency.

An unknown value is a `PlanError` at load. `delivery` joins `review_digest` only as a trailing splice when some edge declares one, so legacy plans hash identically. `cli._continuation_worktree` decides per edge: a `spawn` dependency is continued if any edge to it says `continuation` or says nothing (the `depends_on` inference, unchanged for edges without `delivery`); an explicit `artifact` or `report` edge stops the continuation.

**Limits.** Stage identity is the index: a plan that renumbers stages resets them. A `restructure` pair verdict (revising plan structure through pair review, Core #319) is not implemented; the structure-change test stays in `plan._structural_signature`, and `StageNorm` keeps the edge list as data for a future changed-structure-only review.

### Accepted risks (`risk-accept`)

A `revise`-verdict concern that the plan's author judges an acceptable trade-off previously had no way to clear the plan-review gate short of a cosmetic edit that satisfied nothing but the digest check. `risk-accept` records a `RiskAcceptance` (mirroring `question-dispose --disposition assumed`'s basis/risk shape) bound to the same `(scope, concern_id)` pair a `plan-review --verdict revise --concern` recorded, plus a snapshot of the plan bytes as they stand at the moment the acceptance is recorded. `_plan_review_verdict_blockers` discharges a `revise` verdict once every one of its concerns is matched by a live acceptance — `gates._risk_acceptance_stale` re-derives staleness the same way a review at that scope would (a moved order/meta always invalidates; a moved stage invalidates only an acceptance scoped to that stage), and `_risk_acceptance_superseded` separately catches a concern id that survived a plan edit but whose recorded text no longer matches what was actually accepted. Every live acceptance appears in the coverage block the presented essence must carry, checked by the same containment machinery that already checks the order-coverage block (§ Plugins), so the trade is visible at the approval gate rather than buried.

### Review-round budget

Nothing previously capped how many review-then-revise cycles a plan could churn through. `state.plan_review_rounds` counts them on **both** loops, advanced only while a review actually happened (never re-derived from records still on file, since a re-derivation would misread a stage-scoped review staled by the same edit that answered it as "no review happened"):

- **before approval** — `cmd_submit_plan` counts each `PLAN_READY` resubmission made while a review record stands; the count resets at `approve`.
- **after approval** — `cmd_plan_review` (and, for a pairwise review, `cmd_plan_review_compose`) counts each plan **version** reviewed, i.e. the `replan` loop, which is where review cycles overwhelmingly recur; the count and its marker reset at `replan` (`--renormalize` is excluded: by its own contract it changes no norm and demands no review, so the rounds already spent still belong to the same norm).

The two sites are disjoint by construction, not convention: `cmd_submit_plan` sets `approval.passed = False` before its own increment, so no single call satisfies both conditions.

The post-approval unit is a plan **version**, keyed on `state.plan_review_counted_digest` (the sha256 of the counted plan bytes, computed by the same `_plan_file_sha256` that validates a reviewer's `--plan-digest`), and deliberately not a recorded verdict: `_plan_review_blockers_coverage` surfaces one uncovered stage at a time, so an honest first coverage pass over a multi-stage plan records several stage-scoped verdicts against identical bytes. Counting verdicts would fire the release part-way through that pass — and since the release **substitutes** the blocker list rather than adding to it, a still-outstanding "stage *i* needs its own pass" would be replaced by "no further review is required". For the same reason an unreadable plan does **not** count and leaves the marker untouched: over-counting can retire a review nobody performed, while under-counting only leaves the user's one-sentence override as the exit. `cmd_push_subplan`/`cmd_pop_subplan` hold both fields under `PlanFrame` custody, so a service sub-plan neither spends nor inherits the parent's budget — which is why the counter's monotonicity is scoped to one plan-stack level.

`gates.plan_review_round_release_active(state, thr)` fires once the count reaches `effort-replan-absolute` (config.md's threshold, reused rather than duplicated) — past that point `plan_review_blockers` stops demanding another review pass and substitutes a fixed message naming the two decisions the exhausted budget hands to a recorded decision-maker, never the engine: go ahead as-is (`plan-review --verdict override --reviewer <you> --note <why>`; the coordinator's own `--reviewer agent` override is disclosed, § Autonomous replanning within the approved boundary) or cut scope and re-apply the plan by the route the current state allows (`submit-plan` before approval, `replan --plan <edited>` after it), which does not itself refill the budget or open the gate. Every command whose refusal can carry the release — `approve`, `plan-review`, `replan` — surfaces it as `data["plan_review_round_release"] = {"rounds": n}` and logs the `plan_review_round_release` event once per round value, via the shared `cli._note_round_release`; a `replan` refused under an active release stops naming a thinker review as the fix, since that is the very act the release just retired.

**`review_rounds` — the task-level counter.** `plan_review_rounds` resets at `approve` and `replan`, so a task that reviews many plan versions never reached the release. `review_rounds` (a `task_accumulator` axis, mirrored onto the session when it is loaded) is never reset by `approve` or an ordinary `replan` (only `replan --renegotiation-decision continue|rescope` zeroes it, with the rest of the task accumulator) and is shared by every session of the same task. It advances by one per plan version reviewed pairwise (the first pair record on a new `plan_sha256`; further pair records on that digest add nothing) and by one per whole-plan or stage thinker record; a second session on the same task does not count the digest the task counted last. The release reads `max(plan_review_rounds, review_rounds)` (`gates._PLAN_REVIEW_ROUND_COUNTER`) against `effort-replan-absolute` and, once active, stays active after a later ordinary `replan`. The history events `submit_plan`, `plan_pair_review`, `replan` and `verify_final` carry an ISO-8601 UTC `ts`; events written before this field stay without one.

**Topological review and the budget.** A pair record (§ Review scope, topological review) touches neither `plan_review` nor `plan_review_rounds`: reviewing N pairs spends no `plan_review_rounds` round. The task-level counter `review_rounds` (above) is advanced by the pair records themselves, once per plan digest, not by `plan-review-compose`. After approval, however, `cmd_plan_review_compose` still calls `_count_plan_review_round`, so compose advances `plan_review_rounds` once per plan version; pair records advance `review_rounds`. When the release is active, the whole-plan spawn ceiling and the exhausted budget are separate matters: the ceiling is answered by the topological route, the budget by the recorded decision above.

### Terminal pass and regression evidence

*Difficulty removed:* the round budget above caps churn once it has already happened, but did nothing to stop the commonest shape of churn in the first place — a `pass`, then an unevidenced `revise` on the very next round, re-litigating a concern the reviewer could have raised the first time, over and over, because nothing distinguished "new information" from "re-reading with a different mood".

Once an attested `pass` (a non-empty `plan_sha256`) is recorded for a scope — whole-plan (`""`) or `stage:<n>` — within the current approval cycle, `state.plan_review_passes[scope]` remembers it as **history**, independent of whatever verdict is recorded next; only `approve` and `replan` clear it, starting a fresh cycle (a resubmission at `PLAN_READY` does not — see `cmd_submit_plan`'s staleness clear on `state.plan_review`/`plan_stage_reviews`, which is the *current-record* mechanism and orthogonal to this history). `gates.plan_review_prior_pass(state, scope, target)` looks it up, binding across a path rename the same way an ordinary review does (`_binds_across_path_change`). **The rule is not limited to the scope that was actually passed**: a stage scope carrying no pass of its own falls back to the whole-plan pass (`scope == ""`) — a whole-plan PASS already covered every stage, so a stage-scoped `revise` afterward is bound by the same terminal rule, not a loophole that reopens the gate a scope-hop away from where the pass landed.

A `revise` recorded for a scope while a prior pass binds it (its own, or the whole-plan fallback above) is a **post-pass revise**. It only overturns the pass — reopening `state.plan_review`/`plan_stage_reviews[scope]` and re-arming the gate — when `gates._plan_review_regression_evidence` finds **both**: (1) `--regression-command <cmd>`, actually run by the engine in `state.repo_root` via the same `_run_check` seam `verify_command` uses, exiting **non-zero** (a command that was never supplied, or that exits 0, is refused as evidence — a green check proves nothing broke); and (2) at least one `--concern` whose text opens with a structural token match (`gates._concern_names_part` — not a semantic classification, since `meta:`/`order:`/`stage:<n>` are the engine's own vocabulary, anchored at the start of the concern exactly like the `cut:`/`add:` remedy prefix below), naming a part that `plan.changed_parts(doc, <the pass's own recorded baseline>)` reports as changed since that pass.

Without both, the `revise` does **not** touch `state.plan_review_passes` — the prior pass stays on file and `gates.plan_review_prior_pass` keeps finding it — and is instead logged as `plan_review_post_pass_unevidenced` and returned as a non-blocking `continue` Directive that surfaces the concern text verbatim and names the two exits: `plan-review --verdict override --reviewer <you> --note <why>`, or edit the plan the way the concern proposes. Whether `state.plan_review`/`plan_stage_reviews[scope]` — the *current-record* the coverage check reads — is itself overwritten with this revise is conditional (`gates.plan_review_scope_moved_since_pass`): only when this scope's own part actually moved since the pass, because that is the one case `_plan_review_blockers_coverage` will go looking for a record at this scope next — an unmoved scope leaves the prior pass as the sole record there, nothing to overwrite. That matters for `risk-accept`/`override` at this scope: without a record there, a later attempt to discharge or override this concern finds nothing to bind to. And "keeps the gate clear" is re-verified, not assumed either way: `gates.plan_review_blockers(state, target)` is recomputed after the note is logged, because the plan may have been edited since the pass (independent of this revise) and stale its coverage on its own terms (`_plan_review_blockers_coverage`). When those real blockers are non-empty, `cmd_plan_review` returns `ok=False` with them instead of `continue` — reporting a stale pass as "in force" would silently swallow a re-run review inside a note nobody reads as a refusal. Either way the decision is the user's, not another thinker round. Once any pass has been recorded this cycle, `_PLAN_REVIEW_ROUND_RELEASE_MESSAGE_POST_PASS` replaces the ordinary round-release message and no longer offers "run a fresh whole-plan thinker review" as an exit — an on-budget pass would have cleared the gate directly, so reaching the release message at all means a pass already stands and re-reviewing the same ground is not the fix; its second exit is phrased the same way as above — edit the plan as the concern proposes (cut or add), never a default remedy.

Each `--concern` may carry a leading `cut:` or `add:` remedy tag (`gates._remedy_tag_for_concern`), parsed as a reviewer-typed protocol token rather than free-text meaning, and logged as `remedy_cut`/`remedy_add` counts on the `plan_review` event — descriptive of the reviewer's own suggested remedy, with no engine-side preference between the two. An `override` still requires a reviewer distinct from the one who blocked, and — when the plan names an order customer — the order's `customer_id`, unchanged by any of the above.

### Renormalization (`replan --renormalize`)

*Difficulty removed:* a plan that carries only one "how" field makes every deviation by the executing actor a deviation from the norm, so the executor cannot select its own operations without a replan — and a replan is gated on the user. Selection, element 4' of the activity ontology, becomes structurally unavailable.

`Means` therefore carries two fields, not one. `method` is the **requirement** on the way of acting — what the transformation must be an instance of — and moves only through the ordinary approval-gated routes. `procedure` is the **sequence of operations** proposed for meeting it; it is the executor's, and `replan --renormalize` is how the executor replaces it without a user gate. Both are required of a substantive stage **at submission** (never at parse: the submission-seam-only rule, so frozen corpus plans keep loading byte-for-byte), and `submission_violations` additionally refuses a stage whose two fields say the same thing — in [`procedure.py`](procedure.py), built on the same prefilter-plus-fail-open-judge pattern as `conditions.py` and never on normalized string equality, which was measured catching 0 of 200 corpus stages. Fail-open is inherited honestly: with no advisor reachable, this refusal never fires, and the structural half (the fields existing, both required, the branch refusing the requirement) is what holds unconditionally.

The branch (`cli._renormalize_replan`) diffs the offered plan against the **approved snapshot**, not `plan_path`, so successive renormalizations cannot walk to a norm edit in small steps. `gates.renormalization_blockers` refuses it in two layers: a NAMED list — `means.method`, `means.means`, the result image, and every criterion field including `verify_command`/`verify_venue`/`expected_exit` — which supplies the message; and **two residual totality checks**, one per side. Per stage (`gates._renorm_stage_residual`): transplant only `means.procedure` onto a deep copy of the old stage and require equality of `plan.stage_question_key` **plus `cost_tier` plus `output_artifacts`** — the two engine-consumed fields outside that key, which is scoped to what a `Question.target` may name. Per plan (`gates._meta_place`): equality over **every** field of `PlanMeta`, `weight_class` (the grade the approval spine keys on) included. Both are hand-written membership lists and both are pinned by a test that goes red when a field is added and left out, because a totality claim no code establishes is not one. Stage-set changes, `[meta]` goal/done_criterion/repo_root/delivery_worktree, `[meta.order]` and the final-check surface each carry their own named refusal on top.

Accepted, it copies **only** `means.procedure` onto the live stages — no `_apply_refined_stage_fields`, so no recorded `Outcome`, observation or PASSED status is disturbed — re-stamps `accepted_plan_digest`, and logs the history event as `renormalize`, deliberately **not** `replan`: `effort.replan_count` counts `replan` events, and routine executor autonomy must not feed the divergence trigger at `effort-replan-absolute`. It does not re-arm the approval gate and does not leave `DIAGNOSING`.

### Re-norming outside a difficulty and plan-version content

*Difficulty removed:* `gates.normalization_blockers` (the normalize-or-waiver gate, distinct from § Renormalization's own gate) only ever runs inside a completed `DIAGNOSING` cycle, so a reproducible cause noticed in the ordinary course of work — outside any difficulty, or a normalize recorded in the same breath as an unrelated replan — had no record at all, and a submitted-but-never-approved plan version (a rejected proposal, a refinement nobody kept) left no trace a later `plan_sha256` could resolve to. Widen, don't fork: `normalize` keeps one event name with an `in_diagnosis` flag so every existing reader sees both flavors; snapshots reuse the content-addressed writer; counts are derived from `state.history`, not new mutable state. No new gate — recording is optional and cheap by construction (REQ11): a replan with nothing reproducible to re-norm is a completely ordinary replan, and its absence never refuses anything.

**`normalize` outside `DIAGNOSING`.** `cmd_normalize` now dispatches on `state.node` *before* any of its own validation: a `DIAGNOSING` call reaches the exact original code path (`_require_diagnosing` → completeness check → shared `_normalize_record_fields` validation → sets `state.difficulty.normalization` → shared `_log_normalize_event` with no `in_diagnosis` key at all), while any other node except `RESOLVED` reaches `_cmd_normalize_outside_diagnosing` — the same shared validation, but logging via `_log_normalize_event(..., in_diagnosis=False)` and returning `Directive(True, state.node, "continue", ...)` without touching `state.difficulty` (there is none to touch outside a difficulty cycle); `RESOLVED` is refused outright (a record filed after `resolve` never reaches the quality row). Both branches share the same two helpers, so validation and event shape can never diverge between them.

`replan --normalize-factor <cause> [--normalize-level <level>]` records a normalize act in the SAME `replan` call. Validated immediately (cheap, no state touched) so a bad flag refuses before any of `cmd_replan`'s own gates run — but deliberately WITHOUT staging anything onto `state.difficulty.normalization` yet: this command saves state at more than one point ahead of later refusals (the enumeration-bag fold, the stale-disposition invalidation), and an early mutation would ride one of those saves onto disk as an orphaned record with no matching event if a later gate then refused the replan. **In `DIAGNOSING`**, `gates.normalization_blockers` instead takes the pending factor as an explicit argument, so it is satisfied by the ARGUMENT rather than by state this command hasn't written — the replan is not refused for a factor it was just given, and nothing is persisted for a refusal to leave behind. **Both the record and the event are deferred to the same single point**, past every refusal gate including the critique-coverage gate (strictly after the plan-version snapshots, which are themselves taken past most but not all of the refusals): `state.difficulty.normalization` is set (in `DIAGNOSING`) and the event is logged together, so a refused-then-retried call neither inflates `n_normalizations` with a duplicate nor leaves an orphaned record for the retry to silently skip. `--normalize-factor` and `--renormalize` are refused together (a renormalization by contract touches no norm).

**Plan-version content-addressing.** `_write_plan_snapshot`/`_snapshot_approved_plan` (§ above, `plan-approved-{digest[:16]}.toml`) cover only the **approved** plan. `_write_plan_version_snapshot`/`_snapshot_plan_version` are their parallel, distinct-prefix siblings (`plan-version-{digest[:16]}.toml`, beside the session's state file) covering **every** submitted plan version — `submit_plan`, and all three `replan` kinds (`no_change`, `refinement`, `substantive`), plus `--renormalize` — content-hash-named so an identical resubmission shares one file. The `submit_plan` history event carries `plan_sha256`; every `replan`/`renormalize` event carries both `prev_plan_sha256` (the baseline it replanned from) and `plan_sha256` (the plan it applied), each resolvable to an actual file on disk.

**Quality-row counts and the scorecard.** `resolve`'s quality row adds `n_normalizations` (every `normalize` event), `n_normalizations_outside_diagnosis` (the subset with `in_diagnosis is False`), and `n_renormalize_replans` (every `renormalize` event) — all derived from `state.history`, so an older row predating these fields simply lacks the keys rather than being wrong. `policy-scorecard.py`'s `## Re-norming` section reports coverage (share of the window's rated rows with `n_normalizations >= 1`) and the quality mean split with-vs-without a recorded normalization, treating a missing `n_normalizations` as `0` so an old row still loads and counts toward the denominator instead of raising or being silently dropped.

### Replan authorization

*Difficulty removed:* an approved plan could be edited without the user any time up to the moment a genuine difficulty legitimately required it — not only executed silently after a byte edit (§ Check venue's whole charter), but *changed* silently, because `replan`'s two ordinary outcomes (refinement retries the re-armed stage; substantive re-arms `PLAN_READY`) both apply the corrected plan **before** any approval-shaped gate has seen it, and a refinement never re-arms one at all. `replan_authorization_blockers` (`gates.py`) is the write-side twin of `plan_presentation_blockers`: an approved plan must not change under the user's feet any more than it must not execute under a stale reading of itself.

**What it blocks.** Applying a `refinement` or `no_change` diff to an already-`APPROVED`-or-later plan, outside a complete `DIAGNOSING` difficulty cycle. `cmd_replan` computes `diff_kind` against the approved snapshot exactly once and feeds the same value to both this gate and its own refinement/substantive branch, so the gate can never reason about a different edit than the one about to be applied.

**The three exemptions**, each because the edit is either already governed elsewhere or has nothing left to authorize — never because the edit is safe by nature:

1. **The DIAGNOSING carve-out** — `state.node == DIAGNOSING` AND `difficulty_blockers(state) == []` (the `Difficulty` record is complete: `declare` → `investigate` → `critique` all filled). This is the ORDER's own sanctioned repair path: CLAUDE.md requires the coordinator to run exactly that three-step cycle before a corrected plan may be authored at all (`hook-state-gate.py`'s `diagnosing_plan_write_ok` already gates the edit on it), and the completed record is itself the user-ordered authorization — there is no *separate* user act at this specific gate, and the docs must say so plainly rather than imply one. The carve-out is fully self-attestable: the coordinator's own `critique` call is what flips `difficulty_blockers` to `[]`. What still stands between a spurious "difficulty" and an unauthorized edit is the rest of the difficulty-record discipline (declare/investigate/critique each demanding real content, the resolution-gate's later conformance check) — not this gate.
2. **The substantive-diff exemption** — `diff_kind == "substantive"` (an executor or done-criterion change). Already re-arms the full plan-approval gate (`node → PLAN_READY`, `approval.passed = False`), which demands its own present → deliver → approve cycle before anything executes; gating it here too would be the same obligation twice.
3. **The byte-identical exemption** — the proposed plan's current sha256 equals `state.accepted_plan_digest`. Nothing changed, so nothing needs authorizing. An unreadable proposed file does **not** take this exemption (fail-closed): a read failure is evidence of nothing, and the digest comparison must never default to "same".

Outside these three, `replan` refuses with `present_plan` naming the missing step, exactly mirroring `plan_presentation_blockers`'s shape.

**The present → final-message → ask cycle.** `present-plan --kind replan_diff --plan <candidate>` renders the proposed diff and stamps a `PlanPresentation` receipt bound to the candidate's exact bytes (`plan_sha256`) and the exact rendered text (`rendering_sha256`) — a third `PlanPresentationKind` alongside `essence`/`full`, but keyed for supersession by **kind alone** (`_SUPERSEDE_BY_KIND_ALONE`), not `(plan_path, kind)`: unlike essence/full, which always present the session's one live `plan_path`, a `replan_diff` receipt is presented against whatever `--plan` names, which varies across replan attempts, so only the most recent proposed-diff receipt is ever current. Presenting alone does not authorize anything — the delivery half still requires proof the rendering actually reached the user. `hook-plan-delivery-gate.py` carries a **second, independent** certificate path for this: an `AskUserQuestion` whose options include the literal marker `[authorize-replan]` (`AUTHORIZE_REPLAN_MARKER`) triggers the stamp, checked by the cheap, I/O-free `_has_marker_option` **first** — an ordinary ask carrying no such option (every ask in every other session) reaches no state load and no transcript scan at all, the same cost invariant the essence path already holds. Only past that marker does the hook load state, look up the live `replan_diff` receipt, and stamp it — but only when the rendering was delivered as the **final** message of a turn that has already **completed** before the marked ask fires (the same completed-turn requirement `[[ask-user-question-split-turn]]` documents for essence); a rendering delivered in the *same* turn as the marked ask does not stamp. Precedence when both an essence and a replan-diff stamp are simultaneously due: essence wins.

**The `confirm-delivery --kind replan_diff` escape.** Where the hook cannot fire — uninstalled, disabled, or the harness root does not carry it (§ Two config roots) — `confirm-delivery --session <id> --kind replan_diff --by <human> --note <why> --escape-reason <reason>` is the audited human override, binding a `DeliveryStamp` to the live `replan_diff` receipt exactly as the plain (essence/full) form already does for `approve`. Its own docstring says plainly it is **not** a security boundary: anyone who can run it could already run `replan` with the gate wide open by other means, exactly as a plan-review override needs no separate permission from `approve` itself — it exists for **audit-trail hygiene** (a named human, a stated reason, one of the closed `DELIVERY_ESCAPE_REASONS`), never to gate *who* may replan. This is a deliberate asymmetry worth stating outright: this same change **removes** a self-attested escape (the `plan-review --verdict override` path that let anyone self-record an override under any `--reviewer` string with no audit binding — the vulnerability this whole task started from) and, in the same change, **adds** a self-attested escape here. The two are not in tension: the one removed let an unauthenticated actor *forge* a review outcome; the one added lets an authenticated human *stand in* for a hook that structurally cannot run, and every use is named, reasoned, and logged — audited where the removed one was not. Without this escape, `replan_authorization_blockers` would brick every non-substantive replan on any machine where the delivery hook is not wired, the exact bypass-trainer shape a fail-closed gate must never produce (§ Two config roots).

**`AGENTCTL_REPLAN_AUTHORIZATION`** forces the gate on (`"1"`) or off (`"0"`) regardless of weight class — the same override shape `AGENTCTL_PLAN_REVIEW` and `AGENTCTL_STAGE_REVIEW` already use — read once by the pure predicate `replan_authorization_active`; unset, the gate applies to every SUBSTANTIVE session and to no chat/small-change one.

**The pop-subplan venue-substitution guard (stage 7).** A related, but structurally separate, silent-edit route closes here rather than in `replan` itself: a service sub-plan (§ Sub-plan stack) restores the parent's venue on `pop-subplan`, and while the child ran, nothing prevented the coordinator from performing an ordinary CLAUDE.md-sanctioned in-thread refinement to the parent plan file (e.g. stamping `Actual effort:` on a stage the parent already passed) — a write `replan` never sees because it isn't a `replan` call at all. `PlanFrame` (schema 34) now snapshots the parent's venue pair (`parent_repo_root`, `parent_delivery_worktree`, `parent_venue_captured`) at `push-subplan`, and `pop-subplan` compares a fresh read of the same two fields against that snapshot **only when `parent_venue_captured` is true**: on a mismatch it keeps the frame's already-restored venue (`venue_source = "frame (parent plan venue changed while pushed)"` in the pop-subplan history event) instead of re-deriving from the file as `_sync_venue_from_plan` ordinarily would; otherwise (no capture, e.g. a pre-schema-34 frame, or the parent was unreadable at push) it falls through to that same unconditional re-derive, unchanged.

This is deliberately **source-selection, not a gate**: `pop-subplan` is the only edge out of `RESOLVED` with a non-empty `plan_stack`, so a refusing pop would strand the session with a finished child, a parent it cannot resume, and no transition left — it must stay unrefusable, and the fix therefore lives entirely in which value is trusted, never in a refusal. The comparison is deliberately narrow — the two venue fields alone, never a hash of the parent file's bytes. A whole-file hash was the first draft and was rejected: an in-thread refinement anywhere else in the file (the common case CLAUDE.md itself sanctions while a sub-plan runs) would trip it, and every such false positive **suppresses the very repair the comparison exists to make** — the frame fallback would be selected over a legitimate, already-correct re-read, leaving `state.repo_root`/`delivery_worktree` at a stale value for the rest of the parent's execution. Tightening the comparison to the whole file is the wrong-way fix this paragraph exists to forestall. Symmetrically, the comparison carries **no non-empty precondition** on the captured fields themselves — `parent_venue_captured` exists precisely so "this parent declares no `delivery_worktree`" (the majority plan shape) is a captured *observation* a later addition can still contradict, not a hole the comparison steps over; skipping the comparison whenever the captured value is empty is the opposite wrong-way fix this paragraph also forestalls.

The honest residual: when a substitution **is** detected against an empty frame venue (the frame captured `("", "")` and the fresh read now differs), `pop-subplan` keeps the empty venue — every check then resolves through `resolve_check_venue` with an effectively unset venue, which for a stage's own dispatch/verify falls through to `cwd=None` in the engine process's own working directory, because `_refuse_missing_cwd` (`cli.py`) only refuses a **falsy** `cwd` combined with `state.delivery_worktree` being set — an unset `delivery_worktree` is not refused, it simply runs there, silently. This is **not** a visible, recoverable stop, and documenting it as one would be wrong about the code: the trade is taken on *blast radius*, not on *visibility* — running in the engine's own cwd is a wrong venue but not one an attacker chose, whereas trusting a substituted venue would execute every `verify_command` and `[[final_check]]` in a tree someone else picked after approval. Pinned by the five cases in `scripts/tests/test_subplan.py` covering the frame-vs-file substitution, the untouched-parent re-derive, the whole-file-hash regression this section warns against, the legacy-frame (uncaptured) no-raise path, and the empty-field blind spot.

### Check venue

Every check the engine runs — the active stage's dispatch, `record-result`'s verify, `verify-final`'s per-stage re-verify, and every `[[final_check]]` — resolves its cwd through one shared resolver, `SessionState.resolve_check_venue(venue)` in `state.py`, instead of each site defaulting its cwd independently. This closes the venue-asymmetry defect where dispatch wrote into `delivery_worktree` while every verify site checked `repo_root`, so a stage's actual work and its "passing" verification could silently observe two different trees.

A check declares one of two `CheckVenue` values: `Criterion.verify_venue` on a stage (default `"delivery"`) and `FinalCheck.venue` on a `[[final_check]]` (default `"delivery"`).

- `"delivery"` (the default) resolves to `[meta] delivery_worktree` when the plan declares one, else `repo_root` — with no `delivery_worktree` declared this is byte-identical to plain `repo_root`, so every plan that predates this field is unaffected.
- `"repo_root"` always resolves to the canonical checkout, regardless of `delivery_worktree` — the explicit opt-in a check needs when it must observe a landed artifact in canon rather than the worktree the stage wrote to.

`cmd_dispatch` always resolves `"delivery"` for the spawned stage's cwd (a hard-sandboxed spawned child can only write the tree it is launched in, and dispatch has no `verify_venue`/`venue` of its own to declare); the three verify sites resolve whatever the stage's `verify_venue` or the `[[final_check]]`'s `venue` declares.

**The venue re-derivation invariant.** `resolve_check_venue` can only be as correct as the two state fields it reads, so **every route that establishes, re-establishes or re-reads which plan the session is executing re-derives `repo_root` and `delivery_worktree` from that plan's `[meta]`, together, through the single helper `cli._sync_venue_from_plan`** — `submit-plan`, all three `replan` branches (including `no_change`, which absorbs an in-place edit, and which `delivery_worktree` reaches only this way since `diff_plans` does not compare it), `_refresh_caches_from_plan_path` on the `approve` path, and `pop-subplan`, which re-derives from the parent plan FILE rather than trusting the `PlanFrame` snapshot. The helper is fail-safe: an absent or unparseable plan leaves both values untouched, which is what makes the frame the pop path's fallback. `push-subplan` is the one deliberate exception — it nulls both for the child, and the state machine (stages reset to `[]`, `EXECUTING → CLASSIFIED`) makes the null window unobservable until the child's own `submit-plan` refills it. A route that refreshed only `repo_root` left a plan that declares a delivery worktree silently resolving to the canonical checkout — the venue asymmetry this whole section exists to remove, reintroduced one route down. Pinned by `test_replan_refresh_delivery_worktree`, `test_pop_subplan_rederives_venue_from_plan` and `test_approve_rederives_venue_from_edited_plan`.

**The active-stage pointer invariant.** `pop-subplan` derives `state.current_stage` from the restored stages' own status through `cli._restore_current_stage`, rather than trusting whatever the popped `PlanFrame` snapshotted or hardcoding `None`: the single stage whose `outcome.status` is `ACTIVE` becomes the pointer, run AFTER the originating stage is marked `PASSED` (deriving first could re-point at a stage this same call is about to satisfy). A push can leave a stage `ACTIVE` — mid-flight — while the frame's `current_stage` is already `None`; restoring that snapshot verbatim would leave the pointer lost and the `ACTIVE` stage unreachable by every ordinary verb (`next-stage` only offers `PENDING` stages, `dispatch`/`record-result` act only through `active_stage()`). Fail-safe in the ambiguous cases — zero or more than one `ACTIVE` stage — both yield `None`, matching prior behaviour. Pinned by `test_pop_subplan_restores_pointer_to_active_stage` and `test_pop_subplan_clears_pointer_when_originating_stage_was_active`.

**Missing-venue refusal.** Once a plan declares `delivery_worktree`, a check whose resolved venue does not exist on disk (a worktree never created, or cleaned up after its session ended) is a **refusal**, not a check failure — the engine cannot know whether the check would have passed there, so it neither records the stage FAILED nor enters `DIAGNOSING`; it surfaces a one-line diagnostic naming the missing path and the remedy (create the venue, or declare `venue = "repo_root"` if a delivery venue is no longer needed). With no `delivery_worktree` ever declared, a missing `repo_root` still surfaces the old way — a shell `cd` failure inside the check, i.e. an ordinary check FAILED.

**The venue lint (`plan.check_venue_warnings`).** An advisory-only check at `submit-plan` reads each stage's `verify_command` and every `[[final_check]]`'s `command`, and warns when the command's first `cd` target **contradicts** its declared venue (a `"delivery"`-venue check `cd`-ing into `repo_root`, or vice versa). It is silent when a check declares `venue = "repo_root"` and `cd`-s into canon — that is now a deliberate, reviewable declaration, not a suspected mistake — and it never blocks `submit-plan`.

**The coverage gate's operative surface.** `gates.replan_coverage_blockers`' CHANGE half — see `replan` above — compares the plan's **operative surface** (`gates._operative_surface`): per stage, `means`/`method`/`procedure`/`verify_command`/`expected_exit`/`verify_venue`/`executor`, plus `verify_venue_at_final`. `procedure` and `verify_venue_at_final` contribute **only when the stage declares them**, and `procedure`, added last, is tagged with its own field name (`procedure:<value>`) so that a sentence MOVED from one declared-only component to the other registers as the change it is rather than tying; at plan level, `repo_root`/`delivery_worktree` and every `final_check`'s `(command, expected_exit, venue)`. Deliberately excludes every prose field (title, goal, done_criterion, expected_result_image, material, conditions, invariants, principle) so no amount of narrative rewriting satisfies it, and normalizes each string component (casefold + collapsed whitespace) so a whitespace-or-case-only rephrasing does not register as a change. A replan whose whole correction lives in `verify_command`, a `[[final_check]]`, or `[meta]` now satisfies the CHANGE half; a cosmetic edit to `means`/`method` alone no longer does.

**Two moments, two venues (`verify_venue_at_final`, schema 24).** A stage's `verify_command` can run at up to two distinct moments: at **execution** (`record-result`'s own verify, resolving `Criterion.verify_venue`) and again at **resolution** (`verify-final`'s per-stage re-run). Before schema 24 both moments resolved the same `verify_venue`, so a stage whose delivery worktree is torn down by landing (`land-branch.py`, without `--keep-branch`) would refuse at verify-final even though it passed correctly at execution. `Criterion.verify_venue_at_final` (optional, default `None`) lets a stage declare a second, independent venue for the resolution-time re-run only — `record-result`'s own verify never reads it. `SessionState.resolve_final_check_venue` is verify-final's counterpart to `resolve_check_venue`, applying four validation rules (**V1-V4**, enforced in `plan.py` at parse time):

- **V1** — if declared, must be a `CheckVenue` member (`"delivery"` or `"repo_root"`), exactly like `verify_venue`.
- **V2** — must not appear on a `verify_kind = "landed"` criterion: a landed check's venue is always `"repo_root"` by construction (§ Landed checks below), so a second venue for it is meaningless and rejected as a `PlanError`.
- **V3** — must not appear when `[meta] delivery_worktree` is unset while it differs from `verify_venue`: with no delivery worktree there is only one venue in the first place, so declaring a *different* one at final has nothing to resolve against.
- **V4** — absent (`None`) resolves to `verify_venue` at read time — a plan that never sets the field re-verifies in the identical venue it always has, byte-for-byte the pre-schema-24 behaviour. This is also why `render_plan_md` renders no second-venue line for such a plan (below).

**Recommended shape for a plan that lands its own work:** `verify_venue = "delivery"` on stages that need the worktree while it exists, `verify_venue_at_final = "repo_root"` on those same stages so their resolution-time re-run observes the landed artifact instead of a worktree landing is about to remove, plus a separate stage or `[[final_check]]` with `verify_kind = "landed"` asserting the delivery actually reached trunk. `../tests/fixtures/plan_landed_example.toml` demonstrates the landed-assertion half (its stage criterion uses `verify_kind = "landed"` and its `[[final_check]]` uses `kind = "landed"`); it does not itself carry the `verify_venue`/`verify_venue_at_final` pairing, which a real plan adds on the stages whose worktree its own landing removes.

**The survivability warning (`plan.check_venue_warnings` addition).** The venue lint above now also fires when a stage declares `verify_venue = "delivery"`, carries no `verify_venue_at_final`, and the plan asserts landing somewhere (a `kind = "landed"` stage or `[[final_check]]`) — the exact shape that will refuse at verify-final once landing removes the delivery worktree. Advisory only, never a blocker: `--keep-branch` lets a delivery worktree legitimately survive its own landing, so the condition is a strong signal, not a proof. The warning is scoped to `criterion_type = "measurable"` stages: verify-final re-runs a `verify_command` only for those, so an acceptance-review stage cannot refuse there and is never flagged.

**Plan rendering (`render.py`).** This is the second-venue line V4 refers to: `render_plan_md` appends a `- **Verified in:** <venue>; re-verified at resolution in <venue-at-final>` bullet under a stage's verify command **only when that stage declares `verify_venue_at_final`**. A plan that never sets the field renders byte-for-byte as it did before schema 24 — V4's identity made visible in the projection as well as in resolution.

**`[[final_check]]` has one venue, not two.** A `FinalCheck` runs at exactly one moment — `verify-final`, and only there — so there is no second moment for a second venue to distinguish; `verify_venue_at_final` is a `Criterion`-only field. The asymmetry with per-stage checks (two moments, up to two venues) is deliberate, not an oversight.

**Refusal routing — execution vs verify-final are two different directives.** A venue refusal behaves differently depending on where it fires. At **execution** (`cmd_record_result` — `cmd_dispatch` resolves the delivery venue unconditionally as the spawn cwd and has no venue of its own to refuse) a refusal returns the plain `fix_venue` directive and performs **no node transition** — the stage is simply un-recorded and can be re-dispatched once the venue exists; nothing is stranded. At **verify-final** (`cmd_verify_final`), a refusal — a stage's shell venue, a stage's `landed` exit-97, a `[[final_check]]`'s shell venue, or a `[[final_check]]`'s `landed` exit-97 — instead routes through `_diagnose_venue_refusal`, which transitions `VERIFYING` → `DIAGNOSING`, seeds a `Difficulty`, and returns the `declare` directive under the `OVERCOME-DIFFICULTY` marker: a refusal discovered this late is a genuine plan-level difficulty (the resolution-time venue this stage needs no longer exists), not a simple re-run. `_resolve_final_or_refuse` is the shared helper resolving through `resolve_final_check_venue` before this split applies.

`cmd_verify_final` is **idempotent on re-entry**: called again while already in `DIAGNOSING` it returns the same legible `declare` directive rather than re-attempting the transition; called again from `RESOLUTION` it returns an idempotent `resolve` hint; called from any other non-`VERIFYING` node it returns an `inspect` directive naming the current state. Only a session actually in `VERIFYING` runs the transitioning body.

**Honest limits.** The engine cannot verify that a check is actually *portable* between the two venues — a `verify_venue_at_final = "repo_root"` declaration is trusted, not proven, to mean the same assertion still makes sense against the landed artifact. The survivability warning is advisory and can be ignored (deliberately: `--keep-branch` is a legitimate reason to). A plan whose session state was persisted before schema 24 keeps the old single-venue behaviour permanently — the field is read from the stored `SessionState`, never re-derived, so an old session has no `verify_venue_at_final` to resolve and V4's default silently governs it forever.

### Project permissions forwarded to a spawned developer

`cmd_dispatch` resolves the same delivery venue it pins the spawned child's cwd to (`resolve_check_venue(DELIVERY)`, see § Check venue above) a second time, to look for `<venue>/.claude/settings.local.json`. When that file exists, its absolute path is forwarded to `dispatch_stage`/`build_argv` as `--project-settings`, and `spawn-specialist.py`'s `build_child_settings` merges its `permissions.allow`/`permissions.deny` arrays into the spawned developer's `--settings` grant, alongside the fleet-wide `DEVELOPER_SETTINGS_ALLOW` list (scoped only to this repo's own verifiers). Scoped to `kind == "developer"` only — the read-only kinds never run Bash commands that need this.

**Do not confuse this with `--project-permissions`.** That older, similarly-named flag feeds `permissions_digest`, a PROSE summary of a `permissions/*.json` audit-log file (the `pattern`/`granted_at`/`context` shape `permissions-cli.py` manages) embedded into the spawned child's *prompt* — it never reaches the `--settings` JSON the harness actually gates tool calls against, so a project that already allow-lists its own build/test commands in `.claude/settings.local.json` got no benefit from it. Before this section existed, a spawned developer for a target project could write and test its change correctly but could not RUN its own project's test suite to attest it, because `DEVELOPER_SETTINGS_ALLOW` knows only this repo's own verifiers (`pytest`, `verify-all.py`, …) and nothing about a target project's own commands.

Fails open: a missing or malformed `settings.local.json`, or no resolvable delivery venue at all, forwards nothing — dispatch behaves exactly as it did before this mechanism existed.

### `[stage.grants]` — the per-stage grant channel

*Difficulty removed:* a code-executing or write permission a spawned child needs is neither fleet-wide (so does not belong in `settings/base.json`, read-only-only by invariant, see [[settings-permission-tiers]]) nor durable across every stage of every plan (so does not belong in a per-kind `KIND_BASELINES` row). Without a third home, the only options are widening a fleet-wide allowlist for one stage's sake, or leaving the stage unable to run at all.

**Shape.** A stage may declare a `[stage.grants]` table (`allow` — a list of rule strings, e.g. `Bash(…:*)`, `Edit(//…)`, `Read(//…)`; `add_dirs` — a list of `path:mode` entries, `mode` one of `read`/`write`) in `agentctl/grants.py`'s `AddDirGrant`/`RuleGrant`/`StageGrants` dataclasses. Every entry — declared, derived, or runtime — passes through `grants.validate_rule`/`validate_add_dir` before it can reach `spawn-specialist.py`'s `--settings`/`--add-dir`; a refused DECLARED entry raises at plan-load time (the plan is rejected outright, not silently narrowed), while a refused DERIVED entry is routed to `dropped` instead (see `derive_stage_grants`) since a derivation rule proposing something unsafe is not itself a plan-authoring error. See [[spawning-specialists]] § File-access scope for how a materialized entry appears in the spawned child's own generated prompt, and [[settings-permission-tiers]] § Grant channel for the exhaustive never-grantable-forms list and the interpreter-mediated residual.

**Three provenances.** `declared` — hand-authored in the stage's own `[stage.grants]` table. `derived:DR-V`/`DR-O`/`DR-E`/`DR-R` — proposed automatically by `derive_stage_grants(stage, *, venue)`, the only function allowed to propose a grant from a stage's own already-declared elements:

- **DR-V** — one `Bash(<segment>:*)` per top-level `verify_command` segment (a segment containing `$`, a backtick, a redirect, or a subshell is unresolvable and dropped, never widened to cover it).
- **DR-O** — an in-venue `.py` output artifact not under `tests/` derives `Bash(python3 <rel>:*)`; a `.sh` one derives `Bash(<rel>:*)`.
- **DR-E** — `spawn:developer`/`spawn:tech-writer` stages only: each in-venue output artifact or material ref derives an `Edit(//<abs>)` allow.
- **DR-R** — each outside-venue absolute path named in `material_refs`/`knowledge_refs`/`output_artifacts` derives a READ add_dir on its containing directory.

`runtime` — granted mid-execution via `resolve-permission --scope stage\|once` (see the command table above) and consumed once (`once`) or for the stage's remaining dispatches (`stage`).

**Approval binding (`grants_sha256`).** `plan.grants_sha256(doc)` is a stable sha256 over every stage's EFFECTIVE (declared+derived) grant set. `present-plan --kind essence` stamps it onto the presentation receipt; `approve` re-derives it and stores the result as `state.approved_grants_sha256` — never a stale prior digest on a plan that failed to load or grants nothing (`plan_has_any_grants` no-ops both checks on such a plan). This closes the gap a `plan_sha256` binding alone cannot: a derivation-rule CHANGE in `grants.py` between presentation and approval, or an out-of-band plan edit, never silently carries forward a wider effective grant set as "already reviewed" — and `stage-grants` only reports derived entries when a fresh re-hash of the approved snapshot still matches this stored digest (see the command table above), so a materialization-layer drift after approval degrades to under-reporting, never over-granting.

**Effective-set growth is a substantive diff, even with no `[stage.grants]` edit.** `diff_plans` already treats any change to a stage's DECLARED grants as substantive via `grants_place`'s participation in `_structural_signature`. `plan._grants_grew(old, new)` closes the complementary gap: comparing the EFFECTIVE grant set (both sides derived against `new`'s own venue, since DR-E bakes the venue string into its `Edit(//{venue}/...)` literal) catches a plan edit that widens what gets derived — a `verify_command` edit that derives a wider DR-V rule, or a new output artifact that derives a new DR-E `Edit` — with no `[stage.grants]` line touched at all. `diff_plans` checks `_grants_grew` **before** the ordinary prose comparison and unconditionally returns `'substantive'` on a hit, on the theory that "grant edits and effective-set growth are substantive" is the approved done criterion in full, not "substantive unless the widening rode in on an edit that would otherwise read as a refinement". A stage present only in the new doc counts as growth against the empty grant set (already implied by `_structural_signature`'s differing stage-index sets, but checked independently as cheap insurance); a SHRINKING or unchanged effective set is deliberately not growth — narrowing what a stage may touch never needs the re-approval a widening does.

**A grant collision is refused when the plan is written, not when the child is launched.** `spawn-specialist.py::build_child_settings` refuses a child payload in which an Edit deny covers an Edit allow entirely (`GrantShadowError` — the client resolves deny over allow, so the allow would be void). The commonest way a plan produces one is a `spawn:developer` stage that spells a directory venue-relative in one ref (DR-E's `Edit` allow) and absolute in another (DR-R's read add_dir, which carries an Edit deny over that directory). `grant_shadow.plan_grant_shadow_problems` runs that same assembler over every spawn stage's declared+derived grants, with the workdir dispatch would pass (`delivery_worktree`, else `repo_root`, never the author's cwd, never an existence check), so **`submit-plan` (and every other submission seam, whatever the weight class) and `plan-grants` both refuse a colliding spawn stage** — `plan-grants` exits 1 and lists the problem, `--format json` under `shadow_problems`. The message is the spawn-time message itself, prefixed `stage <n> (<title>):`, naming both rules and the source of each. A stage that merely spells one directory both ways (`grant_shadow.mixed_spelling_advisories`) is **advisory only**: an `advisory:` line from `plan-grants`, an entry in `data["advisories"]` from `submit-plan` and `replan` — never a refusal, since a stage that derives no Edit allow there collides with nothing.

**Materialization defect vs planning miss.** When a dispatched child's transcript shows a permission-denial stop, `_classify_transcript_denials` checks it against the stage's PRE-LAUNCH effective grant set (`_effective_stage_grants`, the same merge `grant_covers_call` checks a live `PERMISSION-REQUEST` against): if the denied call **was** covered, the grant existed but `--settings`/`--add-dir` materialization failed to carry it — appended to `state.materialization_defects` **regardless of which marker the child returned**. If the call was **not** covered, it is a genuine planning miss — appended to `state.planning_misses` with `asked_user` recording whether the coordinator escalated it live or it was only ever discovered after the fact via transcript scan. Routing straight into `FAILED → DIAGNOSING` (`_diagnose_materialization_defect`), rather than asking the user or re-dispatching unchanged, only happens when the returned marker is `PERMISSION-REQUEST` — a child that self-reports `Rule: <harness permission rule>` (see [`_shared/marker-protocol.md`](../../skills/specializations/_shared/marker-protocol.md)) whose rule is already covered is diagnosed via that same defect, not surfaced as a fresh question, and a stop already classified once (by `tool_use_id`) is never double-counted between the live-request path and the later transcript scan. A child that returns `COMPLETED`/`INCOMPLETE`/any other marker after working around a covered-but-materialization-failed denial gets its defect appended to the ledger silently — the stage still proceeds under that marker's own routing; nothing currently promotes it to `FAILED → DIAGNOSING` on the ledger write alone.

**`settings_drift`.** A spawned child is never granted write access to `settings*.json` — so `dispatch` hashes every live settings document under the child's cwd and repo root (`widening_targets.enumerate_live_settings`) both before and after the child runs, and records a `settings_drift` finding whenever any of those hashes changed. This catches a child that tampered with settings on disk (a stray write that slipped past its grants, an out-of-band edit); it does NOT compare the materialized `--settings` payload against what the stage's declared+derived grant set implies it should be — that would be a different check (a mis-assembled payload), and is not implemented.

**`cwd_drift`.** A Bash denial whose raw command text is NOT covered by the stage's effective grants may still be a planning artifact rather than a genuine miss: if the child ran it from a subdirectory of the stage venue (its transcript `cwd` differs, by resolved path, from `state.resolve_check_venue`), `_classify_transcript_denials` rewrites the command's path-like words back to their venue-relative spelling and re-checks the rewritten text against the same grant matcher. The rewrite (`_rebase_bash_command_to_venue`) only fires on a SINGLE top-level statement — a compound command (`&&`/`||`/`;`/`|`, or several physical lines) returns `None` unrebased, because one of its other segments may be a genuine miss this function has no way to check. Within that one statement, only a RELATIVE word that names a path actually existing under the drifted cwd is rewritten, to its resolved-path spelling relative to the resolved venue; an absolute word is left untouched even when it resolves under the drifted cwd, since a venue-launched child typing that same absolute text would still be denied — the cwd was never the cause. Every other word — verbs, flags, bare arguments, and any word this function does not touch — keeps its original quoting and escaping byte-for-byte, because the rewrite edits only the changed words' spans in place rather than re-serializing the whole command. If the rebased command WOULD be covered, the denial is appended to `state.cwd_drift` instead of `state.planning_misses` — it never reaches `asked_user`/live promotion, and a rescan of the same transcript never reclassifies it (its `tool_use_id` joins `known_ids` alongside the other two ledgers). A denial with no `cwd`, a `cwd` equal to the venue, a non-Bash denial, a compound/multi-line command, or a rebase that still doesn't clear the grant matcher all stay `planning_misses` as before. `grant-stats` (see command table) is the read surface over all four ledgers: `planning_misses` (with an `asked`/`unasked` breakdown), `materialization_defects`, `settings_drift`, and `cwd_drift`.

### Resource-based permissions

*Difficulty removed:* `grant_covers_call`'s coverage check (used both for a live `PERMISSION-REQUEST` and for transcript-denial classification, see § Materialization defect vs planning miss above) is a LITERAL command-string match — it cannot tell that `git push origin main` and `git push origin HEAD:main` name the same effect, or that an order the customer approved for `origin/main` covers a differently-spelled push to the same ref. Without a typed layer, closing that gap would mean either widening the literal-match rule (reintroducing the spelling-equivalence bug `_segment_covered`'s docstring records as "round 3" — see its comment) or asking the user again for something already approved.

**Typed resources (`resources.py`).** Five frozen dataclasses — `FileResource(path, mode)`, `VcsRefResource(remote, ref, op)` (`op` ∈ `push`/`land`), `SpecialistResource(role)`, `ServiceResource(name, op_class)`, `DatasetResource(system, locator)` — each with a `covers(approved, requested)` classmethod/method encoding its own equivalence (a `VcsRefResource` is keyed only on its destination ref, matching `_resolve_git`'s own resolution — see § below). Deliberately deferred: money/quota amounts, read-confidentiality, and Org-layer dataset/service contracts — none of these are resolvable from a literal command line alone, so no resolver in this module attempts them; a stage touching any of them stays unresolved rather than getting a typed resource that understates what it actually needs.

**Contract-grounded resolution (`tool_contracts.py`).** `resolve_command(text, venue, contract_table=...) -> Resolution` resolves a literal shell command string to `{status, resources, reason_class, identity}` (`reason_class` is one of the five canonical tags — `residual-syntax`, `adhoc-undeclared`, `contract-unresolved`, `wildcard-tail`, `unknown-program` — with any finer distinction kept in `reason` text instead of a bespoke tag). A `git push <remote> <src>:<dst>` resolves to `VcsRefResource(remote, dst, "push")` keyed only on the destination ref; a force/delete push (or a zero-refspec, `+`-prefixed, or otherwise non-plain push) gets `reason_class="contract-unresolved"`; a non-literal remote/refspec (a shell variable, an expansion) gets `"residual-syntax"`; an unrecognized program gets `"unknown-program"`.

**One shared computation (`plan_resources.py`).** `resolve_rule_grant(rule, venue) -> Resolution` resolves one `Tool(arg)` rule string the same way: a non-Bash rule (`Edit`/`Write`/`Read`) resolves to a `FileResource`; a Bash rule without a `:*` wildcard tail defers to `resolve_command`; a Bash rule **with** a wildcard tail is always `unresolved` with `reason_class="wildcard-tail"` — the argv it admits at materialization time is unbounded, so no bounded resource set can be attributed to the rule text alone (this is a property of the RULE, independent of whether the eventual concrete call would itself resolve cleanly). `compute_stage_resources(stage, venue)` folds a stage's effective (declared+derived) grants, its own spawn/landed shape, and its declared `[[stage.effects]]` into one `StageResources`. All three call sites that need "what does this plan/stage touch" in typed form — the read-only `plan-resources` CLI (below), `approve`'s ledger stamping, and `dispatch`'s self-grant cross-check — go through this one module so a new wrinkle (a new wildcard case, a new resolver) cannot drift between them.

**`agentctl plan-resources --plan P [--format text|json]`** renders every stage's rule/add_dir resolutions (resolved → resource kinds; unresolved → `reason_class`) read-only, with no approval or dispatch side effect — the inspection surface for "what would this plan's grants resolve to". `--corpus DIR...`/`--commands-file F` instead resolve literal command TEXTS directly through `resolve_command`, for a best-effort scan across a directory of plan fixtures or a flat command list; `--require-no-unknown-program` fails the call on any `unknown-program` hit.

**The order-approvals ledger (`order_approvals.py`).** One JSON file per `plan.order_digest(doc)` under `config_root.agentctl_order_approvals_dir()` (`$AGENTCTL_ORDER_APPROVALS_DIR` overridable, test-isolated by default). `record_approval(order_sha256, *, plan_sha256, resources, unresolved_identities, stage_effects, by, at)` refuses `AGENT_ACTOR` as `by` — only a human/customer decision can populate the ledger. `boundary_resources(order_sha256)` returns the typed resources the user's approval of this order stands behind: the resource list of the LAST user-approved version plus every customer stage-scoped grant (a record with no `plan_sha256`) — not the union over every version. A user re-approval may narrow the set, and a resource dropped there must stop being self-grantable; `gates.autonomy_boundary`, `resolve-permission --by agent` and `dispatch`'s self-grant all read this one set, so a later revision's differently-worded but resource-equivalent grant still finds coverage while a dropped resource does not.

**`dispatch`'s self-grant resolution.** A parked `PERMISSION-REQUEST` whose stdout carries a `Rule: <harness rule>` line (and, optionally, a `Resource: <kind>(<args>)` line naming what the child itself believes it needs) is checked in order: (1) the PRE-EXISTING literal-text `self_covered` check (`_rule_line_to_call` → `grant_covers_call` against the stage's effective grants, which for a `spawn:*` stage includes the kind baseline — see `lib.kind_baselines`) fires FIRST and, if covered, routes to the materialization-defect diagnosis (§ above) rather than ever reaching the code below — a rule already granted should never have been denied at all. (2) Only when that check is **not** satisfied does `_self_grant_resources_for_rule` resolve the `Rule:` line via `plan_resources.resolve_rule_grant` and check the resulting resource(s) against the union of `boundary_resources` (the last user-approved version plus customer stage grants) and the stage's own effective grants (each independently re-resolved to resources, never compared by text) — a match returns `self_grant`; a reported `Resource:` line that disagrees with the `Rule:` line's own resolution is refused outright (`resource_disagreement`, naming both) rather than trusted; no match falls through to the pre-existing `ask_user_permission` path, with `reason_class` set from the rule's own resolution (e.g. `wildcard-tail`) when available. A wildcard-tail rule can therefore never self-grant via resolution — the ONE exception is when its bare (wildcard-stripped) form happens to match the literal `self_covered` check in step (1), e.g. `Bash(find:*)`, which every spawn kind's baseline already covers and which therefore never reaches step (2) at all.

### Durable evidence and checkpoint commits

*Difficulty removed:* a spawned developer told to "keep evidence" with nowhere durable to put it defaults to `/tmp` — swept before anyone reviews it, and outside every grant the child actually holds.

**`evidence-dir --session S --stage N`** creates (idempotently) and prints `<evidence root>/<session>/stage-<N>/` (`cli.evidence_dir_for` / `cmd_evidence_dir`), never under `exempt_paths.scratch_roots()`, so it survives whatever GC sweeps `/tmp`. The evidence root resolves, in order: `$AGENTCTL_EVIDENCE_ROOT` (test-only override — skips only the scratch-root refusal below; `grants.validate_add_dir` still applies) → else `$XDG_STATE_HOME` (only when set and absolute) `/agentctl-evidence` → else `~/.local/state/agentctl-evidence`. Resolution **fails loudly**: a root that lands under a scratch root, or that `validate_add_dir` refuses, raises `cli.EvidenceDirError` — no fallback search, no silent second attempt. `cmd_evidence_dir` turns that into a failed `Directive`; `dispatch`'s Directive carries the same path at `data.evidence_dir` for every marker branch (computed via the identical `evidence_dir_for` formula before the child spawns, so a refused root fails the dispatch call itself rather than wasting a real spawn, and a dry-run preview and a real dispatch never disagree) — reported, not created, on that path; creation happens once, on the `evidence-dir` call itself (in-process, from `spawn-specialist.py`) or the standalone CLI invocation.

**Ephemeral output artifacts.** `submission.py`'s `_ephemeral_artifacts_violations`, beside `_negative_control_violations`, flags any stage `output_artifacts` entry that resolves under a `scratch_roots()` root (the same root-containment test as `exempt_paths.is_ledger_noise`, never a substring match) — a committed artifact path under `/tmp` claims a durability the path does not have. `ephemeral_artifacts_waiver = "<reason>"` on the stage names why a flagged entry is legitimate (parsed permissively by `plan.py`, same treatment as `negative_control_waiver`; stored on `Stage`; rendered by `render.py` when present). `verify_command` text is never inspected by this check — a test's own `/tmp` fixture, or a throwaway diff mentioning the path, is unaffected. A waiver-only edit classifies as `diff_plans`' `'refinement'` (a tagged splice in its `_prose` comparison, on the same footing as `actor.cost_tier`) and is carried onto the live stage by `_apply_refined_stage_fields`; `gates._renorm_stage_residual` also folds the field in as its fourth engine-consumed splice, so re-declaring the waiver under the light `replan --renormalize` path is refused like a `cost_tier`/`output_artifacts`/`grants` change would be.

**Checkpoint commits.** Every `--kind developer` prompt (whole-plan and `--plan-brief` alike — one `assemble_prompt` call handles both) gets a fixed `## Checkpoints` section: commit as soon as each checkpoint's own control goes green, push the personal/ticket branch after each commit, and keep evidence in the durable directory above rather than `/tmp` — naming the concrete path when `--session`/`--stage-index` resolve one, otherwise noting none is available. Visible under `--dry-run` with no separate handling, since it rides the same assembled `prompt` string the dry-run branch already prints. Non-developer kinds get no such section.

**Write access for the child.** When `--session`/`--stage-index` are given to a `kind == "developer"` spawn, `load_or_create_evidence_dir` resolves and creates that stage's evidence directory, which then gets a `--add-dir` (via the existing `stage_grant_add_dir_args`) and a write grant (via the existing `stage_grant_rules`) folded straight into the child's `--settings` by `build_child_settings`'s new `evidence_dir` parameter. This is spawn-time-only — never an entry in `derive_stage_grants` or the stage's own `[stage.grants]` — so it does not touch `grants_sha256(doc)` (computed purely from the `PlanDoc`'s own declared/derived grants) and cannot retroactively invalidate an already-approved plan's approval binding.

### Runtime host (sticky)

`state.runtime_host` (`claude` | `cursor`) binds once at `classify` (optional earlier at `start`/`reset`) and never rebinds mid-session. It selects which CLI family every spawn and short LLM call uses: `dispatch.spawn_cli_for`, `lib.host_llm.build_prompt_argv`, advisor judges, and `marker_extract`. Cursor omits `--model` for Auto (`lib.runtime_models.model_for` → `None`). Cross-host argv is refused (`lib.host_llm.CrossHostError`); wrappers also refuse when `AGENTCTL_RUNTIME_HOST` names the other host.

### Advisory judge (warn-only)

`advisor.judge(kind, payload, runner, enabled=...)` shells a fail-open `claude -p --model sonnet` judgment (hard `_ADVISOR_TIMEOUT_S`-second timeout via `advisor.subprocess_runner`) at four cognition points: weight classification, plan completeness, hypothesis genuine-distinctness, and acceptance-observation adequacy. Results (a `list[str]` of advisory strings) are attached under `directive.data['advisories']` by `_attach_advisories`. **Non-blocking contract: `judge` never sets `directive.ok = False` and never changes `directive.node`.** With the advisor disabled or errored the return is `[]` and control flow is byte-identical to advisor-absent — preserving the engine's determinism canon (**code = deterministic control-flow, prose = cognition**). The advisor is the cognition half of the hybrid design: deterministic gates **block**; the advisor **warns**.

The two whole-plan enumeration cross-checks (`advisor.enumerate_claims`, `advisor.enumerate_questions_health`) are a distinct call shape, not one of the four `judge_*` cognition points above: they run through `advisor.enumerate_subprocess_runner`, bound by `advisor.ENUMERATE_TIMEOUT_S = 480` (env-overridable via `AGENTCTL_ENUMERATE_TIMEOUT_S`), sized for measured fleet latency on a whole-plan payload rather than the small per-cognition-point payload `_ADVISOR_TIMEOUT_S` is sized for (see `docs/operations/advisor-timeout-calibration.md`). Since stage 4 the producer also runs **detached**: launched fire-and-forget as soon as a plan content digest exists, it folds its result into the `premise` bag's `enumerated_runner_ok`/`enumerated_count` on the next `approve`/`replan` rather than blocking the launching call — see `docs/operations/detached-enumeration-design.md`.

`_attach_advisories` is the single chokepoint that resolves `enabled` via `advisor.resolve_enabled(weight_class)`, threading each call site's session `weight_class` through rather than re-deriving the rule per site: `AGENTCTL_ADVISOR` env overrides in both directions (`1` forces on, `0` forces off); absent the env override, the advisor is on iff config.md's `advisor-mode` key (`off` | `substantive`, shipped `substantive`) is `substantive` **and** the session's `weight_class` is `SUBSTANTIVE` — auto-activation is scoped to substantive work only, and a missing/unreadable `advisor-mode` key fails closed (off).

## Passing large text (`@<path>`)

Any narrative argument this CLI consumes — a goal, a replanning task, a critique, a concern, an observation — accepts **`@<path>` in place of the text itself**, and reads the value from that file. Both spawn wrappers (`spawn-specialist.py`, `spawn-cursor-specialist.py`) accept it on `--constraints` and `--done-criterion`. The Cursor recursive-escape wrapper (`spawn-cursor-escape.py`) does **not yet** apply the convention — its narrative flags (`--expected`/`--actual`/`--mismatch`/`--tried`) take inline text only.

```bash
python3 -m agentctl critique --session s --functional-ground fg --replanning-task @/tmp/task.md
```

- **`@@` escapes.** A value that really begins with one `@` is written `@@text` and arrives as `@text`.
- **A missing referent is fatal, by design.** `@/tmp/dosier.md` (a typo) exits with a message naming the path, the contract and the `@@` escape — it is never silently recorded as nine characters of literal prose while the coordinator believes a dossier was delivered.
- **Nothing else changes.** A value that does not begin with `@` is passed through byte-identical, and an argument never given stays `None`.

Why: Linux caps a **single argv string** at `MAX_ARG_STRLEN = 32 * PAGE_SIZE = 131072` bytes. Past that the kernel raises `E2BIG` *before the child process starts*, or — when the receiver is path-typed — an illegible `OSError: File name too long`. Neither failure names the actual contract, and both arrive at the worst moment: when the text finally got substantial.

Which arguments take `@` is not a prose list. [`cli.py`](cli.py) declares a partition — `_ARG_RESOLVE` (read here), `_ARG_FORWARD` (handed to a child that resolves it at its own boundary), `_ARG_DO_NOT_WRAP` (ids, slugs, digests, paths; each with a one-line reason) — and [`../tests/test_argv_text_call_sites.py`](../tests/test_argv_text_call_sites.py) walks the parser itself, root parser included, requiring every argument that could carry prose to sit in **exactly one** class. An unclassified new argument fails RED; so does a classification the parser no longer declares. **The change that introduces an argument classifies it, in that same change.** The rule itself lives in [`../lib/argv_text.py`](../lib/argv_text.py).

Core spine: `classify`, `config`, `state`, `store`, `machine`, `gates`, `directive`, `cli`, `dispatch`, `partition`, `permissions`, `plan`, `continuations`, `advisor`, `controls`, `cost`, `exempt_paths`, `text_shape`, `procedure`. Plugin framework: `plugins`, `plugins_tracker`, `plugins_experience` (§ Plugins). `cost` is covered in § Cost tracking; `exempt_paths` backs the `hook-state-gate.py` production-path lockstep, `text_shape` renders Directive text, `procedure` backs the method-vs-procedure collapse refusal (§ Renormalization) with the prefilter-plus-fail-open-judge pattern `conditions` established; `controls` is the single control-name resolver shared by `../check-order-coverage.py` and the `premise` question-materiality check (§ Plugins), parameterized by the admissible grammar set with **no default** so neither caller can silently inherit the other's.

Two modules carry the load-bearing invariants:

- **`gates.py` is pure** — every guardian is `(state: SessionState) -> list[str]` (a list of blocker strings). No subprocess, no I/O, no changeset. `verify-agentctl.py` guards this purity and the `GUARDIANS → GATE_TO_HOOK → install-reminder-hooks` consistency.
- **`state.py` + `plan.py` are the canonical plan model** — see below.

## The plan model

Plan structure is defined **primarily by typed code**, not prose. `plan.py`'s `parse_plan` builds grouped dataclasses (`Subject`, `Means`, `Actor`, `Criterion`, `Principle`, `Supply`, `Outcome`) from the flat author TOML and validates the 8-element activity ontology for substantive plans. The canonical description of the 8 elements and where each lives in the schema is [`memory-global/leaves/plan-activity-ontology.md`](../../memory-global/leaves/plan-activity-ontology.md); plans are TOML-only, and a rendered prose view is available on demand via `agentctl plan-render`. On any divergence between prose and code, the code wins. [ADR-0005](../../docs/adr/0005-activity-act-functional-places.md) records the 8 categorical gaps between this model and the code, and the changes that closed them (among them `material_refs`/`knowledge_refs`, `stage.preconditions`, the completed `ELEMENT_NAMES` vocabulary, typed `Order`, `AcceptanceReview`/`AcceptanceBypass`, `means.procedure`), with corpus evidence and what was deliberately left unimplemented.

**Substantive plans must be TOML.** `submit-plan` refuses a substantive plan whose path does not end in `.toml` — markdown may mirror a plan as prose but cannot carry typed stages the engine tracks. Every substantive stage must also declare `capability_required` (Actor-cluster: the skill or knowledge the executor needs); `parse_plan` raises `PlanError` on any missing field.

**`verify_command` is mandatory on measurable substantive stages.** A measurable criterion you cannot execute is really `acceptance_review` — `_validate_substantive_stage` raises `PlanError` if `criterion_type == measurable` and `verify_command` is absent.

**Acceptance-review passes require a distinct recorded observation.** When a stage's `criterion_type` is `acceptance_review`, `record-result --status passed` requires `--observation <text>` that (after normalization) differs from `subject.result` (the expected image). The reviewer records what they actually observed, not an echo of the target.

### Negative controls

**A measurable shell stage's `verify_command` is trusted only after being shown it CAN fail.** For every substantive plan's measurable stage with `verify_kind = "shell"` and a `verify_command`, the submission seam (`submission.py`, not `load_plan`) requires either `negative_control` (a shell command, run in the same venue as `verify_command`, that feeds the check a known-bad input) or `negative_control_waiver` (a non-empty reason a control cannot be built). Landed checks, `acceptance_review` stages and `[[final_check]]` entries are exempt. Plans without either field still load — `load_plan` stays permissive; only `submit-plan` on a substantive plan enforces the requirement.

**Authoring one.** The default known-bad input is the pre-change base tree: a control that runs the same check against the commit the stage's diff started from (before the fix/feature landed) — the check must fail there, since that is exactly the state the stage is supposed to have changed. Reuse the positive command's shape rather than inventing an unrelated probe, so venue and timeout handling stay identical. Build that known-bad tree in a throwaway copy — `git archive <base> | tar -x -C "$(mktemp -d)"` or a temp worktree — never by mutating the venue in place: the venue is the stage's own live working tree, and checking it out to the base commit (even briefly) races every other command that reads it in the same run.

**At `record-result`**, after the positive check goes green (and before the acceptance judge), the engine runs the negative control. If it exits with the stage's own `expected_exit` — i.e. it did **not** discriminate — the stage does not pass: it routes to `DIAGNOSING`, and the failure is recorded two ways — `state.log("control_not_discriminating", ...)` (a history event) and `Directive.data["failure_kind"] = "control_not_discriminating"` (structured, so a caller can branch on it without scanning history). If the positive check is red, the negative control is never run. A waiver is logged as `negative_control_waived` instead of being executed. A control that itself refuses to run (exit 126/127 — command not found or not executable) is neither a pass nor a fail: `record-result` returns a `fix_control` refusal (mirroring the existing `fix_venue` refusal), and `checkrun`'s submit-time advisory labels it `NOT_JUDGED` rather than scoring it either way.

**At `submit-plan`**, `checkrun` additionally runs each declared negative control advisorily and reports `DISCRIMINATES` / `NOT_DISCRIMINATING` alongside the existing `NOT_JUDGED`/`GREEN_AT_SUBMIT`/`RED` labels — advisory only, never a submission blocker. `DISCRIMINATES` is only ever reported when the positive check is itself `GREEN_AT_SUBMIT`: a red positive means the check hasn't been shown to pass on any input yet, so a control that also fails is still reported `NOT_JUDGED` ("discrimination undecidable") but a control that passes is reported `NOT_DISCRIMINATING` (that direction is decidable regardless) rather than the misleading `DISCRIMINATES`. `plan-render` prints each stage's negative control or its waiver.

**Executable end-to-end checks (`[[final_check]]`).** An optional typed `[[final_check]]` list (each entry: `command`, `expected_exit`, `label`) may be added to the plan. `verify-final` runs each entry after the per-stage re-runs; any mismatch refuses the `RESOLUTION` transition. Absent: back-compat (empty list, behaviour unchanged). Turns the plan's *Final verification* from prose the engine never reads into a machine fact.

### Landed checks (`kind = "landed"`)

A point-in-time "did the delivery reach the trunk" assertion has exactly one durable form — monotone containment of a frozen delivered commit in a moving trunk ref — so it is a typed, engine-synthesized check rather than author-written shell (the `CheckKind` discriminator, schema 23). This closes a recorded 20-instance failure family (`memory-global/leaves/experience/2026-06-29-agentctl-verify-venue-worktree-needs-substantive-replan.md`) where a hand-written landed-ness check used SHA equality or a live-resolved head and false-failed the moment the shared trunk moved.

**Authoring keys** mirror the existing `verify_venue`/`venue` struct-prefix asymmetry: on a stage, write `verify_kind = "landed"` plus a `[stage.landed]` table; on a `[[final_check]]`, write `kind = "landed"` plus a `[final_check.landed]` table. The `[*.landed]` payload:

- `target` (required) — the trunk ref name the delivered commit must be contained in (e.g. `main`).
- `remote` (default `"origin"`) — the remote whose tracking ref (`<remote>/<target>`) is checked alongside `target`.
- `delivered_stage` (required) — the index of the stage whose delivery this assertion is about. On a stage criterion it must be `<=` the declaring stage's own index (self-reference — a landing stage asserting its own delivery — is the normal case and is safe: the delivered head is frozen *before* the verification block runs); a `[[final_check]]` may name any stage, since it runs after every stage.

**A landed check carries no author shell.** `command` / `verify_command` / an explicit `expected_exit` alongside `kind = "landed"` is a `PlanError` — the engine synthesizes the check and owns its exit contract. A landed check's venue is always `"repo_root"` (an explicit `"delivery"` venue is rejected, not silently overridden): the assertion is about the canonical checkout's trunk. A landed **stage** criterion must be `criterion_type = "measurable"` (a landed assertion is objective, never acceptance-review) and needs no `verify_command` of its own — `_validate_substantive_stage` accepts the engine-synthesized command in its place.

**Exit contract.** The synthesized command exits `0` (contained in both refs), `1` (git's genuine "not an ancestor" — the stage genuinely FAILED), or `97` (`state.LANDED_GIT_ERROR_EXIT` — git could not answer: an unresolvable `target`/`remote` ref, an unknown delivered commit, or a broken repository). Every verify site maps `97` to a legible **refusal**, never a stage FAILED — only exit `1` may FAIL a stage. The refusal's *shape* still depends on where it fires, exactly as for a missing check-venue (§ Check venue's refusal-routing paragraph above): at execution (`dispatch`/`record-result`) it is the plain `fix_venue` directive with no node transition; at `verify-final` it routes through `_diagnose_venue_refusal` into `DIAGNOSING` instead.

**Whose commits: the `Task:` trailer.** Before any containment test the command proves the delivery is *this task's*: some line of `git log --format=%B <delivered_base>..<delivered_head>` must be exactly `Task: <plan task id>` (the `Task:` trailer the developer contract already puts on every commit), else it exits `1` with the missing line named on stderr — an empty range is red too. The id is the plan's `[meta].task_id` (stamped on `SessionState.plan_task_id` by `_sync_venue_from_plan` on every route that (re)reads a plan; for state that predates it, read from the plan file, then `state.task_id` as a last resort), not the session's `task_id`, which `start` may name differently. `delivered_base` is `Outcome.delivered_base`, stamped by `record-result` next to `delivered_head` as `git merge-base HEAD <remote>/<target>` and kept once stamped (after landing, HEAD sits on trunk and the merge-base would collapse the range; a merge-base equal to HEAD is never stamped). State without it (`None`) checks the delivered commit's own message instead.

**Delivery venue only.** The range is only meaningful when the delivered commit is on a branch ahead of trunk, so submission (`submission.py`, not `load_plan`) rejects a landed spec whose `delivered_stage` is not verified in the `delivery` venue: a `repo_root`-venue stage freezes a commit that is already on trunk.

**Containment: ancestry, then squash/patch equivalence.** `land-branch.py` is fast-forward only, so when the trunk moved after `record-result` the branch is rebased onto it *before* landing, and the frozen SHA is never an ancestor of the result. Per ref, the check therefore first tries `git merge-base --is-ancestor` (fast path); only its exit `1` continues. With no merge commit in `<ref>..<delivered>`, `git cherry <ref> <delivered>` decides a rebase (no `+` line → contained); a `+` line or any merge falls to the squash test: the patch-id of `git diff <merge base> <delivered>` (merge base = the frozen `delivered_base`, or `git merge-base <ref> <delivered>` for state without one) must be non-empty and equal the patch-id of some `--no-merges` commit of `<merge base>..<ref>` (`git log -p | git patch-id --stable`). Both refs must pass; a git error at any step is still exit `97`. Local and monotone (no fetch; frozen head and base, and a trunk only gains commits, so green stays green). If the frozen commit object is pruned and garbage-collected, a re-check refuses with `97` rather than answering.

**Providers (`provider = "<name>"`, default `"git"`).** The check above is the built-in `git` provider. A delivery in another VCS names `provider = "<name>"` in its `[*.landed]` table (`target` then only has to be non-empty — the git ref-name regex applies to git alone; the delivery-venue rule applies to every provider). The provider is a machine-local module at `${CLAUDE_LANDED_CHECK_PLUGIN_DIR:-<config root>/landed-check-plugins}/providers/<name>.py` (`landed-check-plugins`; `setup-symlinks.sh` creates the directory), loaded lazily through `agentctl/landed_providers.py::load_provider` — only when a non-git spec is used, never at import. Contract: `freeze(venue) -> str | None` returns an opaque delivery token (`record-result` stamps it on `delivered_head`; fail-open, so a missing or broken plugin leaves it unstamped and the check refuses legibly), and `is_landed(token, target) -> bool | None` returns True (landed), False (not yet) or None (cannot decide); once True for a token it must stay True, and the provider owns proving the token is this task's delivery. The rendered check is `scripts/landed-provider-check.py --provider --token --target`, exiting `0` / `1` / `97` for True / False / None-or-missing-or-broken-or-raising, with one stderr line naming the reason. A missing plugin raises `FileNotFoundError`, an unimportable or contract-lacking one `LandedProviderBroken`.

**Known reds** (documented, not fixed): a rebase whose diff text changed (conflict resolution, or trunk edits within a hunk's context); a squash whose combined diff was altered while landing (conflict resolution, a hand-edited squash message with extra changes); a delivery whose combined diff is empty. A landing that merges the branch with a merge commit is green only through ancestry.

**Refusal, not failure.** Besides exit `97`, a landed check refuses when `[meta].repo_root` is unset, or when `delivered_stage` names a stage that has not yet frozen a delivered commit (`record-result` must run for that stage first). There is deliberately no way to point a landed check at a live worktree head — the delivered commit is always the frozen `Outcome.delivered_head` a stage's `record-result` stamped, never a `rev-parse` re-run at verify time.

**Migration recipe.** Convert a free-shell landed check by dropping its `command`/`expected_exit` and declaring the fields above instead:

```toml
# BEFORE (do not copy)
[[final_check]]
label = "trunk contains the delivered commit"
command = "sh -c 'D=$(git rev-parse HEAD) && git merge-base --is-ancestor $D main && git merge-base --is-ancestor $D origin/main'"
expected_exit = 0
```

```toml
# AFTER
[[final_check]]
kind = "landed"
label = "trunk contains the delivered commit"

[final_check.landed]
target = "main"
remote = "origin"
delivered_stage = 1
```

The worked example is [`../tests/fixtures/plan_landed_example.toml`](../tests/fixtures/plan_landed_example.toml), which declares both a landed stage criterion and a landed `[[final_check]]`. A plan already registered in a live session is **not** rewritten in place — a registered plan is frozen, and a landed-check correction is a `replan` (refinement-class: `verify_kind`/`landed`/`verify_venue` participate in the diff, carry-key and coverage-surface comparisons, so the correction is never silently dropped). Machine-local plans under `~/.claude-agent/plans/` are converted opportunistically, not tracked by any in-repo check.

**Resolution requires a landing assertion or a waiver.** A task that delivers a change but never asserts it reached trunk resolves "done" with the change stranded on a branch, so `resolve` (and the confirmed `close`) refuses unless the plan asserts a landing or the omission is excused and logged.

- *Plan-time waiver.* `[meta] landing_waiver = "<why this change lands nothing>"` (parsed permissively by `load_plan`, stored on `PlanMeta` and `SessionState`, rendered by `plan-render`) is declared in the plan, so it is covered by plan review like any other plan field; like `negative_control_waiver`, a waiver-only replan is not a substantive change and is not re-approved by the user. For a plan that sets `delivery_worktree`, `submission.py` requires exactly one of a `kind = "landed"` check (stage or `[[final_check]]`) or a non-empty `landing_waiver`; neither and both are submission violations naming both routes.
- *Resolve blocker.* `gates.landing_gate_active(state)` is on for a SUBSTANTIVE session or one with a `delivery_worktree`. While active, a plan that asserts no landed check and has no plan waiver blocks `resolve` (added in `cmd_resolve` before the gate is logged, so a refused resolve writes no quality row and moves no node; deliberately not part of `gates.resolution_blockers`). Without a `delivery_worktree`, `--landing-waiver '<non-empty reason>'` on `resolve` (and on `close`, which threads it to both its probe and its confirmed resolve) unblocks it; an empty or whitespace waiver is itself a blocker. With a `delivery_worktree` the resolve-time waiver is refused — the excuse must come from the approved plan via `replan`, not from the actor who knows the outcome.
- *Unlanded-branch blocker (git delivery venues only).* While active, with a `delivery_worktree` that still exists as a git work tree and no plan waiver, `resolve` probes — network-free, through the injected `Runner` — whether every non-merge commit of `merge-base(HEAD, <remote>/<target>)..HEAD` is contained in `<remote>/<target>` by ancestry, `git cherry`, or the squash patch-id test (`state.landed_containment_script`, the same containment the landed check applies). `<remote>`/`<target>` come from the first git-provider landed spec, else `origin/main`. An uncontained commit blocks, naming the branch and `python3 scripts/land-branch.py`; a probe error blocks (fail closed); a removed worktree — what `land-branch.py` leaves — does not. Other VCS providers are not probed here.
- *Override and logging.* `AGENTCTL_LANDING_GATE=1` forces the gate on, `=0` forces it off (the test suite's default, via an autouse fixture). Every successful resolve logs `state.log("landing_gate", waiver, waiver_source = "plan" | "resolve" | None, override)` and the quality row always carries `landing_waiver`, `landing_waiver_source` and `landing_gate_override`; an active override is also surfaced in the resolve Directive (`data["landing_gate_override"]`), never silent.

**Resolution ask marker.** The 1-5 quality rating is asked only after the work has landed and final verification has passed, and `resolve --quality` enforces the last link of that order from two machine records instead of prose discipline: the engine's `verify_final` event and the harness transcript.

- *Marker.* `RESOLUTION_ASK_MARKER = "[resolution-ask]"` (in `state.py`, beside `SHOW_FULL_PLAN_MARKER`). The `verify-final` success Directive carries it as `data["resolution_ask_marker"]` and says to embed it in an option label or description of the resolution `AskUserQuestion` that carries the rating. The option walk is `lib/transcript_turns.has_marker_option`, shared with `hook-plan-delivery-gate.py`.
- *Ordering rule.* `verify-final` logs `state.log("verify_final", at=<epoch float>)` — the history's own `ts` is second-precision, too coarse to order an ask in the same second. `gates.resolution_ask_gate_active(state)` is on for a SUBSTANTIVE session; while active, `resolve` adds a blocker (prefixed `resolution ask:`, before the gate is logged) unless the session's transcript — derived from the session id via `_present_plan_transcript`, never supplied — holds an **answered** (a later non-error `tool_result`) `AskUserQuestion` carrying the marker whose timestamp is strictly after the latest `verify_final` `at`. Three blockers are told apart: no marked ask at all, a marked ask only before verify-final, a marked ask after it that is unanswered. A `verify_final` event without `at` (state written before this rule) blocks with "re-run verify-final".
- *Escape.* `--resolution-ask-unverifiable '<reason>'` (on `resolve` and, threaded through, `close`) is accepted **only** when the transcript is unlocatable or unreadable; a readable transcript that lacks the ask refuses it. Without a confirmer, `close` treats the `resolution ask:` blockers as part of the gate-stop (the ask cannot have happened yet); with `--confirmed-by` its probe reports them. Known residual: "unlocatable" is decided by a lookup the caller's environment can influence (e.g. `CLAUDE_CONFIG_DIR` pointing at an empty projects root), so the escape is logged, not unforgeable — the same trust level as the env override.
- *Override and logging.* `AGENTCTL_RESOLUTION_ASK_GATE=1` forces the gate on, `=0` off (the test suite's default, via an autouse fixture). The quality row always carries `resolution_ask_gate_override` and `resolution_ask_unverifiable`; an active override or escape is also logged as `state.log("resolution_ask_gate", override, unverifiable)` and surfaced in the resolve Directive (`data["resolution_ask_gate_override"]` / `data["resolution_ask_unverifiable"]`), never silent.

## Plugins

The core spine above is a **closed monolith** — its nodes and gates are the contract every session obeys, edited only via `self-improvement`. But a skill/tool/specialization whose own workflow is deterministic (most acutely `tracker-management`) can hang a **sub-state-machine** off that spine without touching the three core literals (`machine.TRANSITIONS`, `gates.GUARDIANS`, `cli.COMMANDS`). That mechanism is [`plugins.py`](plugins.py).

A `Plugin` (registered into the module-level `REGISTRY` at import) carries:

- **observers** — `{event: fn(state, bag) -> [PluginDirective]}`. Each coordination command maps to one event (`EVENT_FOR_COMMAND`); after the command runs, `cli._fire_plugins` fires the event on every *active* plugin and appends any `PluginDirective`s under `Directive.data.plugin_directives` (nudges the coordinator surfaces). A plugin-less session is byte-identical — no key added.
- **gates** — `{core_gate: fn(state, bag) -> [blocker]}`. A plugin folds extra blockers into an existing core gate (`resolution` / `plan_approval`) via `plugin_gate_blockers`; it never adds a new gate.
- a per-session **bag** — `state.plugins[name]`, opaque to the core, seeded by `state_factory`.
- a **lifecycle** — `scope` `task` | `phase` and an optional `terminal(state, event)` predicate that auto-retires the plugin mid-task (bag archived into `state.plugins_archive`).

**Registration vs activation** are distinct: registration (import-time, into `REGISTRY`) means the engine *knows* the plugin; activation (`agentctl plugin-activate --plugin <name>`, presence of the name in `state.plugins`) means it *participates in this session*. The owning skill activates on invocation; `plugin-deactivate` is the manual escape hatch, `plugin-record` marks a publish-style phase done. **State is per-session** (keyed by `session_id`), so subtasks share the session's active set while spawned/parallel agents are isolated.

**Engine auto-activation for skill-less plugins.** A plugin need not have an owning skill to activate it. Each `Plugin` may carry an optional `auto_activate(state) -> bool` predicate; `auto_activate_for(state)` — called by `cmd_classify` once the route resolves to SUBSTANTIVE — activates every predicate-true plugin not already active or archived. It is idempotent and **name-free** (no plugin name hardcoded in `cli`), so a universal obligation rides the engine via a general predicate rather than a special case. `dummy`/`tracker` leave `auto_activate=None` (unchanged); a chat/small session activates nothing.

**Scope fence (deliberate):** a plugin introduces **no new `Node`** and **no new gate** — it only reacts to existing transitions and extends existing gates. New control-flow primitives belong in the core spine via `self-improvement`, not in a plugin. This keeps the lifecycle the core can reason about finite.

Two plugins ship in-tree: a built-in **`dummy`** (proves the framework end-to-end with zero core edits; phase-scoped, exercises auto-retire) and **`tracker`** ([`plugins_tracker.py`](plugins_tracker.py)) — the first real consumer. `tracker` observes `submit_plan`/`record_result`/`replan`/`resolve` to surface `publish_*` directives and gates `resolution` until the mandatory ticket publications (plan + result + the ticket status transition) are recorded; the `tracker-management` skill owns the comment content and transport (engine owns *when*, skill owns *what*). It also observes `partition`/`partition_units` to **materialize delivery units** (non-blocking nudges, never gates): on a `recommended` verdict it proposes the delivery structure (subtickets vs several PRs) citing the fired markers, and for every recorded unit with `mode == subtask` and no `ref` it nudges to create a subticket and re-record the unit with the key as `ref` (the nudge converges silent once `ref` is present). `verify-agentctl.py` asserts both register and that the tracker gate is wired.

**Per-stage journal gate.** The three whole-task publications above prove the ticket got a plan, a result, and a status transition — they say nothing about whether a reader can reconstruct what happened *along the way*. On `record_result` with `status == passed`, `_observe_record_result` looks up the stage that just passed (`_last_passed_stage_index` scans `state.history` backward for the newest `record_result`/`passed` entry, because by the time the observer runs `state.current_stage` has already been reset to `None`) and checks whether that stage declared `output_artifacts` without an `ephemeral_artifacts_waiver`: if so, the returned nudge demands a **substantive** per-stage entry (figures/caveats/every artifact, not a one-liner) discharged via `plugin-record --plugin tracker --phase progress --stage <n>`, composing the bag key as `progress:<n>` so multiple stages don't collide under one `progress` key. `_journal_gate` (folded into `_resolution_gate` alongside the existing `_publish_gate` — `Plugin.gates` allows only one callable per core-gate name) enumerates every PASSED, artifact-declaring, non-waived stage via `_passed_artifact_stages` and blocks `resolution` on any whose `progress:<n>` key is still missing from `published_phases`, naming every outstanding stage index in one blocker line. `verify-agentctl.py` asserts the combined gate is wired; [`../tests/test_tracker_plugin.py`](../tests/test_tracker_plugin.py)`::test_journal_gate_blocks_one_stage_at_a_time_then_clears` exercises the mechanics end-to-end.

A third plugin, **`experience`** ([`plugins_experience.py`](plugins_experience.py)), is the **skill-less** consumer and the first user of `auto_activate`: its predicate is `state.weight_class == SUBSTANTIVE`, so every substantive task gets it without any owning skill or manual `plugin-activate`. It observes `resolve` to surface a `record_experience` nudge (the `search → extend-vs-new → write` flow) and gates `resolution` until the leaf flow is recorded — bag complete when `searched` **and** (`recorded` **or** `skipped`). A skip must carry a reason: `plugin-record --plugin experience --phase skipped` requires `--note`, so declining a leaf below the quality bar is a conscious, recorded act rather than an inescapable block. `plugin-record --phase <searched|recorded|skipped>` marks each phase; the plugin auto-retires on the passing `resolve`. `verify-agentctl.py` asserts it registers and wires the `resolution` gate. This closes the deferred experience-search backlog item — the search-before-record step is now engine-gated, not prose-only.

A fourth plugin, **`ledger`** ([`ledger.py`](ledger.py) + [`plugins_ledger.py`](plugins_ledger.py)), is a **skill-less** consumer like `experience`, but for a different discipline: a reasoning/research deliverable is not resolved by "tests pass" — it is resolved by every load-bearing claim it makes (a number, a DECISION, a JUDGMENT) being grounded (`axiom` with a `source`), derived (`derivation` with acyclic `premises`), or explicitly marked (`assumption` with a `basis`). Its `auto_activate` predicate is `weight_class == SUBSTANTIVE and deliverable_kind in {reasoning, mixed}` — `deliverable_kind` is a `classify`-time field (`--deliverable-kind`, § Commands) read *before* `auto_activate_for` runs, since a reasoning-vs-code distinction cannot be judged after the fact. Division of labour: **which claims exist is the coordinator's cognition; whether the claim bag is structurally closed is the engine's.** `ledger.validate_ledger` is a pure closure check reusing the DFS-3-colour + dangling-edge form of `plan._validate_graph` (reused deliberately, not imported) — it never judges whether a claim's content is *true*, only that every load-bearing claim has a source/premises/basis and the premise graph is acyclic with no load-bearing claim resting on a non-load-bearing premise. **Enumerating which decisions/judgments exist is perception, not a form, so it is deliberately not regex-extracted** — a rejected formal proxy that would swap the substantive problem for surface matching. Instead the bag also carries `candidates`: an enumeration pass (the coordinator's own read, or `ledger-enumerate`'s independent `claude -p --model sonnet` advisor pass over the outgoing artifact) *raises* candidates, and `ledger.validate_candidates` gates on their **disposition** — `recorded` (linked to an existing load-bearing claim) or `dismissed` (with a reason) — never on their content. A third deterministic blocker, the bag's `enumerated` flag, makes running the cross-check itself structurally mandatory. Together the three checks (claim closure, candidate disposition-completeness, cross-check-has-run) fold into the `resolution` gate exactly like `experience` and `tracker` — no new node, no new gate. `verify-agentctl.py` asserts it registers and wires the `resolution` gate. Honest residual (recorded in [`memory-global/leaves/formalization-ladder-l1-l3.md`](../../memory-global/leaves/formalization-ladder-l1-l3.md)): the cross-check's recall is below 100% and a dismiss reason cannot be content-checked — enumeration is *narrowed*, not *closed*; the remaining gap is Layer B (CLAUDE.md / planner) discipline's to catch.

A fifth plugin, **`premise`** ([`premise.py`](premise.py) + [`plugins_premise.py`](plugins_premise.py)), is the **first plugin keying the `plan_approval` gate** (all four above key `resolution`) — because a false premise baked into a plan has already cost the execution long before resolution. It is the plan-approval-axis twin of `ledger`: `ledger` closes claims in the *deliverable*, `premise` closes the *questions the plan rests on*. Its `auto_activate` predicate is `weight_class == SUBSTANTIVE` **alone** — unlike `ledger` it does **not** condition on `deliverable_kind`, since a false premise harms a code plan as much as a reasoning one, so every substantive session arms it with nobody hand-arming it (`AGENTCTL_PREMISE=1/0` force-on/off). Division of labour, same as `ledger`: **which questions a plan raises is the coordinator's cognition; whether the recorded set is structurally dispositioned is the engine's.** `plugins_premise.premise_blockers` folds four blocker families into `plan_approval`: per-question disposition-completeness (an `open` question never survives approve; an `escalated` one needs non-empty `own_research`; a `researched` one needs source+derivation; an `assumed` one needs basis+risk), stage-key freshness (a question bound to `stage:<n>.<element>` via `stage_question_key` is stale once THAT element's own fields change — a stamp against the whole stage, which is all an older engine could write, still discharges; `question-rebind` re-affirms either; `plan.goal`/`plan.done_criterion` targets are rebind-exempt), the `enumerated` flag (the `question-enumerate` cross-check must have run against the current plan content), and **order coverage** (below). Enumerating which questions exist is perception, deliberately **not** regex-extracted — same rejected proxy as `ledger`'s candidates.

**Order coverage — the plan against the order it answers.** The three families above close the questions a plan *raises*; they say nothing about whether the plan covers the *order*, so a narrowing chosen at authoring time was never compared to anything: every downstream gate checks the plan, and a green verdict over a silently halved scope is honest about a domain nobody asked for. The `order_elements` bag half closes that. `order-raise` records each element **of the order**; `order-dispose --as covered --stage <n>` / `--as cut --reason <text>` disposes it; `premise.validate_order_elements` (pure, like the question validator) refuses approval on an undispositioned element, a `covered` element naming no stage or a stage the plan does not have, a `cut` element with no reason, and — the empty case — a submitted plan with an empty order bag at all. Note the deliberate **asymmetry with the question bag**: an empty question set is legitimate (a plan may raise nothing), an empty order set is not (a plan always answers an order). Coverage is also made **visible before the user approves**: `premise.render_coverage_block` is the single generator of a `[scope]` block carrying the plan's stage count (element C — plan size, seen before approval, riding the header rather than a second mechanism) plus one line per covered and per cut element; `present-plan --kind essence` fast-fails when the rendering does not contain it, handing the block back verbatim rather than stamping, and the gate re-derives it from **live** state and requires the stored essence receipt to contain the CURRENT block — the only way to catch an element cut *after* presentation, which the `plan_sha256` binding structurally cannot see because the bag is not plan bytes. Past this containment check, `present-plan` refuses an essence while premise blockers stand (an open question, an undispositioned element, an un-landed enumeration cross-check) — see the `plan-review` row above for the full shape and its accepted cost. Mechanical line-containment over engine-generated text only; the essence's free prose is never read (`regex-not-for-semantic-classification`). Honest residuals are in the same leaf: the elements are the coordinator's own reading of the order (no independent enumerator — the `question-enumerate` analogue is deliberately absent, so nothing stops enumerating them off the already-written plan, which makes coverage trivially total), `--reason` and `--element` are free text, and `--stage <n>` proves a stage *exists*, never that it *answers* the element. The countermeasure is the same one: the thinker plan-review, reading `order-list --format md`. `verify-agentctl.py` asserts it registers and wires the `plan_approval` gate. Honest residual (recorded in [`memory-global/leaves/question-provenance-gate.md`](../../memory-global/leaves/question-provenance-gate.md)): recall < 100%, fabrication/decoy/junk-retire are perception, and — load-bearing — a run whose runner FAILED no longer flips the `enumerated` flag for free: since stage 5 it BLOCKS `approve`/`replan` until a typed `question-enumerate-escape` is recorded against the live plan digest, with the discharge made countable via `plugins_premise.escape_counts` (surfaced in `agentctl status` and refusal payloads, three buckets: `runner_failure` / `manual` / `not_landed`). What survives, narrowed rather than closed: an ABSENT advisor and a ZERO-PAIR SUCCESSFUL run both still discharge silently by design (F3b, now naming only these two residual cases), the escape count is a number someone must choose to look at, and detaching the producer makes the check eventually consistent rather than synchronous (a plan approved right after submission can meet a not-yet-landed refusal); plus a designed-in incentive to park questions on the rebind-exempt `plan.goal` (F7). The countermeasure for all of these is the thinker plan-review reading `question-list --format md`.

**Question materiality — a raised question names the control its answer could flip.** A question nothing in the plan turns on still had to be dispositioned, so the gate's cost was paid for questions that could not have changed the plan either way. `question-raise --control <name>` closes that by making the question say which control it bears on, and the check splits along the standard rule/perception line. The **rule** half — does that control EXIST in this plan — is decidable from the plan document, so the engine decides it, using the same resolver `../check-order-coverage.py` uses ([`controls.py`](controls.py)); the coverage caller keeps passing exactly its three grammars (`stage <n> verify_command`, `final_check <n>`, `stage <n> landed assertion`) and only the materiality caller adds the two it needs (`stage <n> done_criterion`, `order requirement <id>`), because a name outside the coverage grammar is a coverage FAILURE and widening that set would move the verdict on every plan in the tree. The **perception** half — would the answer really move that control — is `advisor.judge_question_materiality`, prefiltered on a resolvable control being named, fail-open, surfaced as an advisory and never blocking; nothing regex-classifies the question's text, which is only ever a structured control field. Enforcement sits at the **write** seam (`cmd_question_raise`), deliberately not at the gate: every question persisted before the flag existed carries no control name, and a gate demanding one would convert each of them into a blocker — the exact opposite of the requirement's purpose, pinned by a test that a control-less question still discharges. The same rule reaches the enumeration channel: a candidate addressed to a stage the plan does not contain is recorded `dismissed` with the one countable reason `premise.CANDIDATE_IMMATERIAL` instead of being raised, while a plan-level or unparseable address stays `raised` (dismissing on an address we could not read would discard the question).

A sixth plugin, **`review_dispatch`** ([`plugins_review_dispatch.py`](plugins_review_dispatch.py)), is the **proactive** counterpart to two pre-existing **reactive** preconditions — it names a required specialist spawn the moment the obligation is minted, instead of leaving the coordinator to remember it until a downstream gate refuses. It covers two slots through one module-level table, `_SLOT_SPECIALIST = {"plan_review": "thinker", "code_review": "code-reviewer"}` — the shared extension seam for any future non-stage-actor specialist obligation. Its `auto_activate` predicate is `weight_class == SUBSTANTIVE` alone (`AGENTCTL_REVIEW_DISPATCH=1/0` force-on/off), same as `premise`. **`plan_review` slot:** on `submit_plan` (PLAN_READY) it reuses `gates.plan_review_blockers` verbatim and, when non-empty, emits a blocking `PluginDirective` naming the thinker spawn — the same obligation `approve`/`replan`/`present-plan --kind essence` already refuse reactively (see `plan-review` above), now surfaced at the point it is first owed. **`code_review` slot:** on `dispatch` it reuses `gates.code_review_blockers` verbatim for the just-dispatched active stage and, when non-empty on a `needs_control()` (`spawn:developer`) stage, emits a blocking directive naming the code-reviewer spawn — the same obligation `record-result` refuses reactively (see *Code-review gate* above). Deliberately does **not** observe `replan`: an observer's signature is `(state, bag)`, never `args.plan` (the corrected plan a replan applies), and `cmd_replan` early-returns without `store.save` on a rejected replan, so a `replan` observer would reload stale state via `_fire_plugins`'s `store.load` and could name the wrong plan version — `cmd_replan`'s own inline rejection already names the correct target reactively. `dispatch`, by contrast, is a safe observer target: `cmd_dispatch` saves state before returning on every non-preview path, so the reload always reflects the just-dispatched active stage. `gates={}` — no new gate; enforcement stays entirely in the two pre-existing pure gates, and `blocking=True` on the directive is an advisory label the coordinator surfaces, not a control-flow branch (nothing in `cli` reads `.blocking`). Like every `auto_activate` plugin it arms only at `classify`; an already-classified in-flight session does not retro-activate it. `verify-agentctl.py` asserts it registers with `observers == {submit_plan, dispatch}` and `gates == {}`, that both triggers fire on an unmet gate and stay silent once satisfied, and that `cmd_record_result` refuses a SUBSTANTIVE `spawn:developer` PASSED without a bound passing `CodeReview`.

A seventh plugin, **`obligations`** ([`plugins_obligations.py`](plugins_obligations.py)), is the **conformance ledger**: a single, generic resolution-time checkpoint over every *registered* blocking `PluginDirective` the engine has emitted, so "did the coordinator actually take an expected action" has one owner instead of N scattered per-command reactive gates the coordinator must each remember to satisfy. Unlike every plugin above it contributes **no observers** — it rides `plugins.fire()`'s own post-observe seam (the ONE point that sees every active plugin's fired directives for an event) via a generic delegate call to its module-level `mint(state, fired)`, so `fire()` itself stays plugin-agnostic. `mint` is deliberately **SELECTIVE, not universal**: it records a fired directive into the ledger only when `blocking` is set AND its `action` is a key of the module-level `_DISCHARGE` registry — today `{"spawn_thinker_review": …, "spawn_code_review": …}`, each value reusing the producing plugin's own reactive gate verbatim (`gates.plan_review_blockers` / `gates.code_review_blockers`) as the discharge oracle, so the ledger and the gate it mirrors can never disagree about whether an obligation is still owed. `_DISCHARGE` is the **single source of truth** for "what is a conformance obligation" and the extension seam for a future one: register a new action there (reusing that action's own gate/check as the oracle) and it is tracked with zero other code changes. Universal mint was considered and **rejected** — `premise`'s `close_questions` (on `approve`) and `experience`'s `record_experience` (on `resolve` itself) are also blocking directives that auto-activate on every SUBSTANTIVE session; sweeping them in would mint `record_experience` at the very event that would need to discharge it, permanently deadlocking `resolution` for nearly every substantive task (`test_obligations.py`'s deadlock-regression test pins this). Its `auto_activate` predicate is `weight_class == SUBSTANTIVE` alone (`AGENTCTL_OBLIGATIONS=1/0` force-on/off), same as `premise`/`review_dispatch`. The `resolution` guardian walks the ledger's open entries and re-checks each one's `_DISCHARGE` oracle against **live** state (not a cached snapshot), so a bound passing review clears the blocker immediately without needing the minting event to re-fire. **Honesty note (belt-and-suspenders today):** for the two obligations that exist right now, this checkpoint is redundant with pre-existing enforcement — `plan_review_blockers` already gates `approve` and `code_review_blockers` already folds into `record-result --status passed`, so both are necessarily discharged before every stage can reach PASSED, the precondition for reaching `resolution` at all. Its standing value is (1) one explicit, auditable resolution-time conformance checkpoint instead of trusting each reactive gate was hit on the path actually taken, (2) continuous re-surfacing of an owed action every event until it is discharged, and (3) the ready-made extension home — one `_DISCHARGE` entry — for the next blocking directive that has no reactive gate of its own. `verify-agentctl.py`'s `check_obligations` drives this live (`plugins.fire('submit_plan', …)` on an unreviewed plan → `plugin_gate_blockers(state, 'resolution')` blocks → a bound passing `PlanReview` clears it) and statically pins `set(_DISCHARGE)` to the two known actions — a literal tripwire that fails the build the moment `_DISCHARGE` changes, forcing a conscious pin update rather than a runtime fail-closed that could reintroduce the deadlock a universal mint would cause. No schema bump: the ledger lives in the free-form `state.plugins['obligations']` bag like every other plugin's.

**Plugins vs hooks — two determinization surfaces.** A *plugin* hangs off the coordination spine: it fires on engine commands and folds gate blockers, so it fits obligations that live *on* the task lifecycle (publish-on-resolve, record-on-resolve). Obligations that fire *off* the spine — at tool-write time or prompt time — are **hooks** instead, because there is no coordination command to observe. Two ship for memory work, both **non-blocking** (exit 0 always, preserving memory's gate-exempt status):

- [`hook-memory-consistency.py`](../hook-memory-consistency.py) (`PreToolUse` Write/Edit) classifies the target as a memory leaf in any of the **three** scopes (instruction-repo `memory-global/leaves/`, project `.claude/agent-memory/`, personal `~/.claude-agent/projects/*/memory/` — the last is invisible to `verify-leaf-structure.py`) and surfaces missing/malformed frontmatter (`name`/`description`/`type`) plus an index-pointer reminder. It only informs; it never denies.
- [`hook-experience-record-reminder.py`](../hook-experience-record-reminder.py) (`UserPromptSubmit`) reads the `experience` plugin bag and nudges to record before close — loudest at `node == RESOLUTION` (naming the exact missing phase and the `record-experience.py search …` → `plugin-record` commands), a soft nudge otherwise, silent when the flow is complete or the plugin is inactive. It mirrors `hook-tracker-publish-reminder.py`.

## Loop primitives: the turn-end gate, the acceptance judge, and composition with `/goal`

Three primitives adopted from Claude Code's loop taxonomy, plus one deliberately deferred. The first two are **landed mechanisms**; the third is a recorded non-decision.

### The turn-end Stop gate (the exit gate)

[`hook-turn-end-gate.py`](../hook-turn-end-gate.py) runs on the harness **Stop** event and is the **exit** counterpart to `hook-state-gate.py`'s **entry** gate on production edits. Its architecture mirrors `gates.py` one level up: an impure shell does all I/O and freezes a `TurnContext`; a module-level `TURN_GUARDIANS` registry maps a guardian name to a **pure** `(TurnContext) -> list[str]` function. Three guardians ship — `self_improvement_blockers` (fires on a corrective-feedback turn where neither `self-improvement` nor `overcome-difficulty` was invoked), `long_job_autowake_blockers` (fires when the turn launched a detached long-running external job — the shared `long_job_detect.py` launch scan over the turn's Bash commands — but armed no harness-tracked auto-wake, i.e. no `Bash(run_in_background:true)` waiter and no `CronCreate`; `ScheduleWakeup` is excluded because it no-ops outside `/loop`, the very silent-idle failure the guardian catches), and `resolution_turn_blockers` (fires only on a SUBSTANTIVE session whose stages are all PASSED, the resolution gate is unpassed, and the ending turn shows no closure being sought — neither an `AskUserQuestion` nor an armed `sleep >= 2` background deferral timer, the latter detected via the shared `timer_arm_detect.py`).

Three loop-safety properties live **once** in the shell, not per obligation: a `stop_hook_active` short-circuit, a durable per-message marker keyed on `sha256(session + triggering user text)` (so the same message blocks at most once), and fail-open on any malformed/empty/unreadable input. Every fired guardian is **aggregated into ONE block** whose numbered reason names each unmet obligation, so N obligations cost exactly one extra model turn. The trade this buys is stated in the hook: aggregation gives up per-obligation *enforcement* (if the model addresses only obligation 1 of 2, the second stop is allowed) in exchange for turn-boundedness — accepted because a Stop hook that can block a session more than once per message has unbounded blast radius, and because the block text names every obligation. When `self_improvement` and `resolution` co-fire, resolution is named **last** and is enforced only when it is the sole fired guardian; `hook-resolution-reminder.py` stays registered on `UserPromptSubmit` as the complementary advisory for the residual co-firing hole. `verify-agentctl.py`'s gate-to-hook check maps the resolution gate to this hook.

### The acceptance-review judge

For a `criterion_type = acceptance_review` stage, `record-result --status passed` invokes an external cheap judge (a fail-open `claude -p` on the small-fast tier via `advisor.subprocess_runner`) that reads the stage's expected image plus the executor's `--observation` and returns a yes/no verdict. The verdict is recorded on `SessionState` bound to `sha256(observation)` by `cmd_stage_review` (a `StageReview` dataclass), exactly as `plan_review` binds a plan review to the reviewed plan's bytes — defeating "get a pass, then rewrite the observation".

The gate itself is a **pure** function, `gates.acceptance_review_blockers(state, stage)`, that reads only the recorded review (and any recorded `JudgeBypass`) — no subprocess, no LLM, no network. It refuses PASSED when the gate is active (see below) and no matching review or bypass exists, the `observation_sha256` does not match, or the verdict is `revise`/unknown; a `verdict=override` clears only with a non-empty reviewer **and** note. Like `plan_review_blockers` it is an **internal command precondition and deliberately NOT a member of `gates.GUARDIANS`**, so `verify-agentctl.py`'s check needs no new hook and `gates.py` still imports no subprocess. Scoped to SUBSTANTIVE sessions with its own kill switch `AGENTCTL_STAGE_REVIEW` (not routed through the advisor's cost knob, because a mandatory gate's off switch must not be the advisor's optional one).

`agentctl stage-review` (the CLI recorder behind the override escape) refuses on the **identical** predicate, `gates.stage_review_active(state)` — not on `criterion_type` — so the override escape is available for any stage the gate itself can deadlock, including a `measurable`-criterion stage on a SUBSTANTIVE session (Defect 2 already broadened the *gate* past `acceptance_review`-only stages; the escape hatch had not followed until GitHub issue #145). Before this widening the only escape for a non-`acceptance_review` deadlock was the strictly weaker, unattributed `AGENTCTL_STAGE_REVIEW=0` kill switch.

### Judge after the check

R4 fixed a fail-open-judge / fail-closed-gate mismatch: `advisor.acceptance_judge`'s docstring always promised fail-open (a timeout, malformed answer, non-zero exit or disabled judge returns `(None, reason)`, never a false pass), but the pre-R4 gate treated a `None` verdict exactly like an unreviewed stage and blocked on it — an infra failure or a killed judge process silently became a hard stall the operator had to notice and clear by hand with `stage-review --verdict override`. `cmd_record_result` now addresses this with three changes, in order:

1. **The mechanical check runs first.** A stage's `verify_command` (or `kind = "landed"` check) is executed — *before* the judge is ever consulted. Only a `verify_command` check may be served from the green-check cache below; a `kind = "landed"` check is never cached and always re-runs. A red check routes straight to DIAGNOSING without spending a judge call; only a green check (or a stage carrying no check at all) reaches the judge.
2. **A green `verify_command` check is cached by venue-tree identity.** `_venue_tree_identity(cwd, runner)` lets git itself compute the content identity rather than hand-rolling one: it resolves the venue's real index path (`git rev-parse --git-path index`, worktree-aware), copies it to a disposable temp index, then runs `git add -A` and `git write-tree` against that copy (via a `GIT_INDEX_FILE=<tmp>` env prefix on the runner's argv, since the `Runner` protocol is argv-only) to get the tree git itself would produce from every tracked and untracked path — the real index and working tree are never touched, and the temp index is always removed. The real **object store** is untouched too: `add -A`/`write-tree` write new blob/tree objects for any new or changed content, so the same env prefix also sets `GIT_OBJECT_DIRECTORY` to a second disposable directory alongside the temp index (removed with it) and `GIT_ALTERNATE_OBJECT_DIRECTORIES` to the venue's real objects dir (`git rev-parse --git-path objects`, worktree-aware — resolves to the one shared store from a main checkout or any of its linked worktrees), so git can still read every already-committed object without writing a byte back into it. Every git call in the sequence carries a bounded timeout (`_VENUE_IDENTITY_GIT_TIMEOUT_S`, 30s); a timeout is treated exactly like any other git failure below. Identity = HEAD sha + that tree sha. It fails safe (returns `None` — no caching, the check always re-runs) whenever any git call in the sequence times out or returns non-zero or empty output, and whenever the temp index contains a gitlink (mode 160000, an embedded repo git cannot see inside without recursing). `_cached_check_hit` compares the result against the identity recorded on the stage's last GREEN run. A repeated `record-result` call on an unchanged tree skips re-running the command and goes straight to the judge — but the judge itself is **always** re-queried, never cached, since only the check's mechanical outcome is a function of tree state. A red result is never cached, and any tree movement (even a staged-only edit, or a content edit to an already-untracked file, including a non-ASCII filename) invalidates the cache and forces a fresh run. Three documented limits: the cache assumes the check reads only the venue tree — a check that also reads files outside it (the plan TOML, `proposals.json`, ...) can be served stale even though its own venue is unchanged; a change confined to a `.gitignore`d file is invisible to `git add -A` exactly as it would be to a real commit, so it never moves the identity and never invalidates the cache; and a checkout whose untracked tree itself contains linked worktrees or embedded repos (e.g. the canonical checkout with its `.claude/worktrees/*` subtrees) stages each one as a gitlink the moment `add -A` reaches it, so the identity always resolves to `None` there — by design, not a missed cache opportunity.
3. **A `None` verdict now fails genuinely open.** When `advisor.acceptance_judge` returns no verdict — killswitch, no runner, timeout, non-zero exit, empty output, or an unparseable answer — `cmd_record_result` records a `JudgeBypass(kind="fail_open", note=<the judge's own reason>, observation_sha256=...)` and lets the pass **proceed immediately**, rather than blocking until a human notices and runs `stage-review --verdict override`. A genuine `revise` verdict (the judge *answered* and said no) is unaffected: it still blocks and still needs an explicit override. `gates.acceptance_review_blockers` accepts a `fail_open` bypass bound to the current observation's sha256 in place of a passing `StageReview`.

Every decision point is logged: `advisor.acceptance_judge` now shares `_classify`/`_record_result`/`_record_raised`/`_judge_unavailable` with `judge_binary_ask`, so every call — genuine verdict or fail-open — writes a `judge_ledger` `decided` line (previously it called `begin_attributed_call` but never `decided`, so the ledger recorded 0 decided lines over 2284 judge calls in the judge ledger). `state.log` gains `acceptance_judge_verdict` (stage, verdict, reason, `observation_sha256`) for every verdict including `revise`, `acceptance_judge_fail_open` (stage, reason) for every fail-open bypass, and an unconditional `record_result_attempt` (stage, attempt number) on **every** `record-result` call, including ones a gate blocks before any verification runs — a diagnosing session scanning history sees every attempt made, not just the ones that got past the first gate.

Honest limit: unlike Anthropic's `/goal` evaluator (which the *harness* invokes and the agent cannot reach), our judge is **agent-invoked**, so `AGENTCTL_STAGE_REVIEW=0` restores "do not lie to exit" one env var away. We make the bypass impossible to take *silently* rather than impossible to take: every bypass (kill switch, override, or fail_open) is recorded on `SessionState.judge_bypassed`, never cleared by a later passing review, and `verify-final` refuses a clean bill without printing it — so it reaches the user's resolution confirmation instead of dying in a log.

### Composition with `/goal`, and the four places this engine stays stronger

`/goal` and `agentctl` are **orthogonal** and compose. `/goal` is a session-scoped prompt-based Stop hook: a small fast model evaluates a natural-language condition each turn and returns yes/no + a reason. It keeps the *session looping*; `agentctl` decides *what is legal inside that loop*. A `/goal` evaluator naturally sits as a **reader** of our `[[final_check]]` commands — it can only judge what the agent surfaced in the conversation and cannot call tools, whereas the engine **executes** those commands and checks `expected_exit`.

Four properties this system must not regress toward a prompt-based loop:

| Property | agentctl | prompt-based `/goal` loop |
|---|---|---|
| Criterion | execution-verified — `verify_command` / `final_check` with `expected_exit` | reads a *report* of a test run it cannot run |
| Numeric bounds | checked by code (`max-recursion-depth`, `_MAX_PLAN_STACK`, budget tiers) | a turn cap living in the condition *text*, model-judged |
| Production edits | an **entry** gate (`hook-state-gate.py`) **and** an **exit** gate (the turn-end gate) | none |
| Divergence | a typed difficulty object (FAILED → DIAGNOSING → declare/investigate/critique → replan with a coverage gate) — the loop *learns* | repeats the same prompt |

### Deferred: the time-axis scheduler primitive

`/loop`'s local interval and `/schedule`'s cloud routine are **explicitly deferred, not built**. Rationale: (1) we drive long jobs with a detached zero-token poller for durability **plus a harness-tracked `Bash(run_in_background)` waiter for in-session auto-wake** per [`memory-global/leaves/long-job-monitoring.md`](../../memory-global/leaves/long-job-monitoring.md) — note that `ScheduleWakeup` is **gated off outside `/loop`** and silently no-ops there, so it is *not* a reliable auto-wake path in an ordinary session (observed 2026-07-12: a detached job left to ScheduleWakeup idled the main thread until the user pinged); the harness-tracked waiter is what closes that gap without a scheduler; (2) a routine that survives with no open session is a harness capability we do not currently need; (3) a scheduler would duplicate the harness rather than determinize anything of ours. Tracked so it is revisitable rather than forgotten: [`sthe0/claude-agent-instructions#28`](https://github.com/sthe0/claude-agent-instructions/issues/28) (Core `backlog`). If a concrete recurring need for a session-independent scheduled routine appears (a cadence neither the waiter nor `ScheduleWakeup` can serve), that item is where the evidence should land and reopen the decision.

## Effort divergence

*Difficulty removed:* a task can run many times over its own plan and nothing in the system notices. The only detector is the user's attention — the resource the engine exists to spend less of. [`effort.py`](effort.py) is the measurement half; the fire sites in [`cli.py`](cli.py) are the acting half. When a session's ACTUAL effort has run past what its CURRENT plan claims the work costs, by the configured multiple, the engine enters the ordinary `declare → investigate → critique → replan` cycle by itself: the chosen norm is visibly missing something essential about the real situation, and that is a difficulty like any other.

**Four scales, two shapes.** The estimate is derived from the plan; the actual is accumulated by the engine.

| Scale | Shape | Estimate — from the CURRENT plan | Actual — accumulated |
|---|---|---|---|
| `spend` | ratio | Σ `budget-<tier>-usd` over the stages (spawn stages default `medium`, `in_thread` stages are priced at `small` on wall-clock but carry no spend) **plus the engine-MANDATED review spawns** — one thinker plan review per plan version, one code review per `spawn:developer` stage | monotone accumulator over `~/.local/log/claude-spawn-costs.jsonl`, summed **by `plan_path` alone** |
| `wall_clock` | ratio | Σ `effort-stage-minutes-<tier>` over every stage | monotone ACTIVE-minutes accumulator, stamped by `hook-engine-start.py` with an idle cap |
| `replans` | absolute | none — a plan's intended replan count is structurally 0 | count of `replan` history events |
| `interactions` | absolute | none — not derivable at all | `user_prompt_count`, hook-stamped |

The mandated reviews are in the estimate deliberately: they are derivable from the plan, they are charged to this task, and the actual counts them — omitting them would make every plan read as over-budget by exactly its own mandated review cost.

**The arming-relative window.** Every actual is compared as `actual − baseline`, where `baseline` is a snapshot of the actual vector taken at **arming**, which happens once, at `approve`. That is the only window the estimate describes: the estimate is derived from the approved plan's stages, and all of them execute after approval. Without the window a pre-classify prompt or an overnight idle interval would fire the trigger on its own. The mechanism is **armed-only by construction**: `divergence()` returns `None` unless both `effort_estimate` and `effort_baseline` are set, only `arm()` sets them, and only `approve` calls `arm()` — so a small-change session, which reaches `EXECUTING` from `ROUTED` without passing `approve`, is inert without needing a weight-class test some future route could forget. `arm()` always **re-derives** the estimate but snapshots the baseline **only if unset**: a substantive replan re-arms the approval gate, so `approve` runs a second time for the same task, and re-snapshotting there would rebase onto the accumulated actual, zero every ratio, and destroy precisely the scenario the trigger exists for.

**Re-derivation at every replan is the load-bearing detail.** `rederive()` is the estimate field's only writer and runs on all three `replan` branches, each after that branch's own stage-list update and after the branch logs its `replan` event — so the in-flight replan's own mandated review is counted. The comparison is therefore always against the plan the session is executing *now*, not the one it started from. A plan that contracts — stages dropped in response to a difficulty — lowers its estimate while the actual stands, which is the case the whole mechanism is sharpest on.

**The multiple, the non-degeneracy rule, and re-arm.** Ratio scales fire at `effort-divergence-multiple`; the absolute scales fire at `effort-replan-absolute` and `effort-absolute-interactions`. Values live in [`config.md`](../../config.md) and are referenced here by key only — that file is the single source of truth, and each row states its own basis. An estimate of 0 makes a ratio scale **inapplicable**, not infinite: that is both the division-by-zero guard and the reason there is no separate numeric floor row, since armed-only plus inapplicable-at-zero implies a floor already. A threshold of 0 on an absolute scale means **accounting-only** — measured and written to the ledger, never fired on. Re-arm has two belts, both required: the baseline is **rebased onto the actual vector at each firing**, so a plan that contracts below the accumulated actual cannot re-fire on the next command; and a further fire additionally requires at least one `replan` event logged since the last one — silent until a replan sets a new estimate. Ranking between simultaneously-diverging scales is by **distance past each scale's own trigger**, not by raw multiple, because a ratio scale trips at `5.0` and an absolute one at `1.0`.

**Two fire sites, and why the second is not optional.** The trigger is evaluated at `record-result` (on the PASSING branch — no stage is marked FAILED, the work genuinely passed) and at `verify-final`. `verify-final` is not an optimization: a plan that contracts can reach resolution without another `record-result` ever running, so without the second site such a session would carry its divergence all the way to `RESOLVED` unnoticed. On the paths that already enter `DIAGNOSING` — a FAILED record, a venue refusal at `verify-final`, a `failures` verdict — the trigger does not transition again; it attaches its framing to the existing directive and marks itself fired-and-rebased. The one deliberate exception is the repeat-digest branch, which returns `ESCALATE` from `VERIFYING` **without** entering the difficulty cycle: there the fire is neither spent nor silenced, because the rule is *"already diagnosing"* as an observed post-condition, not *"the record was FAILED"* as a proxy for it.

**The terminal is diagnose, never a question — at the fire site itself.** At the fire site the engine transitions `VERIFYING → DIAGNOSING`, seeds a `Difficulty`, and returns the `declare` directive under the `OVERCOME-DIFFICULTY` marker, pre-framed with the numbers that triggered it. It asks the user nothing there — a confirmation at that instant would reinstate exactly the supervisory burden the trigger exists to remove. Honestly: the *downstream* consequence can still reach the user, because a **substantive** replan coming out of that cycle meets the ordinary plan-approval gate like any other. What the trigger removes is the need for the user to *notice* the overrun, not the user's authority over a changed plan.

**The synchronous gate.** Not asking at the fire site is only sound if the fire is actually read before more work happens — otherwise a still-executing session (or coordinator) can carry right past a recorded-but-unread `state.effort_fires` entry, which is exactly the ed1e2dd0 incident this closes: a session running at 8.93x its own wall-clock trigger with the fire already recorded and never acted on. `gates.effort_fire_blockers` closes that gap: while the LAST entry in `state.effort_fires` carries no `"ack"` key, `dispatch` / `submit-plan` / `replan` all refuse, returning `Directive(ok=False, marker="ESCALATE_TO_USER", action="fire_acknowledge", data={"effort_fire": …})` — a typed directive the coordinator cannot silently drop, not a state flag it can choose to ignore. `fire-acknowledge` (see command table) is the only way to clear it, and it never deletes the entry — the fire and its resolution both stay in the append-only audit trail. This closes the two gaps the two existing fire sites left open on their own: a fire that rides along as a side-note on an unrelated FAILED-branch directive (`data["effort_divergence"]`) is now also a first-class blocker on the next dispatch, and `cmd_dispatch` — which previously had zero fire-awareness — now refuses until acknowledged.

**The turn-driven check, and what it does and does not close.** Both comparison points above are commands the coordinator *chose to run*: the two fire sites (`record-result`, `verify-final`) and the `gates.effort_fire_blockers` refusal on `dispatch` / `submit-plan` / `replan`. A session that runs long without reaching any of them — one stage worked for hours, a specialist that never returns, a next command that keeps being deferred — diverges unobserved however far past the multiple it goes; "needs no human to notice it" holds only once something calls the engine. `agentctl effort-check` (see command table) is the observation that does not wait for such a call, and `hook-effort-divergence-watch.py` (UserPromptSubmit, registered in `install-reminder-hooks.sh`) drives it on **every prompt**: it prints one advisory line naming the scale furthest past its own trigger — ranked on that normalized distance for the same reason `divergence()` ranks that way — and stays silent otherwise. The hook never blocks and always exits 0; a missing session, an unarmed trigger, a broken subprocess or a malformed payload are all silence. Throttling is per session **per scale**, in bands of "how many times past its own trigger", so a divergence that keeps growing speaks again while a static one does not repeat, and one scale's line never silences another's. **Scope:** this closes the case where the engine is present but has not been *called*. A session that never started the engine has no declared norm to measure against, and no hook can invent one (limit 6).

**Re-entering a RESOLVED task is now typed and counted.** `RESOLVED` has no outgoing edge but `pop_subplan`, so `reset` is the only way back into a closed order — and the fresh `SessionState` it builds zeroes the effort baseline, the replan count and every round-release counter on the way in. An unbounded reopen loop therefore paid nothing: each lap discarded the very budgets that would have bounded it. `gates.resolved_reentry_blockers` (pure, taking plain data) refuses a **same-task** reopen off a RESOLVED prior state unless `reset --reopen-reason <text>` records why the closed order is being re-entered, and at `effort-replan-absolute` prior reopens the reason alone stops being enough: it demands `--reopen-user-decision <text>` **alongside** `--reopen-reason` — the `round_release` release-active shape, escalating to an explicit user decision rather than another lap. The decision does not replace the reason; the two answer different questions (who authorized another lap, and what the last one missed), and the highest-friction reopens are the last ones that should be allowed to log an empty reason. Both refusals name their escape; `--force` is not one of them. The count lives on the cross-session task accumulator's `resolved_reentry` axis, read in `cli.py` and passed to the gate as an int: a counter kept on the `SessionState` that `reset` replaces would be zeroed by the act it exists to count. Re-arming for a **different** task, and the ROUTED / BLOCKED prior-node paths, are untouched; `task-reset` does not consult this gate.

### Renegotiation gate (GitHub #177, #128)

*Difficulty removed:* the ordinary DIAGNOSING-exit cycle is itself a `replan`, and a `replan` is exactly what re-arms the `replans` scale (§ above). Past `effort-replan-absolute`, closing one firing manufactures the next: `declare → investigate → critique → replan` clears the current fire only by incrementing the very counter the trigger re-compares against the same unmoved threshold, so every subsequent diagnosis loops the replan iterations without bound (GitHub #201: one session logged eleven such firings against a comparand constant at `3` throughout). Prose alone could not close this — `CLAUDE.md` already carried "a second `replans`-scale firing warrants asking the user, not another replan", and it was still not enough, because nothing stopped the loop from *executing* before a human ever read that sentence.

**The fix is a gate on `replan` itself, not a hint in the framing.** `gates.diagnosing_replan_blockers`, evaluated inside `cmd_replan` right after the existing `difficulty_blockers` check, reads the same live `replan_count` the effort-divergence trigger reads — never `state.renegotiations` (below) — because a single counter value cannot distinguish "this exact case was already decided" from "a new, independent difficulty cycle happens to reach the same threshold"; only a real reset of the live counter can clear the block. At or above `effort-replan-absolute`, a bare `replan` is refused outright: the caller must supply `--renegotiation-decision {continue,rescope,abandon} --renegotiated-by <name> --renegotiation-note <text>`, matched against the order's declared `customer_id` when the plan can be read (fail-open on an unparseable plan, mirroring `cmd_accept`'s identical existing pattern). `continue` and `rescope` call `task_accumulator.reset()` **before** the replan is allowed to proceed, so the completing replan's own bookkeeping starts the next `effort-replan-absolute` budget from 0, not from the stale threshold value — this is the same fix GitHub #201 asked for (its own option 3, escalate rather than repeat, plus its option 4, stop the closing replan from re-arming itself), now enforced structurally rather than left to the coordinator's memory of a prose rule. `abandon` takes the third path neither issue needed to consider: it stops the replan entirely, never touches `--plan`, and parks the session at `BLOCKED` via the existing reversible-park idiom `block` uses.

**`state.renegotiations` is a durable audit trail, not gate-clearing memory.** Every decision recorded through the gate above — who decided, when, at what counter value, and which branch fired — is appended to this list purely for a human to read back later; the gate itself never consults it, for the reason stated above (a stale journal entry cannot prove the *current* firing is the same case).

**A related, structurally different entry into DIAGNOSING closed by the same plan (GitHub #128):** a fail verdict recorded on an all-PASSED session previously left `verify-final` returning a passive `fix_stages` refusal, with no reachable difficulty cycle at all (`declare`/`investigate`/`critique` require `DIAGNOSING`; `reject` requires `RESOLUTION`, a node this session never reaches when acceptance already failed). `gates.failing_acceptance_requirements()` distinguishes a genuine rejection (an `AcceptanceReview` verdict recorded `fail`) from the other three `resolution_blockers()` causes (no review yet, a stale review, an unreadable plan), which keep their existing passive refusal unchanged; `cli._diagnose_acceptance_rejection()` routes only the genuine case into `DIAGNOSING`, mirroring `_diagnose_venue_refusal`'s transition/save/Directive shape and `cmd_reject`'s declaration pre-seed. This shares the renegotiation gate's underlying concept — a customer's negative verdict must always reach a reachable difficulty cycle — but is a separate code path with its own gate function, not a second caller of `diagnosing_replan_blockers`.

**`AGENTCTL_EFFORT`** (`1` forces on, `0` forces off; absent, active on SUBSTANTIVE sessions) gates **firing only, never accounting** — `gates.effort_active` is read at the fire sites, while `arm` / `rederive` / `refresh_spend` run unconditionally, so an exempted session still writes its ledger row. `resolve` carries `effort_estimate`, `effort_actual`, `effort_ratio_max`, `effort_fires` and `effort_interactions` onto the quality-ledger row.

**Honest limits.**

1. **The estimate is declared by the same actor it constrains.** Nothing prevents a comfortable estimate. The only mitigation is that estimate and actual both land on the quality-ledger row, so the thresholds — and the estimating habit — can be recalibrated against what they actually caught.
2. **The spend scale sees only what the cost ledger attributes to this plan's path.** Main-thread and `in_thread` tokens are never written there at all, and a spawn launched by hand under a different `--plan` path is charged to that other path. Symmetrically, the ledger is summed by `plan_path` with **no session filter**, so two live sessions naming the same plan path would each read the other's spend into its own actual — the repo's own `session_scope` / `hook-scope-conflict.py` machinery treats that overlap as a real case it guards against, not an impossible one. A task whose overrun lives entirely in the main thread therefore under-reads on spend; the wall-clock scale is what covers that case, and it is the only one that does, since the interactions scale ships disabled per limit 5.
3. **The hook-stamped accumulators are best-effort, and their errors are asymmetric.** A missed hook stamp under-counts interactions and active minutes. `_stamp_prompt_ts` is a whole-file read-modify-write, so a lost race against a concurrent engine write can revert a booked spend increment as well — under-count in that direction. The active-minutes accumulator can also **over**-count by up to one idle cap per lost write, because the add and the restamp are one read-modify-write.
4. **The window opens at approval, so the planning phase is invisible.** An overrun spent before `approve` — and any session that never passes `approve` — is outside the mechanism entirely. This feature's own planning phase, which ran three full review rounds, is the worked example of what that blind spot costs.
5. **Only three of four scales can fire.** Two on a ratio (spend, wall-clock) and one on an absolute count (replans); interactions ships accounting-only, with a named re-enabling contract on its `config.md` row rather than an open-ended zero.
6. **The turn-driven watch reaches only a session that started the engine.** `hook-effort-divergence-watch.py` removes the dependence on the coordinator calling a *particular* command, not the dependence on the engine existing: a session with no state file has no approved plan, hence no norm, and the hook is silent by design rather than by accident. Work driven entirely outside the engine remains outside this mechanism — the same boundary limit 4 draws in time, drawn here in enrolment.
7. **The reopen count is keyed on `task_id` equality, and the task slug is chosen by the actor it counts.** `resolved_reentry_blockers` recognizes a re-entry only when the new `--task` string equals the resolved session's; the same order re-entered under a reworded slug reads as a *different* task, arrives at zero prior reopens, and bypasses both the reason and the ceiling. Nothing in the engine can tell a genuine new order from a rename, and `hook-engine-start.py` invites the confusion by suggesting `agentctl reset --task <slug>` for a new task in exactly the situation where the old one is still open. The count is therefore a friction on the honest path, not a lock — which is what a counter whose key is supplied by the counted party can ever be.

### Autonomous replanning within the approved boundary

*Difficulty removed:* an order the user already approved stopped at every replan for a fresh user decision — including replans that only re-sequenced work inside what the user had approved — so the user's attention was spent re-approving what they had already authorized, and a `replans`-scale fire (a symptom of planning trouble, not of the user's stake) was routed to them too.

**The boundary is computed, not judged.** `gates.autonomy_boundary(ledger_snapshot, resolved_plan, first_verdicts)` is a pure function over the order-digest-keyed approvals ledger (`order_approvals`) and the candidate plan's resolved view (`plan_resources.compute_boundary_view`). It returns `{eligible, reason, order_changed, extra_resources, unresolved_changed_commands, thinker_pass, open_effort_fire}` and is eligible only when: the order's digest is unchanged from the user-approved version; every resource the plan touches (op-exact, e.g. `vcs_ref(origin, main, push)` is never covered by a feature-branch push) is inside the ledger's approved set; every changed command the engine cannot resolve to a typed resource is an engine-executed fixed text (`verify_command`/`negative_control`/`final_check`) vouched for by the order's **first** thinker verdict (write-once, whole-plan, pass/revise only) — a changed declared or output-artifact-derived rule always goes to the user; and no spend/wall-clock fire is still open for the user. Protected permission surfaces are never inside the boundary.

**Routing.** `submit_plan` and every `replan` Directive carries `data["autonomy"]`. A substantive change inside the boundary returns action `self_approve` (no `PLAN-READY`), and `approve --by agent` is accepted only for a ledgered order with an eligible boundary; the plan-review, premise and submission gates still apply, the presentation and grants-approval blockers are replaced by the boundary, the ledger is never stamped by an agent approval, and the `approve by=agent` history event lists the autonomy lists and any active overrides as `name=value`. A substantive change outside the boundary — including a refinement that moves the order digest or adds a resource — returns `PLAN-READY` to the user; `cmd_drive` mirrors both routes.

**Open spend/wall-clock fire.** While a spend or wall-clock fire is open for the order, `resolve-permission --by agent` and the dispatch self-grant path are refused with the reason `open spend/wall-clock fire owed to the user`; only a customer-authored acknowledgement or a customer re-approval closes the marker. A customer's `--scope stage` permission grant widens the order's approved set; a `once` grant does not.

**The `replans`-scale fire is the agent's own difficulty.** For a ledgered order the fire Directive (and the `dispatch`/`replan`/`submit_plan` refusal) names the agent's planning-difficulty cycle — `declare → investigate → critique (differences_to_remove) → normalize` — instead of `ESCALATE-TO-USER`. `fire-acknowledge --by agent` is accepted only for a `replans` fire, decision `revise`, with a difficulty record declared **after** the fire (`difficulty_id_at_fire`), not already consumed (`state.agent_ack_difficulty_ids`), carrying a non-empty `differences_to_remove` and a real `normalize` record. `continue`/`abandon` and any spend/wall-clock acknowledgement by the agent are refused. `effort.record_fire` keeps the `replaced_baseline`; the agent's acknowledgement restores the non-`replans` baselines from it so the swallowed spend/wall-clock progress still counts toward the user's own fire. The closing `replan` refuses `--normalization-waiver` and a corrected plan whose operative surface is unchanged.

**Diagnosing ceiling.** At `effort-replan-absolute` the agent may itself record `--renegotiation-decision continue --renegotiated-by agent` — only after a ceiling refusal was recorded (`renegotiation_ceiling_difficulty_id`), with a complete difficulty record declared after it (same conditions as above) and a plan inside the boundary. `rescope` and `abandon` by the agent are refused; they change the scope or end the order.

**Round-release override.** When the review-round budget is spent (`gates.plan_review_round_release_active` / the cross-axis friction release) `plan-review --verdict override --reviewer agent` records the coordinator's own decision, never counts as the first thinker verdict for the boundary, and the next present/`PLAN-READY` Directive carries `data["agent_review_override"]` so the user sees it.

## Optional stages

*Difficulty removed:* adjacent backlog debt a planner notices while planning an order either inflates the order's scope or goes unrecorded. A stage may declare `optional = true` and `backlog_issue = "<repo>#<n>"`; the user decides at approval whether it is done.

- **Loader rules** (`plan.optional_stage_violations`, `plan.optional_rest_violations`): at most `plan.MAX_OPTIONAL_STAGES` (2) optional stages; each needs a well-formed `backlog_issue`, and a required stage may not carry one; no required stage depends on an optional one; at least one stage stays required; no `[meta.order.coverage]` entry and no `[[final_check]]` may rest only on optional stages (`check-order-coverage.py` reports the same rule). An optional stage is exempt from order-requirement traceability, since it traces to its issue. `optional` and `backlog_issue` are part of the stage's structural signature and the plan content digest (conditionally, so a plan with no optional stage digests as before).
- **`approve --skip-optional <index>`** (repeatable) is the customer's decision: refused with `--by agent`, for an unknown or non-optional stage, and for a stage a kept stage depends on. Each declined stage gets `StageStatus.SKIPPED` and a `skip_optional` log event. A SKIPPED stage is never in `ready_stages`, so `dispatch` never picks it.
- **Settled, not passed.** Every "the plan is finished" decision goes through `state.is_settled` / `SessionState.all_stages_settled` (PASSED or SKIPPED): the resolution gate and the RESOLVED invariant, `verify-final`, `next-stage`, the tracker progress summary, and the effort estimate (a SKIPPED stage is not priced). `all_stages_passed` remains as an alias for out-of-engine hooks. Reachability counts only non-optional producers, since an optional output may never be produced.
- **One carry rule** on both the approve-time refresh and a substantive replan: a stage whose definition changed returns to PENDING (PASSED or SKIPPED alike, so the customer chooses again at re-approval); an unchanged declined stage stays SKIPPED. A no-change or refinement replan resets only FAILED stages.
- **A declined stage is never re-opened.** `reject` without `--stage` targets the last non-SKIPPED stage, `reject --stage <n>` naming a SKIPPED stage is refused, and `pop-subplan` does not mark a SKIPPED originating stage PASSED. Every `approve` of a plan that holds a SKIPPED stage re-runs the stranded-dependency check, so a replan that adds a dependency on a declined stage is refused there.
- `plan-render` marks optional stages with their backlog issue.

*Universal quantification:* [`../tests/test_optional_stages.py`](../tests/test_optional_stages.py) carries two AST + line-grep enumerators over `scripts/` (excluding `tests/`): one fails on any single-stage `PASSED` comparison, the other on any write of a stage status or outcome, each not on its allowlist (one reason per entry; a stale entry also fails). The bounds above have catalogue entries `skipped-is-settled`, `optional-not-depended`, `optional-max-two`, `optional-coverage-rule` and `reject-spares-skipped` in [`../tests/mandate_mutation_control.py`](../tests/mandate_mutation_control.py).

## Mandate

A **mandate** is the user's one-time, bounded grant of authority to the background debt cycle (a timer-driven worker that triages the backlog, fixes eligible issues and opens review-gated pull requests). It is not a session and has no node in the state machine: it is a standing record under `~/.claude-agent/agentctl/mandates/<id>/` (override: `$AGENTCTL_MANDATE_DIR`, which the tests set), and the `mandate-*` verbs are session-independent in the way `task-reset` is (`--session` is accepted and ignored so the default-session injection does not crash argparse).

*Difficulty removed:* an authority granted once and used unattended is only as safe as its bounds, and a bound enforced by a model's judgement is a suggestion. The split is the engine's usual one. **`mandate.py` holds every decidable bound as a pure function** (no filesystem, process or clock; `now` is a parameter, and a test pins the import list): the gate (expired / paused / breaker open / daily and weekly spend over a rolling 24 h and 7 × 24 h window / per-cycle minutes), issue eligibility, the triage filter, selection, the baseline-relative test verdict, per-item overrun, the breaker policy, and the constitution classifier. **`mandate_store.py` is the I/O half**: atomic JSON, append-only logs, the `cycle.lock` flock whose text is the holder's pid, the state fingerprint, and stop/resume. The model supplies only perception (triage verdicts, the fix, the review).

State files, one directory per mandate: `mandate.json` (the record), `events.jsonl` (audit log), `labels.jsonl` (which label the cycle, not the user, applied — the repo owner's account applies every label, so only this log can tell the two apart), `items.jsonl` (one row per item taken: outcome, PR, cost, test and review verdicts), `cycles.jsonl` (one row per cycle, carrying `digest {notifier, ok, delivered_at}`; `mandate_store.read_digests` returns the per-cycle delivery records the eligibility rule takes), `cycles/<cycle_id>/commands.jsonl` (every external command the driver ran), `cycle.lock` (holds the pid of the cycle that owns the flock). The shapes are in the `mandate_store` module docstring; the fingerprint the driver uses to detect a spawn tampering with mandate state covers `mandate.json`, `events.jsonl`, `labels.jsonl`, `cycles.jsonl` and `items.jsonl` (the driver appends to them only between spawns, never during one); the per-cycle `commands.jsonl` and the lock are outside it.

| Verb | Authority | Effect |
|---|---|---|
| `mandate-grant --by <user> [--days N] [limit flags]` | user only (`AGENTCTL_USER_AUTHORITY_VERBS`; `--by agent` is refused) | creates the record; refuses an id that exists |
| `mandate-extend --days N --by <user>` | user only | pushes expiry past the later of now and the current expiry |
| `mandate-resume --by <user>` | user only | unpauses, closes the breaker, re-enables `agent-debt-cycle.timer` |
| `mandate-stop` | open to the agent (it only narrows authority) | pauses first, then disables the timer, then kills the cycle's process tree **only if** the lock is held — an idle mandate is never killed and prints `no running cycle`; a corrupt record does not stop it (the pause is best-effort), and a held lock whose pid is unknown is reported, not guessed at |
| `mandate-status` | read-only | the record, the spend windows, the gate verdict with every refusal reason, whether a cycle is running |

The bounds, as they are decided: a cycle may start only while the mandate is unexpired, unpaused, its breaker closed, and both spend windows below their caps; spend is the sum of spawn-cost rows whose `plan_path` lies under the mandate directory plus `judge-cost` and `overrun-charge` events, and an unreadable timestamp counts in both windows. An issue is eligible only if the repo owner authored it, it is in the backlog or difficulty domain, no open pull request references it, and nothing vetoes it (`no-auto`, `auto-no`, `process-umbrella`). A user-set `auto-ok` is eligible at once; a cycle-set one never is for `severity:high`, and otherwise only after a *delivered non-file* digest plus the veto window. Only a **failed** item (a newly failing test after one rerun, a reviewer reject, a constitution, permission or org-neutral rejection, tampered mandate state) opens the breaker; an `overrun`, a `declined` item and a `limit` stop do not. So "pause after one failed cycle" means one failed item, not one over-budget one, and a cycle that merely ran long starts again the next night. A diff touching a constitution path — on either side of a rename or copy — or any `settings*.json` is rejected; the default list names the mandate machinery itself, the permission and widening tables, the hooks and the verification scripts.

Each bound has an entry in [`../tests/mandate_mutation_control.py`](../tests/mandate_mutation_control.py): an exact textual mutation of the production line and the test ids that must go red, run in-suite by `test_mandate_mutation_catalogue.py` (the first run of a new catalogue goes through `scripts/cap-run.sh`).

## Cost tracking

`record-result` attributes spawn-stage cost from `~/.local/log/claude-spawn-costs.jsonl` (written by `spawn-specialist.py`) and stamps `cost_usd / duration_ms / spawn_count` on each spawn stage's `Outcome`. In-thread and main-session tokens are **not** split per stage — use `scripts/cost-report.py` for the whole-session estimate.

`verify-final` aggregates per-stage attributed costs into `SessionState.cost` (a `CostRollup`). `resolve` includes the `CostRollup` in `Directive.data` so the manager can fill the experience-leaf `## Cost` section from real figures rather than a TODO placeholder.

## State location

Session state is JSON at `~/.claude-agent/agentctl/state/<session_id>.json` (the durable machine-written record, kept separate from the human/LLM-authored TOML plan).

Alongside it sits a second, append-only store: `~/.claude-agent/agentctl/edit-log.jsonl` (`config_root.agentctl_edit_log()`), fed by `edit_ledger.py`. Two feeders write to it: the `hook-scope-track.py` PostToolUse chokepoint for every Edit/Write, and the direct-IO canon writers (`record-experience.py`, `stamp-memory-dates.py`, the setup shell scripts) that bypass that hook and instead call the module's `stamp(file, tool, session=None)` primitive — a fail-open wrapper over `append()` that names its feeder in the row's `tool` field. Both feeders drop scratch paths via `exempt_paths.is_ledger_noise` (`/tmp`, `$TMPDIR`, `$AGENTCTL_SCRATCH_ROOTS`), so the store keeps only durable edits. Unlike the session-state file, which holds one current snapshot per session, the edit-ledger accumulates one row per edit, forever. Each row carries **two ids**: `session_id` (the agent that made the edit, possibly a subagent) and `env_session_id` (the root session's `CLAUDE_CODE_SESSION_ID`) — so a later query can join a commit back to every subagent edit made under its root session. Query it with `../edit-ledger.py`; see [`../README.md`](../README.md#change-attribution) for the full convention.

The `Agent-Session`/`Agent-Task` commit trailer that ties a commit to a session is built by `../agent_commit_trailer.py`, called from both the git `commit-msg` hook and arc's `arc-land-pr.sh` so the two VCS contexts stamp byte-identical trailers. Arc has no `commit-msg` hook to test against a live landing, so trailer-injection coverage for arc is verified by the injection *intent* that `arc-land-pr.sh --dry-run` prints (a Core-side test) rather than by an actual arc landing.

## Two config roots

Read this before adding a gate whose satisfier is a hook.

There are **two** roots, and they are not the same object:

- the root the **harness** loads hooks from — `$CLAUDE_CONFIG_DIR`, else `~/.claude`, which is the
  CLI's own rule and nothing else's (`lib/config_root.harness_config_root()`);
- the root the **agent system** installs into — `$CLAUDE_AGENT_HOME`, default `~/.claude-agent`
  (`lib/config_root.agent_home()`).

Under `claude-task` / `claude-agent` the two coincide. Under a bare `claude` they diverge, and that
divergence is **deliberate**: the personal root is the user's, the system root is the agent's.
Nothing in this repo installs the system's hooks into the personal root —
`install-reminder-hooks.sh` covers `$HOME/.claude/settings.json` prune-only, adding to it never.

The consequence for an engine author is exact: **a gate whose proof is written by a hook is
unsatisfiable in any session whose harness root does not carry that hook.** The delivery gate met
this in the worst form — `approve` refused for "no delivery proof recorded" while the hook that
writes the proof had never been registered in the loading root, so the refusal named a remedy
("let the delivery hook verify the turn's transcript") that could not be reached.

What the engine can and cannot do about it:

- it **can** observe wiring — `lib/hook_wiring.probe(basename, root)` reads the harness root's
  settings chain and answers `WIRED` / `ABSENT` / `UNKNOWN`. `UNKNOWN` is first class: an unreadable
  or unmodelled member is not evidence of absence, and only a positively established `ABSENT` may
  be reported as one;
- it **can** diagnose — `gates._no_stamp_blocker` consults the probe *only on the branch already
  about to block*, so the read is off every passing path, and any exception degrades to the
  undiagnosed wording rather than raising;
- it **cannot** repair, and must not try. Installing into the personal root would overwrite a
  deliberate choice of the user's. The report is the whole intervention:
  `hook-canon-guard-wired-check.py` runs at SessionStart and names every gate-bearing hook
  (`lib/hook_wiring.GATE_BEARING_HOOKS`) that is absent from the loading root, together with the
  enforcement each absence disables. Presence is not the whole story: a hook can be WIRED and
  still never finish, because the harness kills it at its registered `timeout`. The same file
  checks a second, independent axis for that — every hook in `lib/hook_wiring.TIMEOUT_REQUIREMENTS`
  registered with a timeout below its own whole-invocation judge budget. The SessionStart path
  reports both axes fail-open (established problems only, never blocks). `--check-timeouts` is a
  separate one-shot entry point over the timeout axis alone, and its polarity is the opposite:
  FAIL-CLOSED — a shortfall, an UNKNOWN, or an exception inside the check itself all exit non-zero,
  because a check whose only job is to refuse must not default to "fine". It has no caller yet; a
  later stage is expected to wire it as a gate of its own (e.g. into `install-reminder-hooks.sh`'s
  own final check), not to run it as a hook;
- it **must not** change the verdict on wiring. A missing prover changes what a gate *says*, never
  whether it blocks. Letting approval through because the hook is missing would convert every
  un-onboarded machine into an ungated one.

Where the gate genuinely cannot be satisfied, the escape must stay reachable, and each escape must
record a **typed** reason (`confirm-delivery --escape-reason`, one of
`delivery.DELIVERY_ESCAPE_REASONS`) so escapes are countable rather than an archive of free-text
notes — `--kind replan_diff` takes the identical escape for the replan-authorization gate
(§ Replan authorization), not only for `essence`/`full`. `scripts/escape-hatch-report.py` is the standing count, and the inventory of the engine's
other hatches. The norm behind all of this:
[`verdict-covers-the-evidence-domain-it-claims`](../../memory-global/leaves/principles/verdict-covers-the-evidence-domain-it-claims.md).
